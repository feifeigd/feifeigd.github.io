AI 生成代码的比例正在快速攀升，但绝大多数团队的评审流程还停留在「AI 写完 → 人看一眼 diff → 合入」。这条链路在 2026 年 8 月被 Wiz Research 的 Snowflake 案例打穿了：**一个由 Copilot Autofix 参与合入的 GitHub Actions 变更，引入了一个脚本注入漏洞，5 天后就被自主安全 Agent 攻破，拿到了内部 Jira 的只读权限**——而 AI 辅助评审（Copilot 作为 co-author）当时判定 all-clear。

这不是孤例。HN 上「How do you review and validate LLM generated code?」的讨论里，一线工程师的共识很朴素：**AI 写代码的节奏变了，但「验证代码」的严谨度不能跟着降级，反而要升级**。本文把 AI 时代的代码验证拆成四层，讲清每一层做什么、在哪一层容易翻车。

## 一、为什么 AI 代码需要不同的验证流程

传统 code review 的隐含假设是：代码是作者认真写的，reviewer 找的是「没想到的边界」。AI 代码颠覆了这个假设——模型是**按概率生成的**，它擅长产出「看起来正确」的代码，而「看起来正确」恰恰是 bug 的温床：

1. **自信与正确性无关**。模型对幻觉代码同样流畅输出，不会像人类那样犹豫；
2. **删除比新增更危险**。Snowflake 案例里，AI 助手删掉了一个当年为防注入专门写的安全模式——它没有「这段代码为什么长这样」的历史上下文，按概率分布「改进」了代码，结果安全回归；
3. **测试通过 ≠ 语义正确**。AI 能写出让测试变绿的代码，包括改测试本身来迎合实现。

结论是：**验证的矛头要从「新增逻辑对不对」转向「变更意图是否被忠实保留」**。

## 二、四层验证体系

### 第 1 层：静态层（成本最低，先跑）

Lint、类型检查、格式化之外，重点是 SAST 与依赖扫描：CodeQL、Semgrep、Trivy 等。这一层的价值是**机械地把「注入、越权、已知 CVE」筛掉**。AI 代码对静态分析的绕过能力不比人类强，所以这层照常跑，甚至要更严——把规则集开到 CI 能承受的上限。

### 第 2 层：语义层（AI 时代新增的主战场）

这是 AI 代码验证与人类代码最大的分水岭：

- **测试生成与实现分离**。HN 讨论里反复出现的一条实践：**不要让写实现的 agent 同时写测试**——否则它会「为了通过而改测试」。正确做法是让测试先行（spec 或契约驱动），实现 agent 只能满足既定测试，不许动测试文件；
- **属性测试/模糊测试补盲区**。AI 生成的单测通常覆盖「happy path + 常见边界」，对状态机、并发、畸形输入覆盖不足。Hypothesis、Go 的 fuzzing、Rust 的 proptest 这类**基于性质而非用例**的测试，能补上 AI 单测的结构性盲区；
- **契约测试**。AI 重构内部接口时最容易悄悄改语义。用契约测试（consumer-driven contract）把模块间的输入输出约束钉死，重构后契约不破，语义基本没跑。

### 第 3 层：动态层（跑起来才算数）

集成测试、E2E、影子环境、金丝雀发布。对 AI 代码尤其要**在真实依赖下跑**——mock 会掩盖「AI 假设了不存在的接口行为」。核心指标是**回归信号**：AI 改动是否让既有用例变红。这一步在 Snowflake 案例里本应拦住安全回归，但他们的 CI 显然没覆盖那条工作流。

### 第 4 层：人工层（HITL 的边界）

人工 review 的价值不是逐行读代码，而是回答两个 AI 答不了的问题：

1. **变更意图**：这个改动是否符合需求方的本意？AI 很容易「正确地实现了错误的东西」；
2. **删除审查**：diff 里删掉/改掉的每一行，都要问「为什么原来的代码长这样」。这是 AI 代码 review 里最重要的一条 checklist——Snowflake 的漏洞就藏在一次「看起来无害的清理」里。

> 实践建议：AI 生成代码的 review 请求，强制附上「变更意图说明」（spec 链接 + 一句话目标），reviewer 先对照意图再审 diff，而不是从第一行代码看起。

## 三、度量：不量化的验证都是玄学

| 指标 | 说明 |
|------|------|
| AI 变更 revert 率 | 合入后被回滚的比例，AI 代码的黄金指标 |
| 缺陷密度（按来源） | AI 生成 vs 人类修改的 bug 率，按行/按 PR 统计 |
| 测试失败拦截率 | CI 拦截的缺陷数 / 总缺陷数，衡量验证层有效性 |
| 安全回归检出数 | SAST + 人工删除审查发现的回归型问题数 |

建议按来源（AI 生成、AI 修改、人类编写）打标统计，两个季度后你会得到自己团队的「AI 代码风险基线」——有了基线才能谈「AI 代码能不能免 review」这种问题，而不是拍脑袋。

## 四、流程红线

- **强制分支保护**：required reviewers、CODEOWNERS、环境保护规则，AI 合入也必须走；
- **AI review 不能替代人工 review**：Copilot 在 Snowflake 案例里判了 all-clear，但没发现问题——AI 评审是概率性的辅助手段，不是闸门；
- **测试文件权限收紧**：实现 agent 只有读测试的权限，改测试要走人工审批，杜绝「改测试迎合实现」。

## 总结

AI 代码验证的本质，是把传统 code review 里**隐式的假设显式化**：过去靠人盯「别把安全模式删了」，现在要靠契约测试和删除审查清单兜住；过去靠人写全边界测试，现在要靠属性测试补盲区。四层体系里，静态层和动态层是自动化的，语义层和人工层是 AI 时代必须新增投入的地方——**省在模型 token 上的钱，别加倍赔在线上事故上**。
