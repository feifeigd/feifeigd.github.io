线上有一套 4 副本的推理服务，每个请求前面挂着 6k token 的 system prompt 和工具定义，后面是不断增长的会话历史。网关当时用的是最朴素的轮询。运维看板上 prefix cache 的命中率一直在 70% 以上，看起来挺好，但同一批会话的 TTFT p99 每隔一段时间就冲到几十秒。

排查下来是两件事叠在一起：命中率高的是 system prompt 那一段（每个副本都有，谁都能命中），真正贵的会话历史只有 65% 左右命中——因为下一个 turn 落到哪个副本是随机的，历史只有 1/4 的概率在。而 decode 前的 prefill 成本跟未命中 token 数成正比，剩下那 35% 的未命中就足够把队列顶满。

把这件事按同样的流量重算一遍：换成前缀亲和路由，p99 从 749 秒掉到 56 秒，平均服务时间从 1.48 秒降到 0.86 秒。但这不是「命中率高了所以快了」这么一句话能交代的：亲和路由本身有两个能把系统打死的退化形态，命中收益也不是线性放大的。

这篇把这件事算成账：先算清前缀命中到底省了什么，再把路由写成一个收益函数，然后用一套事件驱动模拟器量出四种策略和六档容量的差别。

## 一、命中省掉的是 O(L²)，剩下的是 O(T·L)

前缀缓存最容易被误解的一点是「命中就等于这段 token 不要钱」。实际不是：命中让你跳过这 L 个 token 的 QKV 投影和前馈，但新来的 T 个 token 仍然要对全部 L 个历史位置做 attention，KV 还是要从 HBM 读进来。

把两层成本写出来，单位是秒：

```python
# 70B, 80 层, GQA 8 个 KV head, head_dim 128, BF16
P, L, T = 70e9, 20000, 600
kv_bytes = 2 * 80 * 8 * 128 * 2          # 327,680 B/token ≈ 320 KiB

miss_cost = 2 * P * (L + T) / flops       # 全量复算：算力受限
hit_cost  = T * L * kv_bytes / bw         # 命中：只剩 KV 读，带宽受限
```

代入单卡 H100（有效算力按 400 TFLOPS、可用带宽按 3.35 TB/s）：

| 口径 | 全量复算 20k + 600 | 命中后只算 600 | 倍数 |
|---|---|---|---|
| TP=1 | 7,210 ms | 1,174 ms | 6.1x |
| TP=8 | 901 ms | 146 ms | 6.2x |

TP 从 1 到 8，算力和带宽同比例放大，倍数几乎不变。这不是巧合，把两式相除就能看出倍数只由三个量决定：

```
倍数 = 2P · BW / (T · kv_bytes · FLOPS)
```

也就是说收益全看 **T/L 之比**：600 个新 token 摊在 20k 前缀上只有 6 倍；如果只追加 100 个 token，倍数是 36 倍；反过来一次性塞 2000 个新 token，只剩 1.8 倍——这时候它更接近一次正常 prefill，缓存帮不上多少。

这条算术解释了为什么 agent 场景（历史长、每次只加几百 token）对前缀缓存极度敏感，而长文档问答（每次塞整篇文档）几乎无感。它也解释了为什么「命中率 90%」这个数字单独看没有意义：得乘上这批请求的 T/L 分布，才是真正的延迟收益。

## 二、命中率是路由的函数

一个请求的前缀通常由三段拼起来，三段的复用范围完全不同：

- **system prompt + 工具定义**：租户级共享，可以主动预热到所有副本，命中率跟副本数无关；
- **会话历史**：只有处理过这个会话的副本有，命中率随副本数 1/N 衰减；
- **用户本轮输入**：永远不命中。

第一段和第三段跟路由无关，只有第二段是路由能动的。模拟器里把这个区分直接量出来（同样的流量，4 副本，6k system prompt）：

| 策略 | 总命中率 | 只看会话历史 | 平均服务时间 | p50 | p99 |
|---|---|---|---|---|---|
| 轮询 | 76.8% | 65.6% | 1.48 s | 254 s | 749 s |
| 会话粘性（一致性哈希） | 90.6% | 90.9% | 0.86 s | 4.1 s | 56 s |
| 贪心亲和（只看命中最多的副本） | 87.0% | 84.3% | 1.02 s | 4,501 s | 9,662 s |
| 收益函数路由 | 89.7% | 88.0% | 0.90 s | 1.7 s | 15 s |

注意第一行的 p50：轮询那套不是「慢了 1.7 倍」，而是**已经过载**。平均服务时间 1.48 秒、4 个副本，容量上限是 2.7 req/s，而这份流量是 2.9 req/s。超过容量之后排队时间不是线性的，是指数往上翻的——util 96.6% 换算下来 p50 就是分钟级。

这也给出第一个可落地的判断：**前缀亲和不只是优化延迟，它改变的是容量**。服务时间 0.86 秒对 1.48 秒，同样 SLO 下需要的副本数是 2.5 个对 4.3 个，差 1.7 倍。跟各家推理框架论文里报的量级（数倍，视复用率而定）对得上，只是别指望十倍。

## 三、把路由写成收益函数

第三种策略「贪心亲和」是个很好玩的失败案例：它几乎把所有流量都发给了一个副本（max/mean 负载比 = 4.00），因为每个副本的 system prompt 都命中，`max()` 在平局时永远返回列表里的第一个。p50 直接干到 4500 秒。

修法不是换个平局规则，而是别用「命中块数」当目标函数——目标和 SLO 不一致。正确的做法是把两边换算成同一个单位（毫秒），取差：

```python
def pick(replicas, prefix, now_ms):
    best, best_score = None, -inf
    for r in replicas:
        matched_ms = r.match(prefix) * BLOCK / PREFILL_TOK_PER_MS   # 命中能省多少
        wait_ms    = max(0.0, r.busy_until - now_ms)                # 去它那儿要等多久
        score = matched_ms - wait_ms
        if score > best_score:
            best, best_score = r, score
    return best
```

两行代码，两个退化形态自动消失：

- 副本空闲时 `wait_ms` 接近 0，`matched_ms` 占主导 → 自然去做亲和；
- 热点副本排队变长时 `matched_ms` 被 `wait_ms` 抵掉 → 自然把流量溢出到冷副本。

表里第四行就是这个策略，命中率比粘性略低（89.7% 对 90.6%，因为偶尔主动放弃命中去做均衡），但 p99 好 3.7 倍（15 秒对 56 秒）。这是一个典型的取舍：**亲和是为了省算力，均衡是为了压尾延迟，两个目标在饱和点附近直接冲突**，只能用收益函数把它们放进一个标量里。

顺带说一句，会话粘性路由在这里表现已经很好（p99 56 秒），代价是它不感知负载：只要某个会话很长，它的副本就可能一直比别人忙。热租户那组实验里（50% 的会话共用同一个 system prompt），粘性的 max/mean 负载比到了 1.12，p99 从 24 秒起步；收益函数路由是 1.11、6.6 秒。

## 四、模拟器长什么样

上面所有数字出自这套事件驱动模拟器，核心不到八十行，可以直接跑。工作负载按 agent 流量建模：会话按泊松到达，每个会话 3 到 20 个 turn，turn 之间隔 1.5 到 5 秒，前缀按块增长。

```python
BLOCK = 16                      # vLLM 默认 block 粒度
CAP_TOKENS = 131_000            # 每副本允许 prefix cache 占用的 KV 额度

class Replica:
    def __init__(self):
        self.cache = OrderedDict()       # block hash -> None，LRU 顺序
        self.busy_until = 0.0

    def match(self, blocks):             # 最长前缀匹配，按块对齐
        n = 0
        for b in blocks:
            if b in self.cache:
                n += 1
            else:
                break
        return n

    def insert(self, blocks):
        for b in blocks:
            if b in self.cache:
                self.cache.move_to_end(b)
            else:
                self.cache[b] = None
        while len(self.cache) * BLOCK > CAP_TOKENS:
            self.cache.popitem(last=False)      # LRU 淘汰

def simulate(policy, requests, n_replicas=4):
    reps = [Replica() for _ in range(n_replicas)]
    for when, prefix, new_tok, sid in sorted(requests):
        r = policy(reps, prefix, when, sid)
        hit = r.match(prefix)
        cost = (len(prefix) - hit) * BLOCK / PREFILL_TOK_PER_MS \
             + new_tok * len(prefix) * BLOCK * KV_BYTES_PER_TOKEN / KV_READ_BW * 1000
        start = max(when, r.busy_until)
        r.busy_until = start + cost
        yield start + cost - when            # 这个请求的 TTFT
        r.insert(prefix)
```

几个刻意写清楚的地方：

1. **成本模型就是第一节那两式**，没有再引入别的常数，所以「命中快多少」这个结论和代码是可对账的。
2. **命中判定按 block 对齐**，和 vLLM 的 `block_size=16`、SGLang 的 radix tree 一致；差一个 token 就会整块不命中，这一点后面还会踩到。
3. **缓存容量是硬上限**，用总 KV 额度而不是条目数，因为真实瓶颈是显存。

## 五、容量才是隐形天花板

第二组实验固定粘性路由，只改每副本的 prefix cache 额度：

| 每副本额度 | token 数 | 总命中率 | 平均服务时间 | p99 |
|---|---|---|---|---|
| 8k blocks | 131k | 90.6% | 0.86 s | 56 s |
| 4k blocks | 65k | 86.4% | 1.05 s | 285 s |
| 2k blocks | 32k | 47.9% | 2.76 s | 6,082 s |
| 1k blocks | 16k | 17.7% | 4.10 s | 10,792 s |

是一条很陡的 S 曲线，不是线性的：从 131k 掉到 65k，命中率只退 4 个点；再掉到 32k，命中率腰斩、服务时间翻三倍、系统直接过载。

拐点位置有明确的算术：**每副本额度必须装下「该副本上并发会话数 × 平均前缀长度」**。这份负载里副本上同时活跃约 20 个会话、平均前缀 7k token，乘起来 140k token，正好落在 131k 这条线附近——低于它就开始互相淘汰。

更难看的是 16k 那一档：命中率 17.7%，比容量 32k 时还低。原因是 16k 装不下 6k 的 system prompt 加上几个会话历史，LRU 在插入新前缀的过程中把刚插进去的块自己淘汰掉了，形成自旋 thrash。这种状态下命中率不是缓慢下降，而是**归零**——和 CPU 上 page cache 抖动是同一个病理。

工程上的推论：容量规划要从「并发会话数」倒推，而不是「反正有剩余显存就全给」。反过来说，也不能给太少：额度不足时亲和路由不但没收益，还会因为频繁淘汰把带宽打满。

## 六、扩容、重平衡和滚动发布

第四组实验是 4 副本扩到 6 副本：

| 策略 | 副本数 | 总命中率 | p50 | p99 |
|---|---|---|---|---|
| 粘性 | 4 | 90.6% | 4.1 s | 56 s |
| 粘性 | 6 | 90.5% | 1.3 s | 20 s |
| 收益函数 | 4 | 89.7% | 1.7 s | 15 s |
| 收益函数 | 6 | 90.2% | 1.0 s | 3.9 s |

有两个反直觉的地方。

**第一，扩容后命中率没掉。** 一致性哈希重排会把会话重新分配，新副本缓存全冷，理论上每个活跃会话都要多付一次冷 prefill。但这份负载里会话本身有 3 到 20 个 turn，每个会话只需要一次冷启动就被重新暖起来，摊到总请求数上不到 1%。如果换成一次性请求为主的流量（每个会话 1 个 turn），同样的重排就是灾难——成本是「活跃会话数 × 前缀长度」，500 个会话 × 8k token 就是 400 万 token 的冷算，按 2.8 tok/ms 折算约 1,430 秒单副本算力，摊到 4 个副本上也是六分多钟的集体排队，而且全部砸在扩容那一刻。

所以扩容策略要看会话长度分布来决定：长会话流量可以直接重排；短会话流量要么按虚拟节点做最小迁移，要么用「新副本慢启动 + 只把新会话分过去」的方式让缓存自然变热。

**第二，副本越少，收益函数路由的优势越大。** 4 副本时 p99 15 秒对 56 秒，6 副本时 3.9 秒对 20 秒。饱和度越高，路由的边际价值越大——这也解释了为什么小规模部署（3 到 6 个副本）反而更值得上亲和，大规模部署里亲和主要省的是电费和 GPU 时。

滚动发布是同一个问题的极端版本：新 pod 起来时缓存完全冷，如果立刻接满流量，等于在发布窗口里凭空多出一次全量 prefill。可行的做法是发布前把 system prompt 和工具定义预热进去（只要把一段固定前缀发一次 prefill 请求，不要让模型 decode；用 `max_tokens=1` 或引擎的 prewarm 接口都行），再用加权路由做慢启动。

## 七、踩坑清单

以下都是这套东西上线时真实撞过的：

**1. 网关的 hash 和引擎的 hash 对不上。** 网关只拿到 HTTP 正文，拿不到 token，只能对文本做 hash；引擎内部是 token 级 block hash。两边一旦不一致，路由以为命中、引擎实际重算，看板上「命中率」好看，账单和延迟都没改善。正解是让引擎上报：vLLM 会通过 KV events（ZMQ）广播 block 的创建和淘汰，SGLang 可以直接暴露 radix tree 状态，路由器只维护「前缀 hash → 副本」的近似索引，不自己算 token。

**2. tokenizer 或 chat template 版本不一致，前缀全废。** 同一段文本在两个模板下 token 序列不同，hash 自然不同。灰度发布时新旧版本的副本混跑，跨版本的路由命中率恒为 0——这类问题在监控上表现为「某个副本的命中率突然只有别人的一半」，而不是报错。

**3. block 对齐差一个 token。** 前缀长度 6137，命中只有 6136，最后一个块整体作废。这会让人误以为缓存有 bug，其实是设计如此：块哈希要带父哈希才能保证「同 hash 即同前缀」，所以只能整块命中。修法是把不稳定内容（时间戳、请求 ID）放到前缀的最尾部，让它落在最后一个块里——反正那个块本来就不会被复用。

**4. 时间戳把缓存打穿。** 上一篇文章算过这条账：把「今天日期」拼进 system prompt 第一行，命中率会从 85% 掉到 1% 以内。路由做得再好，也救不了前缀本身不稳定。这里补一句路由侧的观察手段：命中率要按前缀段统计，把 system、工具定义、历史三段分开看，否则一段的暴跌会被另一段的稳定掩盖。

**5. 亲和 + 副本故障的放大效应。** 粘性路由下，一个副本挂掉意味着它上面所有会话同时迁移，每个都要付一次冷 prefill，可能把剩下的副本压垮。要给会话迁移加预算：迁移速率限流，或者故障瞬间用「只允许溢出、不做亲和」的降级模式先保住可用性。

**6. 大前缀吃满 chunked prefill 预算。** 请求进来时如果命中率低、前缀又长，单个请求就可能吃掉整个 `max_num_batched_tokens`，后面的请求要等好几轮 chunk。这也是「未命中 = 容量下降」在调度层的另一种表现形式：不只是时间变长，是会挤掉别人。

## 八、结论

把结论压成五条：

1. **命中不是免费**，它省的是 O(L²) 的 GEMM，剩下的 O(T·L) KV 读还在。收益倍数 = 2P·BW/(T·kv_bytes·FLOPS)，agent 流量（T/L 小）能到 6 到 30 倍，长文档塞入接近 1 倍。
2. **命中率要分三段看**。system prompt 那段跟路由无关，会话历史那段才归路由管；只看总命中率会被糊弄。
3. **路由目标函数用「省下的毫秒 − 排队毫秒」**，别用命中块数。贪心亲和的实测后果是负载比 4.0、p50 4500 秒。
4. **同 SLO 下亲和大约省 1.7 倍副本**，量级是「值得做」而不是「十倍提速」。
5. **容量下限是并发会话数 × 平均前缀长度**，低于这条线命中率是断崖式归零（自旋 thrash），规划要从并发倒推，而不是从剩余显存倒推。

最后一句实话：如果你的服务只有 2 个副本、流量也不饱和，前缀亲和带来的复杂度大概率不值——一致性哈希加上「前缀尾巴别放时间戳」这两条，就能拿到八成的收益。
