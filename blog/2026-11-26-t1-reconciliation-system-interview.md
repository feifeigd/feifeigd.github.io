## 一、先把规模钉死，否则后面全是空谈

面试时最该做的第一件事是把数字写在白板上。1000 万单/天，单笔对账记录 7 个字段，一行 58.8 字节：

| 指标 | 实测 | 说明 |
| --- | --- | --- |
| 单行大小 | 58.8 B | order_id / amount / status / date / seq / channel / trace 七个字段 |
| 文件大小 | 0.55 GiB | 1000 万行 |
| 解析吞吐 | 128.6 万行/秒 | `str.split` 单线程 |
| 解析耗时 | 0.1 分钟 | 1000 万行 |

解析根本不是瓶颈——0.1 分钟的活，谁做都行。**瓶颈全在写库和匹配上**，而这两件事的差距可以直接差三个数量级。

### 落库：单行提交比 T+1 窗口还长

同一个表、同样的数据，只改提交方式：

| 写入方式 | 吞吐 | 1000 万行耗时 |
| --- | --- | --- |
| 单行自动提交 | 160 行/秒 | 62405 秒 = **17.3 小时** |
| 5000 行一批 | 214832 行/秒 | **46.5 秒** |

差 1341 倍。这个数字的含义是：如果你在对账任务里写出「读一行、插一行、自动提交」的循环，任务在第二天早上八点前跑不完，而运维看到的现象是「对账任务又超时了」，不是「代码写错了」。

正确写法是攒批 + 显式事务，批大小 1000 到 5000 之间（再大对锁持有时间和主从延迟都不友好）：

```python
BATCH = 5000
def load(rows):
    for i in range(0, len(rows), BATCH):
        yield rows[i:i + BATCH]

for chunk in load(parsed_rows):
    with db.transaction():
        db.executemany(
            "INSERT INTO recon_detail(file_id, line_no, oid, amount_cents, status)"
            " VALUES(?,?,?,?,?) ON CONFLICT(file_id, line_no) DO NOTHING",
            chunk,
        )
```

### 内存：别想着把一天的账全装进一个 dict

| 结构 | 每行开销 | 1000 万行 |
| --- | --- | --- |
| Python dict（str 键） | 183.7 B | **1.71 GiB** |
| 紧凑编码（int64 订单号 + int32 金额 + 状态） | 25 B | 250 MiB |

183.7 字节里只有 8 到 12 字节是真实数据，其余是哈希表和字符串对象的开销。所以设计上的第一个决定是**流式 + 分片**：订单号取模 64 片，每片一个子任务，每个子任务的内存峰值就是 1000 万除以 64 约为 16 万行，20 MiB 级别，随便跑。

这也解释了为什么「对账」这个场景特别适合按订单号分片：**对账是逐笔的，每一笔的判定不依赖别的笔**，除了「一对多」的拆单支付，那个后面单独说。

## 二、重放：唯一键加一条语句，不要「先查后插」

银行文件会重复投递，这不是异常，是常态：FTP 传输超时后重传、调度器重试、运维手工补跑，任何一个都会让同一个文件进来两三次。所以「重放 N 次等价于 1 次」是这道题的**第一硬约束**。

实测两种实现，4 线程并发重投同一个文件、3 轮、共 72 万次尝试：

| 实现 | 结果行数 | 重复行 | 重复入账订单 | 耗时 | 吞吐 |
| --- | --- | --- | --- | --- | --- |
| 唯一主键 + INSERT OR IGNORE | 60000 | **0** | 0 | 4.67 秒 | 154222 次/秒 |
| 先 SELECT 再 INSERT | 63371 | **3371**（5.6%） | 3082 | 105.06 秒 | 6853 次/秒 |

两个方向都错：一是**慢 22.5 倍**（每条记录一次查询加一次插入，两次往返），二是**会错**——查询和插入之间那个窗口就是经典 check-then-act 竞态，两个线程同时查到「不存在」，然后都插进去。

而且这类错误在生产上极其阴险：不抛异常、不打告警，账上多出 3371 行，第二天的余额就差了钱，运营要花一周去追。

正确做法是把幂等性下沉到存储层，让数据库来做这件事：

```sql
CREATE TABLE recon_detail (
  file_id    VARCHAR(64)  NOT NULL,
  line_no    INT          NOT NULL,
  oid        VARCHAR(32)  NOT NULL,
  amount_cents BIGINT     NOT NULL,
  status     VARCHAR(16)  NOT NULL,
  PRIMARY KEY (file_id, line_no)
) ENGINE=InnoDB;
```

主键选 `(file_id, line_no)` 还是 `(channel, bank_trade_no)`，是个值得被追问的点：

- `(file_id, line_no)` 保证的是**文件级幂等**，同一个文件重投不会有重复行；但如果银行重出了一份内容相同、文件名不同的文件，就失效了。
- `(channel, bank_trade_no)` 保证的是**业务级幂等**，同一笔银行流水无论从哪个文件来都只有一行。真实系统两个都要：前者防重传，后者防换文件重出，用两张表或者在后者上建唯一索引。

同样的问题出现在状态机和冲正上。重复投递不只是「多一行」，还会把已经冲正过的差异再冲一次——那才是真的丢钱。所以冲正单的主键必须是**差异 ID**，而不是流水号：

```python
def reverse(diff_id, amount_cents):
    # 冲正单号 = f(diff_id)，天然幂等；重复调用只会命中已存在的那张
    with db.transaction():
        created = db.execute(
            "INSERT INTO reversal(diff_id, amount_cents, status)"
            " VALUES(?, ?, 'PENDING') ON CONFLICT(diff_id) DO NOTHING",
            diff_id, amount_cents,
        ).rowcount
        if not created:
            return "already_reversed"
        pay_gateway.refund(amount_cents)          # 外部调用放在事务外
        db.execute("UPDATE reversal SET status='DONE' WHERE diff_id=?", diff_id)
```

注意外部调用（调用支付网关退款）必须在事务外，否则一次网关超时就会把数据库事务挂上几十秒，把整个对账任务拖死。反过来，外部调用成功、数据库更新失败时，靠「PENDING 状态加对账轮询」来收敛——这就是为什么状态机必须有中间态，不能只有成功和失败。

## 三、匹配：哈希订单号，不要哈希金额

20 万单对 22.7 万条银行流水的实验，构造了三种真实差异：968 笔短款（银行没有）、1363 笔差 1 分、28000 笔长款（银行有商户没有）。四种匹配设计：

| 设计 | 命中 | 误匹配 | 覆盖率 | 耗时 |
| --- | --- | --- | --- | --- |
| 只按金额建索引 | 203495 | **5564（2.73%）** | — | 0.79 秒 |
| 按 oid 哈希，金额精确比较 | 197669 | 0 | 98.835% | 0.39 秒 |
| 按 oid 哈希，金额 ±1 分容差 | 199032 | 0 | **99.516%** | 0.20 秒 |
| 金额邻桶实现 ±1 分容差 | 199032 | 0 | 99.516% | 8.31 秒 |

三个结论：

**第一，金额索引是错的，而且错得隐蔽。** 203495 相比 197669 看起来「多匹配了 5826 笔」，实际上那 5564 笔全是长款撞上了某个订单的金额——你不仅漏了真正的差异，还制造了一批假匹配，把该报的差错吞掉了。对账里最贵的错误不是「多报」，是「漏报」。

**第二，容差必须有，但要在正确的键上做。** 差 1 分的 1363 笔在精确比较下全部落进「金额不符」，覆盖率掉到 98.835%；同样这 1363 笔在 ±1 分容差下全部匹配，覆盖率回到 99.516%。但容差只在 oid 已对齐的前提下才有意义——用金额做键去容差匹配，等于放弃了「这是同一笔」的证明。

**第三，邻桶实现慢 21.3 倍。** 因为金额是连续值，容差查询要查 `b-1, b, b+1` 三个桶再逐个比绝对值，而 oid 哈希是一次 `dict.get`。所以在无 oid 的场景（比如只有银行卡号加金额的流水），这条路的成本你要提前算进预算——1000 万单按这个比例外推是 6 到 7 分钟，而不是十几秒。

### 一对多：拆单支付的账

真实业务里经常一单拆成多笔支付：100 元的订单，用户用两张 50 元券分两次付。这时不能用「一比一」的匹配，要先按 oid 聚合银行流水再比总额：

```sql
SELECT oid, SUM(amount_cents) AS paid, COUNT(*) AS legs
FROM bank_flow
WHERE trade_date = ?
GROUP BY oid
HAVING SUM(amount_cents) <> (SELECT amount_cents FROM orders WHERE orders.oid = bank_flow.oid)
```

这条 SQL 的复杂度是 O(n)，聚合在数据库里做就够了。面试官如果问「那 300 笔流水对应 1 单怎么办」，答案是不要做子集和搜索（那是 NP 难），而是先按金额分组、再做有限深度的贪心配对，剩下配不上的直接进人工——**对账系统的目标是账平，不是算法优雅**。

## 四、舍入：让账对不上的不是 float 噪声

「金额用 float 会有精度问题」是面试里的标准答案，但只背这一句会答偏。实测 float 累加 100 万次 0.01：

```
float:    10000.000000171856
Decimal:  10000.00
绝对误差: 1.719E-7 元
```

1000 万笔的累加噪声约 1.7e-6 元，也就是百万分之一块钱。**这个量级解释不了任何一笔「差 1 分」的差错**，所以浮点噪声在对账场景里是个假问题（它真正的危害在阈值比较：`if amount == 100.0` 判等，以及分页累计时的单调性）。

真正的元凶是舍入方向。0.6% 费率、100 万样本：

| 规则对 | 差异笔数 | 比例 | 外推 1000 万单 |
| --- | --- | --- | --- |
| HALF_UP vs HALF_EVEN | 1046 | 0.105% | **10460 笔/天** |
| HALF_UP vs 截断 | 499581 | 49.96% | 499.6 万笔/天 |
| HALF_UP vs float 再 round | 746 | 0.075% | 7460 笔/天 |

结论很直白：**银行和你用的舍入规则只要不一致，每天就有上万笔差 1 分**。1 分钱不多，但它会污染整个差错池——1000 笔真实差异被埋在 10460 笔假差异里，运营的排查效率直接掉一个数量级。

所以对账系统里有三条必须写进契约的东西：

1. 金额全程用 **int64 存分**，不用 float、不用 double，也不要在中间层用元做单位传来传去。
2. 费率计算用**定点小数**（`Decimal` 或数据库的 `DECIMAL(18,4)`），并显式指定 `ROUND_HALF_UP`，别依赖语言默认（Python 的 `round` 是银行家舍入，和多数银行的规则相反）。
3. 与银行对齐时，**把舍入规则做成配置**，按通道配置，而不是硬编码。换一个银行就换一次规则，这是常态。

```python
from decimal import Decimal, ROUND_HALF_UP

def fee(amount_cents: int, rate: Decimal) -> int:
    """amount_cents 是分；费率定点；结果四舍五入到分，再转回 int"""
    return int((Decimal(amount_cents) / 100 * rate)
               .quantize(Decimal("0.01"), rounding=ROUND_HALF_UP) * 100)
```

## 五、99.99% 意味着什么：一天 1000 笔，五个人

这是面试官最想听的那句话。「我们有 99.99% 的匹配率」听上去很好，但：

| 匹配率 | 每天差异笔数（1000 万单） |
| --- | --- |
| 99.9% | 10000 |
| 99.99% | **1000** |
| 99.999% | 100 |

1000 笔要人工处理，按一人一天 200 笔算，需要 5 个人；把效率提到 300 笔/天也要 3.33 个人。**这就是为什么支付公司的对账运营团队从来不小**——不是系统做得差,是 99.99% 这个数字在千万级规模上就是这么贵。

再往下一层，1000 笔差异按常见结构分布（比例是我设的假设，用来算人力，不是实测）：

| 差错类型 | 占比 | 笔数/天 | 能否自动处理 |
| --- | --- | --- | --- |
| 长款（银行有商户无） | 31% | 310 | 否，需查订单 |
| 短款（商户有银行无） | 28% | 280 | 否，需查银行 |
| 金额不符 | 19% | 190 | 部分，容差内可自动 |
| 状态不符（银行成功商户失败） | 14% | 140 | 是，自动补单 |
| 跨日切分（次日到账） | 8% | 80 | 是，等次日再对 |

自动可处理的是最后两类，合计 22%，220 笔。也就是说**上一节那些容差、舍入、幂等的功夫，全做完也只解放 22% 的人力**。这不是劝退，而是要在设计阶段就说清楚：对账系统的核心价值在于**让差异可解释、可追、可一键冲正**，而不是把差异做到零。真正把 1000 笔压到 300 笔的，是支付链路本身的问题（超时没重试、状态机丢了回调），不是对账系统。

冲正必须有度量和刹车：

- **额度上限**：单笔超过 100 元的冲正必须人工审批，自动冲正只处理小额和状态类差异。
- **频次熔断**：同一商户一小时超过 50 笔自动冲正就停下来报警——这通常意味着上游出 bug 了，自动冲正会放大损失。
- **全部落审计**：冲正单记录差异 ID、原始金额、操作人（或机器人）、依据的规则版本。出事的时候这是唯一的证据。

## 六、断点续跑：checkpoint 的间隔怎么定

对账任务跑 60 分钟，中途 OOM 或者发版重启，是必然事件。要不要支持断点续跑，答案是必须；间隔怎么定，是个纯算术题。

100 个 chunk、每 chunk 40 秒（共 4000 秒），进程在随机时刻崩溃，重跑浪费的平均 chunk 数：

| checkpoint 间隔 | 平均浪费 | 折算时间 |
| --- | --- | --- |
| 每 1 个 chunk | 0.5 chunk | **20 秒** |
| 每 10 个 chunk | 5.02 chunk | 201 秒 |
| 只在结尾存一次 | 49.93 chunk | **1997 秒** |

数学上很干净：崩溃时刻均匀分布，平均浪费是间隔的一半。所以间隔越细越好，但 checkpoint 本身有成本（一次写库 + 一次状态更新）。工程上的答案是把 checkpoint 和业务事务**合并**——反正你每 5000 行就要提交一次，顺手把 `progress` 更新在同一事务里：

```sql
UPDATE recon_job SET last_done_seq = ?, updated_at = NOW() WHERE job_id = ?
```

这里有两个必须点出来的细节：

**其一，checkpoint 必须和业务数据同一个事务。** 如果先提交数据再更新进度，崩溃会丢进度（重跑，浪费），如果先更新进度再提交数据，崩溃会**跳过数据**（漏账，致命）。前者是慢，后者是错，这就是为什么这条要写进代码规范。

**其二，断点续跑依赖幂等。** 因为崩溃点可能落在「数据已提交、进度未提交」的窗口里，重跑必然重放一个 chunk。如果第二节的幂等没做对，断点续跑就是在制造重复入账。**幂等的真正价值不是防重传，是让你敢用粗粒度的 checkpoint。**

## 七、时间窗、文件到达与并行

最后是调度层面的账，面试官常问「文件没到怎么办」：

- **文件到达检测**：不要用固定时间 sleep，要轮询「文件存在 + 大小稳定 + 校验和匹配」。银行文件写完之前就下载，是最常见的低级事故——你会拿到一个截断的文件，然后对出几千笔「短款」。
- **退避重试**：拉取失败按 1、2、4、8、16 分钟退避，最多重试 6 次（约 1 小时）。超过就告警进人工，不要无限重试——那会让第二天的任务和第一天撞车。
- **跨日切分**：23:59 的支付 00:01 到账，是每天的固定差异（上面表里的 8%）。解法不是等，而是**允许「未匹配」在 T+1 和 T+2 之间滚动**：当天对不上的进 pending 池，第二天再匹配一次，命中就自动核销。
- **并行度**：按订单号取模 64 片并行，单机 16 个 worker，全程 1000 万行落库 46.5 秒、匹配十几秒，真正的耗时在拉文件和等银行，不在计算。所以同一天的对账和 T+1 的日终结算要**分队列**，别让结算把对账的 worker 抢完。

## 收尾：这题真正在考什么

三个层次，答到第三层才算过：

1. **会不会写对账**：拉文件、解析、匹配、差错表、冲正。这是流程图。
2. **知不知道它会在哪里崩**：单行提交 17.3 小时、check-then-act 多出 3371 行、金额索引 2.73% 误匹配、舍入方向一天 10460 笔假差异。这是数字。
3. **能不能把正确性做成不变量**：幂等键下沉到主键、checkpoint 与业务同事务、金额全程整数分、冲正单号等于差异 ID。这是设计。

第 3 层的人写出来的系统，运营只会在出事的时候找他；第 1 层的人写出来的系统，运营每天都在找他。
