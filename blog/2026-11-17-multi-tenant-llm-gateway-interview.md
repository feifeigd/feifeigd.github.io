## 一、先把「一次请求值钱多少」算出来

网关要限流、要计费、要定配额，前提是知道**一次请求消耗了多少稀缺资源**。LLM 推理里稀缺资源不是「请求数」，是 GPU 秒（严格说是显存带宽秒 + 算力秒）。

所以第一步永远是 roofline：把一个阶段的实际吞吐算出来，再乘上单价。

### prefill：算力受限，算术强度约等于 prompt 长度

一个 N 参数的稠密模型，处理 P 个 token 的 prefill，前向 FLOPs 约等于 `2 * N * P`。同时它要读一遍权重，也就是 `N * bytes_per_param` 字节。

算术强度就是两者相除：

```text
intensity_prefill = 2 * N * P / (N * bytes) = 2 * P / bytes
```

FP8 下 bytes = 1，所以 **prefill 的算术强度就是 2P 左右**——prompt 多长，强度就多高，与模型大小无关。这是一条很漂亮的结论。

H100 的 FP8 拐点：1979 TFLOPS（dense，不算稀疏）/ 3.35 TB/s ≈ **590 FLOP/byte**。也就是说 P 大于约 300 token，prefill 就已经站在拐点右边、处于算力受限区。除了一句话问答，几乎所有请求的 prefill 都是算力受限，能跑满。

实测口径：70B 模型在单张 H100 上 prefill 能到 **1.5 万到 2 万 token/s**（vLLM 默认 chunked prefill 关闭时更高，但会阻塞 decode）。

### decode：带宽受限，算术强度约等于 1

decode 每生成一个 token，要把全部权重读一遍，只用一次。算术强度 ≈ `2N / (N * bytes)` = 2/bytes = **FP8 下就是 2**，远在拐点左边。

单请求 decode 的物理上限：

```text
70B FP8 权重 = 70 GB
H100 带宽 = 3.35 TB/s
每 token 最少耗时 = 70 / 3350 s ≈ 20.9 ms
单请求上限 ≈ 48 token/s
```

实现效率 70%~85%，实测 **40 到 45 token/s**，这就是你调用 API 时看到的「打字机速度」。

好消息是 decode 可以 batch：32 个请求一起 decode，权重只读一遍，总吞吐变成 `32 / 20.9ms ≈ 1530 token/s`。但代价在 KV Cache 的读取上——32 个请求各带 32k 上下文，每个 token 要读的 KV 是 `32 * 32000 * 160KB ≈ 164 GB`，是权重的 2.3 倍。**长上下文下 decode 从「权重带宽受限」变成「KV 带宽受限」，batch 的收益被自己吃掉。**

70B / GQA-8 的 per-token KV（FP8）：`2 * 80 层 * 8 KV头 * 128 head_dim * 1 byte = 160 KB`。32k 上下文就是 5.2 GB。8 张 H100 的 640 GB 显存，去掉 70 GB 权重，按 32k 会话算只能容纳约 110 个并发——这是硬天花板，不是调参能解决的。

### 两边一对比，QPS 限流为什么错就清楚了

| 请求形态 | prefill 耗时 | decode 耗时 | GPU 秒 |
|---|---|---|---|
| 200 输入 / 20 输出 | 200/18000 ≈ 0.011 s | 20/45 ≈ 0.44 s | ≈ 0.45 |
| 32k 输入 / 4k 输出 | 32000/14000 ≈ 2.3 s | 4000/45 ≈ 89 s | ≈ 91 |

**两个请求的 QPS 都是 1，GPU 时间差 200 倍。** 按 QPS 给租户配额，等于允许他每次用最贵的那种形态把你打成 100% 利用率、把别人全部挤掉。

所以网关的第一个设计决定是：

> 限流和配额的基本单位必须是 **token（进一步说是「按阶段加权的 token」）**，QPS 只作为辅助的、防雪崩的粗粒度闸门。

## 二、计费单元和容量单元是两把尺子

厂商定价你背得很熟：gpt-4o 输入 2.50 美元每百万 token，输出 10.00，比例 1:4；Claude Sonnet 3 比 15，比例 1:5；DeepSeek V3 0.27 比 1.10，比例 1:4。

但按上一节的账，真实的 GPU 时间比远不止 4 倍。用单卡口径粗算：

```text
输入 token 的边际成本 = 1 / 18000 token/s  = 55.6 微秒 GPU 秒
输出 token 的边际成本 = 1 / 45    token/s  = 22.2 毫秒 GPU 秒   (batch=1)
比例 ≈ 400 倍（未考虑 batching 摊薄）
```

batch 32 把 decode 摊薄 32 倍之后，比例降到约 **12 倍**；长上下文再把 KV 带宽算进去，实际在 **1:14 到 1:40** 之间浮动，取决于 batch 和上下文长度。

那为什么定价是 1:4？

1. 输入价格里含了「不赚钱也要收」的部分，用来支撑免费额度和长上下文溢价；
2. 输出侧的真实瓶颈是**交互体验**（TTFT 和 TPOT），不是纯吞吐，愿意为速度付溢价；
3. 竞争压力下输入价格被打得最狠（价格战主战场），比例被强行拉大的是输入侧，不是输出侧。

结论对网关设计的直接含义：

- **计费单元**（对租户报价）用厂商口径，1 输出 = 4 输入，这是市场锚点，改了租户不认；
- **容量单元**（做准入控制、算 GPU 预算）必须用实测 GPU 秒，1 输出 ≈ 15 到 40 输入。

两套系数分开维护，用一张配置表映射。混用会导致两种事故：用计费单元做准入 → 长 prompt 请求被严重低估、把集群打穿；用容量单元做报价 → 账单和厂商对不上，财务对不了账。

```yaml
# 一个租户档位的真实配置形态
tier: pro
billing:
  input_per_mtok: 2.50        # 报价用，和上游对齐
  output_per_mtok: 10.00
  unit_ratio: 4               # 1 输出 token = 4 计费单元
capacity:
  unit_ratio: 18              # 1 输出 token = 18 容量单元（实测）
  max_context: 32768
  max_output_tokens: 2048     # 硬 cap，防止预扣失控
  max_inflight: 64            # 并发请求数，这才是真正的隔离旋钮
```

注意 `max_output_tokens` 这个字段——它不是一个可选的礼貌性限制，而是第三节要讲的预扣失控的唯一解药。

## 三、流式响应下的用量：你必须在知道答案之前扣钱

这是整道题最脏的一段，也是最容易出彩的一段。

普通 API 计费：请求进来，算出 cost，扣钱，返回。LLM 不行，因为**输出长度在请求进来时是未知的**（除非你让模型先答一遍）。而 TTFT 又是核心体验指标，你不可能等请求跑完再决定要不要接。

于是必然出现三方博弈：

- 你想在入口就把钱扣准 → 做不到，输出长度未知；
- 租户想把额度用满 → 他一定会设 `max_tokens=8192`，哪怕实际只输出 300；
- 你必须让在途请求不被打断 → 因为 LLM 流式输出一旦中断，用户看到的是「半句话」，这不是降级，是数据损坏。

### 先算一遍「预扣失控」的量级

朴素方案：入口按 `prompt + max_tokens` 预扣，结束时按实际 usage 结算差额。

```text
单请求预扣 = 2000 输入 + 4096 * 4 = 18,384 计费单元
500 并发   = 500 * 18,384 ≈ 920 万计费单元被冻结
实际用量   = 2000 + 600(p95 输出) * 4 = 4,400
500 并发   = 220 万
冻结 / 实际 = 4.18 倍
```

一个日额度 1000 万计费单元的租户，实际只用了 220 万，网关却告诉他「额度不足」。这是**真实事故形态**，不是构造出来的极端值：`max_tokens` 的默认值普遍是 4096，而真实输出 p95 往往在 500 到 800 之间。

更糟的是这个冻结是「幂等不可见」的——租户在自己的控制台看到剩余额度只剩 8%，去查用量报表却只用了 22%，然后开始质疑你的计量系统。这类工单的排查成本极高，因为两套数字都对，只是语义不同。

### 三层解法，从粗到细

**第一层：租户档位 cap。** `max_output_tokens` 按档位写死（free 512 / pro 2048 / enterprise 8192），网关把租户传入的 `max_tokens` 截断到档位值。这一步就把预扣上限从 8192 压到了常规区间，成本是一条配置，收益是数量级。

**第二层：按 p95 预扣 + 超限续扣。** 入口不按 `max_tokens` 扣，按「该租户该模型该 prompt 长度分桶的历史 p95 输出长度」扣。流式过程中每累计 64 个输出 token 检查一次，超了就再扣一个 chunk。这样冻结倍数从 4.2 降到 1.3 左右。

```python
# 网关侧：流式过程中的续扣（伪代码，省略错误处理）
async def stream_with_metering(req, lease):
    charged = lease.initial_units        # 入口按 p95 预扣的量
    produced = 0
    async for delta in upstream.stream(req):
        produced += count_tokens(delta)   # 增量估算，见下
        if produced * OUTPUT_UNIT > charged - lease.headroom:
            need = chunk_units(produced)
            ok = await quota.consume(req.tenant, need)   # Redis Lua，原子
            if not ok:
                # 关键决策：不能断流。记账 + 打标，请求继续跑完
                lease.overdraft += need
                metrics.inc("quota_overdraft", tenant=req.tenant)
            charged += need
        yield delta
    # 流结束，用上游返回的 usage 做最终结算（唯一权威数字）
    actual = usage_units(upstream.final_usage)
    await quota.settle(req.tenant, charged, actual)
```

**第三层：chunk 预取，把 Redis 调用量降三个数量级。** 上一步每 64 token 一次 Redis 调用，单请求 600 输出就是 9 次，QPS 1000 时是 9000 QPS 打在同一个租户的 key 上——Redis 单分片扛得住，但集群模式下这个 key 是热点，且每次调用都有 RTT。

改成「网关本地预取一个 chunk 的额度，用完再取」：

```text
chunk = 4096 计费单元
平均单请求用量 = 4,400 → 约 1.07 次 Redis 调用
对比逐次扣减 = 4,400 次
降低约 4000 倍
```

代价是两个：本地预取但没用完的部分是「网关侧虚占」（不影响租户可见余额，但会浪费集群总预算）；网关崩溃时已预取未消费的额度丢失。

后者必须用**租约 + 心跳对账**解决，思路和延迟任务系统里的可见性超时完全同构：

```text
Redis:  HINCRBY quota:{tenant}:leased  chunk     # 预取
        网关每 5 秒上报 heartbeat(instance_id, consumed)
        Redis 记录 lease:{instance}:{tenant} = chunk, expire = 15s
        实例超时未心跳 → 扫出 lease 记录，把未消费差额退回
```

`leased` 和 `consumed` 是两个独立计数器，永远不相等，差额就是「在途」。对账报表里这两个数字加上时间轴，就是一张完整的资金流水。

### 流式下怎么数 token

`usage` 字段在流式响应里通常只在最后一个 chunk 出现（`stream_options: {include_usage: true}`），前面拿不到。你只能估算：

- **按 SSE delta 计数**：OpenAI 和 vLLM 的 delta 绝大多数情况是一个 token 一个 chunk，直接数 chunk 数就是 token 数。但工具调用（tool_calls 的 arguments 分片）、JSON mode、多字节字符边界会破坏这个假设，误差 2%~5%；
- **增量 tokenizer**：维护 tokenizer 状态，对已收到文本重新编码。准，但每个 chunk 都要跑一次 BPE，CPU 开销不可忽视（单核跑 tiktoken 大约 1 到 3 MB/s，够用但会抢 GIL）；
- **混合**：按 chunk 计数做实时准入，流结束时用最终 `usage` 做权威结算。**永远以 usage 为准，估算只用于过程中的续扣决策。**

这个「估算用于控制、权威数字用于结算」的分层，是流式计费系统的通用骨架，和 CDR（话单）系统的思路一样。

## 四、Redis 里的原子扣减：Lua、分片、和「不要断流」

### 竞态

先看错的做法：

```text
GET  quota:{tenant}  → 5000
if 5000 >= 4000: DECRBY 4000
```

两个并发请求同时读到 5000，各扣 4000，余额变成 -3000。这就是超卖。

窗口有多小？GET 到 DECRBY 之间大约 0.2 到 0.5 ms（同机房）。QPS 1000 时，这 0.5 ms 里有 0.5 个请求并发——也就是**平均每秒发生 0.25 次碰撞**，超卖率在 1% 量级。看着不大，但在「租户额度是钱」的场景里，1% 的超卖就是 1% 的直接损失，且完全静默。

正确做法是 Lua，因为 Redis 单线程执行脚本，check 和 decr 之间不可能插入别的命令：

```lua
-- KEYS[1] = quota key,  ARGV[1] = units,  ARGV[2] = ttl
local remain = tonumber(redis.call('GET', KEYS[1]))
if remain == nil then
  return -2                       -- 无配额记录，交给上层初始化
end
local units = tonumber(ARGV[1])
if remain < units then
  return remain - units           -- 负数 = 不足，返回缺口
end
redis.call('DECRBY', KEYS[1], units)
redis.call('EXPIRE', KEYS[1], tonumber(ARGV[2]))
return remain - units             -- 剩余额度
```

返回值设计成「负数即不足」而不是 `0/1`，是为了让网关能立刻知道缺口多少，决定是排队、降级到小模型，还是直接 402。

### 集群模式的坑

Redis Cluster 里跨 slot 的多 key 操作不原子。租户配额往往要同时校验三个维度：租户总额、模型级限额、全局集群预算。三个 key 大概率不在同一个 slot。

三种处理：

1. **hash tag 强制同 slot**：key 写成 `quota:{tenant_id}:total` 和 `quota:{tenant_id}:model:{m}`，花括号内相同 → 同 slot。代价是单租户的所有 key 挤在一个分片，大租户变成单点热点；
2. **分层扣减**：本地 chunk 承担绝大多数调用，Redis 只做粗粒度；三个维度分开扣，失败时反向补偿（非严格，但业务可接受，因为差额会被租金预取吸收）；
3. **放弃跨维度原子**：租户总额是强一致（Lua），模型级和全局预算是近似值（定期同步），超了只告警不拦。

线上绝大多数系统选 2 或 3。**「所有维度都强一致」是个假需求**——你真正需要的是「钱不能超卖」，而不是「每个维度的报表在同一毫秒对齐」。

### 为什么不许在流中间断

这是设计哲学问题，值得单独说。

如果续扣失败就掐断流，用户拿到的是半句话、半个 JSON、半个函数调用参数。对调用方来说这不是「额度不足」，是**响应损坏**——他没法区分这是你的限额还是网络故障，通常的做法是重试，于是你又扣一次预扣、又断一次，形成雪崩。

正确的三段式：

```text
入口：严格执行准入（余额不足 → 402，请求根本不发出去）
流中：只记账不断流（超额打标，允许透支到 -X 软限额）
之后：封禁下一个请求（租户进入 over_quota 状态，后续请求直接 402）
```

透支窗口的上限由 `max_inflight × p95 单请求用量` 决定，是可以算出来的（64 × 4400 ≈ 28 万计费单元），把它写进风控阈值就行。**「允许有限透支」不是妥协，是唯一不损坏数据的方案。**

## 五、失败转移：什么时候能切供应商，什么时候不能

多供应商（OpenAI + Anthropic + 自建 vLLM）是网关的核心价值之一，但切换策略直接决定成本。

### 错误分级矩阵

| 错误 | 是否已产生上游成本 | 能否切换 | 理由 |
|---|---|---|---|
| DNS 失败 / 连接被拒 | 否 | 可以 | 请求根本没出去 |
| 429 / 配额耗尽 | 否 | 可以 | 上游明确拒绝，未计费 |
| 400 参数错误 | 否 | 不可以 | 切了也一样错 |
| 5xx 在首 token 之前 | 可能 | 谨慎 | 上游可能已开始算，但没输出 |
| 读超时（首 token 之后） | **是** | **不可以** | 上游已计费，且客户端已消费部分输出 |
| 非流式请求超时 | **很可能** | **不可以** | 超时 ≠ 没执行，服务端可能已算完 |

后两行是钱袋子。**一旦收到第一个 token，切换就同时破坏了正确性（输出拼接不连续）和经济性（两边都计费）。**

非流式超时更隐蔽：你 read timeout 设了 60 秒，上游实际算了 90 秒才返回，这时候你早就切到 B 并成功了。上游账单上有两笔，你只向租户收一笔。

### 这笔账有多大

假设切换率 2%（首 token 前失败的比例，正常水位），毛利 30%：

```text
收入 R = 1.43 C（C 为成本）
切换后成本 = 1.02 C
新毛利 = (1.43 - 1.02) / 1.43 = 28.7%
```

掉 1.3 个百分点。看起来不大，但如果你的毛利是靠 prompt cache 抠出来的 15%（很多套壳厂商就是这个水位），2% 的重复计费直接吃掉近十分之一的利润。所以「能不能重试」这个判断必须由网关的**错误分类器**做，不能交给客户端的通用重试库。

### 落地清单

1. 每笔请求记录 `attempts[]`，每个 attempt 带上游、时间、是否计费、错误码。成本核算用 attempts 汇总，收入只算最终成功的那条链，中间的差额记入「失败成本」科目——这是唯一能看见重复计费的地方；
2. 重试预算：最多 2 个供应商、总预算不超过客户端超时的 60%，避免「重试把总延迟撑爆」；
3. 幂等：`Idempotency-Key` 透传给支持的上游，不支持的就靠「首 token 前」这个硬边界；
4. 熔断：单供应商错误率超过阈值时，摘除 30 秒（半开探测），别让每次请求都去摸一个已经挂掉的上游。

## 六、prompt 缓存：唯一能改毛利的杠杆

这一节是这道题的分水岭。前面都是「不出错」，这里才是「赚钱」。

### 定价差

| 供应商 | 缓存写 | 缓存读 | 相对正常输入 |
|---|---|---|---|
| Anthropic | 1.25x | 0.1x | 读便宜 10 倍 |
| OpenAI | 无额外费用 | 0.5x（部分模型 0.25x） | 读便宜 2 到 4 倍 |
| 自建 vLLM | 显存换时间 | 0（prefix cache 命中省 prefill） | 省 prefill 的 GPU 秒 |

### 算一个真实场景

客服系统：system prompt + few-shot 共 3000 token，用户输入 100 token，输出 300 token。Claude Sonnet 口径（输入 3 美元、输出 15 美元每百万）。

```text
无缓存:
  输入 (3000 + 100) * 3 / 1e6  = 0.0093
  输出  300 * 15 / 1e6         = 0.0045
  合计                          = 0.0138

缓存命中(3000 全中):
  缓存读 3000 * 0.3 / 1e6      = 0.0009
  普通输入 100 * 3 / 1e6       = 0.0003
  输出（同）                    = 0.0045
  合计                          = 0.0057
```

单请求成本降 **59%**。按 1.43 倍的售价系数，毛利从 30% 变成 51%——这不是优化，这是换了个生意。

命中率对毛利的敏感度可以近似线性化：命中率每 10 个百分点，成本降约 2.7 个百分点（在 3000/3100 这个结构下）。所以网关必须把命中率当成**一等指标**上报，而不是埋在日志里。

### 缓存为什么不命中：三个经典坑

**坑一：前缀不稳定。** 前缀缓存是**前缀匹配**，从第一个 token 开始逐字比对。你在 system prompt 开头拼上 `当前时间：2026-11-17 14:02:33` 或者 `用户名：张三`，第一个 token 就不同了，整个 3000 token 全部失效。

正确做法：稳定内容（角色设定、规则、few-shot 示例）放最前面，易变内容（时间、用户信息、检索到的文档）放最后。这个顺序在 Anthropic 的 cache_control 里是硬约束，在 OpenAI 的自动缓存里是软优化（它按前缀找最长公共片段，但命中长度会从 3000 掉到 0）。

**坑二：多实例路由打散。** 自建 vLLM 的 prefix cache 是**实例本地**的 LRU，不是全局共享的。你有 8 个实例，请求随机负载均衡，同一个租户的相同 system prompt 落在 8 个实例上，每个实例都要重新 prefill 一次，命中率上限就只有 1/8 的有效性。

解法是**按前缀 hash 的粘性路由**：

```python
def pick_instance(prefix_hash, instances):
    # 一致性哈希 + 最小负载加权，避免热点实例被打爆
    candidates = rendezvous(prefix_hash, instances, replicas=150)
    healthy = [i for i in candidates if i.load < i.capacity * 0.85]
    return healthy[0] if healthy else candidates[0]
```

一致性哈希保证同一前缀稳定落到同一实例，最小负载兜住「前缀 A 特别热」的情况。这里有个张力：粘性越强，负载越不均；粘性越弱，缓存越不命中。生产上通常用「加权 rendezvous + 溢出到次选」来折中——溢出会损失缓存，但比排队超时便宜。

**坑三：多租户串味。** 前缀缓存是按内容寻址的，理论上 A 租户的 prompt 和 B 租户相同就能共享缓存。**这在合规上是事故**：如果你的缓存实现里能观测到「命中率异常高」的租户对，你实际上在泄露「这两个租户用了同一段 prompt」这个信息。所以缓存 key 必须加租户命名空间，放弃跨租户共享的那点收益。

### 缓存也影响计费

命中缓存的部分，成本降到 0.1 倍。如果你按「正常输入价」向租户收费，毛利率会随命中率上升而暴涨——这看起来很美好，直到有个大租户发现自己的账单里输入 token 数没变但你的成本降了一半，开始要求折扣。所以成熟的网关会把缓存折扣**部分让渡**给租户（比如按 0.3 倍计费），既保住毛利又保住客户。

这是一个典型的「成本结构透明化」问题：你的毛利来源必须能解释给客户听，否则议价时你没有立足点。

## 七、多租户隔离：真正的旋钮是 in-flight，不是 QPS

### 噪音邻居怎么产生的

7B 以上的模型，decode 阶段显存里最大的东西是 KV Cache。一个租户用 32k 上下文并发 100 路，KV 就吃掉 128 GB（`100 * 32768 * 160KB`），把整个卡塞满。vLLM 的调度策略是 FCFS + 抢占（preemption），被抢占的请求要重新 prefill 或者从头算——小租户看到的现象是 TTFT 从 300 ms 变成 30 秒，然后超时。

这就是噪音邻居。它的特征是你**在 QPS 维度完全看不出来**——大租户可能只有 2 QPS，但每路都是长上下文。

### 隔离的三个层次

| 层次 | 手段 | 隔离强度 | 成本 |
|---|---|---|---|
| 准入 | per-tenant in-flight 上限 | 中 | 0 |
| 调度 | WFQ / 加权赤字轮转 | 中高 | 需要改调度器或网关排队层 |
| 物理 | 专用实例池 / 专用 GPU | 高 | 利用率下降 20%~40% |

`max_inflight` 的计算必须基于 KV 预算，而不是拍脑袋：

```text
单会话 KV = 上下文长度 * per_token_kv
70B FP8, 8k 上下文: 8192 * 160KB = 1.31 GB
单机可用 KV = 640GB - 70GB(权重) - 30GB(激活/碎片) = 540 GB
单机容量 ≈ 410 路（8k 上下文）
租户占 10% 份额 → max_inflight = 41
```

注意这个数字随上下文长度线性变化。所以更准的做法是**按 token 预算而非请求数**做闸门：租户的 `kv_budget_tokens` = 100 万 token，一个 32k 请求扣 32k，一个 1k 请求扣 1k，用完排队。这样租户既能开很多短请求，也能开少量长请求，总量受控。

### 公平排队

准入只保证不超额，不保证公平。租户 A 的 50 路长请求在跑，租户 B 的 1 路短请求进来，如果队列是 FIFO，B 要等 A 全部跑完（几十秒）。

加权公平队列的做法：按租户权重维护虚拟时间戳，每次从「虚拟完成时间最小」的租户取请求。权重来自付费档位（free 1 / pro 4 / enterprise 16）。实现上用赤字轮转（deficit round robin）就够，不需要严格 WFQ 的数学性质。

这里有个容易被忽略的点：**排队要有明确的超时语义**。LLM 请求排队 30 秒再开始跑，对用户来说比直接拒绝更糟（他以为在生成，其实在排队）。所以响应头必须回 `X-Queue-Position` 和 `X-Estimated-Start`，让客户端能决定「继续等」还是「降级到小模型」。

## 八、可观测性：网关计数和上游 usage 必须对齐

网关自己数 token、上游也返回 usage，两者必然有差异。差异来源：tokenizer 版本不同（同一个模型换 tokenizer 分词结果会变）、流式估算误差、缓存命中的 token 归属、工具调用参数的计费规则。

健康水位：差异小于 0.5%。超过就告警，因为这意味着你在**按错误的数字收钱**。

必须上报的指标（按租户 × 模型 × 供应商）：

```text
ttft_p50 / ttft_p95 / ttft_p99      首 token 延迟，体验核心
tpot_p50                            每输出 token 时间，decode 效率
tokens_in / tokens_out / tokens_cached
unit_ratio_observed                 实测 GPU 秒比，用来校准容量系数
switch_rate                         失败转移率
overdraft_units                     透支量
cache_hit_rate                      prompt 缓存命中率
cost_actual / cost_billed           成本 vs 收入，按租户归因
```

最后两个指标是财务和工程的交点。`cost_actual` 里要包含失败重试的浪费，`cost_billed` 只算成功的请求。两者之差除以 `cost_billed` 就是「工程损耗率」，一个健康的网关应该在 3% 以内。

## 九、完整链路走一遍

一个请求进来之后，按顺序经过：

```text
1. 鉴权：虚拟 key → 租户/项目/档位（key 明文永不落库，只存 hash 前缀）
2. 参数规范化：截断 max_tokens 到档位 cap、补默认值、拒绝超上下文
3. tokenize：算准确输入长度（这里必须用与目标模型一致的 tokenizer）
4. 准入：
   a. 租户状态（over_quota 直接 402）
   b. in-flight / kv_budget_tokens 闸门
   c. 配额预扣（本地 chunk 优先，耗尽则 Redis Lua）
5. 路由：模型 → 供应商优先级 → 前缀粘性 → 健康实例
6. 转发：带上 Idempotency-Key、透传 stream、记录 attempt
7. 流式计量：chunk 计数 + 阈值续扣（不断流）
8. 结算：上游 usage 为准，退回差额，写 CDR
9. 失败路径：按错误矩阵决定是否切换，attempts 全量记录
10. 异步：用量聚合、毛利归因、缓存命中率、租户账单快照
```

第 3 步值得强调：tokenize 必须用**目标模型对应的 tokenizer**。同一个字符串在 Llama 和 Qwen 的 tokenizer 下长度能差 30%。如果你用 tiktoken 估算然后路由到 Anthropic，输入长度报错和计费偏差都会出现。网关要维护一张「模型 → tokenizer」映射表，并且 tokenizer 版本变更要打版本号——否则历史上报数据不可比。

## 十、常见追问

**追问一：租户要求「预算不能超」，你怎么保证？**

分三层回答：入口严格准入（不超卖）、流中有限透支（`max_inflight × p95` 为上限）、事后封禁下一请求。**不能承诺「精确不超」**，因为流式输出的最终长度不可预知；能承诺的是「超支量有上界且可计算」。如果面试官坚持要精确，唯一办法是要求调用方提供输出长度上限并在入口按上限预扣——这就是为什么很多企业版 API 强制 `max_tokens` 必填。

**追问二：为什么要区分计费单元和容量单元？一套不行吗？**

不行，因为两者服务的目标函数相反。计费单元要向市场锚点对齐（否则客户拿你的账单和厂商账单对比会质疑），容量单元要向物理真相对齐（否则你的准入控制会失效）。用计费单元做准入 → 长 prompt 请求被低估数十倍，集群被打穿；用容量单元做报价 → 账单不可解释。两套系数、一张映射表、定期用 `unit_ratio_observed` 校准，是唯一可行的结构。

**追问三：自建和调 API 的成本交叉点在哪？**

用 GPU 秒算。8 张 H100 的节点按 2 美元每卡时算是 16 美元每小时。70B FP8 在其上跑，混合负载下总吞吐大约 2000 到 3000 输出 token/s（batch 32、8k 上下文的保守值）。换算：`16 / 2500 * 1e6 / 3600 ≈ 1.8 美元每百万输出 token`。对比厂商输出价 10 美元，毛利空间很大——但这是**满载**口径。如果你的利用率只有 20%，成本变成 9 美元，和厂商打平。所以「自建更便宜」这句话的前提是「你能把卡喂满」，而喂满的前提正是这个网关（多租户、配额、缓存、路由）。这是一条闭环论证，面试时说出来会加分。

**追问四：推理模型（reasoning）的隐藏 token 怎么计费？**

reasoning token 由模型内部生成、不返回给用户，但上游照样计费（OpenAI 的 `reasoning_tokens` 在 usage 里可见但不在 content 里）。网关的处理是：在 usage 里单独拆一列，按输出价计费，并在租户侧明确告知「思考 token 计入账单」。不做这一步的后果是租户发现账单比自己数的字数多好几倍，然后投诉计量不准。这也是为什么 `usage` 必须以数据结构完整透传，而不是只取 `total_tokens`。

**追问五：怎么防止租户用网关做模型蒸馏？**

这是安全侧的题，但网关是唯一能拦住的地方。手段：按租户做语义相似度聚类（大量高度相似的 prompt = 在造数据集）、对输出做水印或指纹、限制单租户的单日 token 上限、对高频低熵输出告警。强度取决于商业判断，技术上都能做，但误伤率高——正常的大客户也会跑批处理。所以通常是「额度 + 人工审核」而不是自动阻断。

## 十一、收尾

这道题的三条主线：

- **计量线**：QPS 是错的单位，token 才是，而且要拆成计费单元和容量单元两把尺子。所有定价和准入的争论，最后都回到「一次请求多少 GPU 秒」这个除法上。
- **流动性线**：流式输出让「先收钱后服务」不可能，只能「入口预扣 + 流中记账 + 事后结算」。而「流中断」是禁手——宁可透支也不能损坏响应。
- **经济线**：毛利率不在转发代码里，在 prompt 缓存的命中率和失败重试的浪费率里。这两个指标一个靠路由粘性，一个靠错误分类，都是架构决策而不是运维调优。

如果面试官继续往下压，还有几个方向：多模态的计费（图像按 tile、音频按时长，和 token 不是一个维度）、批处理 API 的折扣模型（异步 + 24 小时窗口，本质上是在卖「不保证延迟」的容量）、阶梯定价（上下文超过 200k 后单价上浮，因为 KV 带宽成本非线性）、以及网关自身的高可用（它是个无状态代理还是有状态配额中心，决定了你能不能做多活）。这些留到后面的题。
