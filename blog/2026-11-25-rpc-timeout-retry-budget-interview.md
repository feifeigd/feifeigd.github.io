>
> 这道题在被问出来的时候往往只是一句话：「你们服务的超时设多少？」答「1 秒」的人很多，但接着问「为什么是 1 秒」「下游变慢的时候你这个 1 秒会怎样」「重试几次」「连接池多大」，就没人能一路答下去了。
>
> 因为超时不是一个配置项，它是**你和下游之间关于「谁先放弃」的合同**。合同签错有两个方向：签得太紧，你砍掉了本来会成功的请求，用户看到错误，重试又把下游压垮；签得太松，失败的请求占着线程和连接，队列堆起来，p99 自己涨上去。
>
> 数字来源：① 纯 Python 离散事件仿真，8 个 worker、指数服务时间 10ms、FCFS、单次超时 300ms、40 秒窗口、3 个随机种子取均值；② 解析模型（随机和的尾分布、全抖动的时刻分布）。延迟分布统一用 lognormal（中位 40ms、sigma 0.6），因为真实 RPC 的延迟是右偏的，正态分布会把尾部算得太乐观——这是第一个要先纠正的直觉。**没有生产环境实测**，绝对数值依赖参数，但结论的形状不依赖。

## 一、先看清你给什么东西设了超时

### 1.1 延迟不是一个数，是一条尾巴

```
lognormal(中位 40ms, sigma 0.6)，30 万次采样：
  p50 = 40 ms
  p90 = 86 ms
  p99 = 161 ms
  p99.9 = 258 ms
  均值 = 48 ms
```

四件事值得盯住：

1. **p99 是 p50 的 4.0 倍**，p99.9 是 p50 的 6.4 倍。任何「p50 乘 3 就是 p99」的经验说法，在右偏分布上都只是碰巧。
2. **均值 48ms 大于中位 40ms**。尾部在拉高均值，所以用平均延迟做容量规划会低估排队。
3. **p99 和 p99.9 之间差了 97ms**。超时设在 161ms 附近时，跨越这几个毫秒就会让 0.9% 的请求从成功变成失败——这是「超时值附近最敏感」的量化解释。
4. 尾部不是异常，是常态。1% 就是每 100 次请求里有 1 次，QPS 1000 的服务每分钟 600 次。

### 1.2 超时是尾部上的一个截断点，代价两边不对称

设 T 为超时：

- **T 偏小**：被砍掉的请求里，有一部分本来会成功。你付出的是「确定的错误率」，而且这些请求会走重试，把负载推高。
- **T 偏大**：失败请求占着 worker 和连接不放，排队变长，后面的请求开始超时。你付出的是「不确定的长尾」。

这两边不对称的地方在于：**偏小的损失是可计算的、立即的；偏大的损失是延迟出现的、非线性的**——因为排队在接近饱和时会突然爆炸（第四节会给出 7% 流量换 5.6 倍池等待的数字）。

所以工程上的默认做法不是「取一个好看的数字」，而是：

```
单次尝试的超时 ≈ min(该跳的 p99.9, 剩余预算) 
端到端 deadline ≈ 用户可接受的 p99 × (1 + 重试放大预算)
```

### 1.3 扇出会把尾延迟放大，聚合接口必须单独算

一个聚合接口并行调 10 个下游、等最慢的那个返回，它的延迟分布是 10 个样本的最大值。仿真实测：

| 扇出路数 k | p99 延迟 | p99.9 延迟 | p99 相对中位的倍数 |
|---|---|---|---|
| 1 | 161 ms | 258 ms | 4.0x |
| 2 | 187 ms | 289 ms | 4.7x |
| 5 | 227 ms | 330 ms | 5.7x |
| 10 | 258 ms | 368 ms | 6.4x |
| 20 | 289 ms | 404 ms | 7.2x |
| 50 | 330 ms | 472 ms | 8.3x |

数学上就是 `P(max 超过 t) = 1 − F(t)^k`，所以 **k 路的 p99 等于单路的 `F^-1(0.99^(1/k))`**——k=10 时单路的 99.9 分位点成了新的 99 分位点。

由此得到两条直接可用的结论：

- **聚合接口的超时不能沿用单跳的超时**。如果每个下游 200ms 超时，聚合层再用 200ms，正常情况下就有 10% 的概率至少一路被砍（10 × 1%）。
- 反过来，**扇出让你更早看到尾部**：k=50 时 p99.9 是 472ms，单路才 258ms。这就是为什么大扇出的查询总是「偶发慢」，而且复现不了。

## 二、超时设好之后，第一件事是把它传下去

### 2.1 铁律：上游超时必须大于下游超时

这条「铁律」很多人会背，但说不出算术。反过来的情形（上游 800ms 先放弃，下游按 1.2s 继续算）在真实系统里的成本是两块：

1. **白干**：下游继续消耗 CPU、数据库连接、下游的下游。
2. **放大**：上游超时后重试，下游同时在做两件同样的事。

我用仿真量了这块成本。场景：8 个 worker、服务 10ms、容量 800 req/s、负载正好等于容量（1.0 倍，也就是「上游流量刚好打满下游」这个最常见的位置），客户端单次超时 300ms：

| 配置 | 成功率 | 尝试/请求 | 白干服务时间占比 | p99 |
|---|---|---|---|---|
| A 不重试，服务端照做已放弃的活 | 66.3% | 1.00 | 33.5% | 296 ms |
| F 不重试，服务端开工前查 deadline | **96.0%** | 1.00 | **3.6%** | 297 ms |
| B 3 次重试，服务端照做 | 46.1% | 2.08 | 76.6% | 267 ms |
| C 3 次重试，过期丢弃，无退避 | 50.3% | 2.04 | 50.4% | 905 ms |
| D C + 50ms 全抖动退避 | 50.6% | 2.03 | 50.2% | 994 ms |
| E D + 10% 重试预算 | 83.5% | 1.08 | 16.4% | 517 ms |

A 和 F 之间只差一行代码：**服务端在开工前检查一下这个请求的 deadline 是不是已经过了，过了就直接丢掉**。同一台机器、同一个超时，成功率从 66.3% 变成 96.0%，白干从三分之一降到 3.6%。

为什么会差 30 个百分点？因为队列里的请求一旦过期，服务它就是在给一个已经挂断的电话说话。而这段白干的时间，本来可以服务一个还在等的请求。**过载时最贵的不是算得慢，是算没人要的**。

这就是 deadline 传播的价值：它不是「礼貌」，是把「谁先放弃」这个信息同步给整条链路，让每一层都能在开工前做这个判断。

### 2.2 deadline 是绝对时间，超时是相对时间

代码里最容易写错的地方，是把「超时」当成「deadline」传：

```go
// 错：把相对值当绝对值传，下游会重新开始计时
ctx = context.WithTimeout(ctx, 500*time.Millisecond)

// 对：从上游 deadline 反推这一跳还能用多少
func callDownstream(ctx context.Context) error {
    dl, ok := ctx.Deadline()
    if !ok {
        return errors.New("no deadline upstream")
    }
    remain := time.Until(dl) - 15*time.Millisecond // 网络 + 序列化余量
    if remain <= 0 {
        return errBudgetExhausted // 预算不够就别发，直接快速失败
    }
    hop := min(remain, perHopTimeout) // 单跳上限与剩余预算取小
    sub, cancel := context.WithTimeout(ctx, hop)
    defer cancel()
    return doRPC(sub)
}
```

三个细节：

- **每次重试前重算剩余预算**，而不是 `attempt × 固定超时`。总预算 800ms、单次 500ms，最多只能重试一次，第二次的可用预算只剩 300ms 减余量。
- **余量要显式留**。15ms 是经验值（同机房），跨机房按 RTT 的 2~3 倍留。
- **预算不够时直接失败，不要发出去等超时**。发出去再超时，你付出了连接、序列化、下游排队三段成本，换回一个必然会失败的尝试。

### 2.3 取消要真的能停下

deadline 传下去不等于工作会停。分三层看：

- **协议层**：gRPC 的 deadline 是协议的一部分（`grpc-timeout` header），服务端框架能看到；HTTP/1.1 没有取消语义，客户端断开只是关连接，服务端可能继续算到结束。
- **应用层**：服务端要在三个点检查——入队时、开工前、循环/分批处理中间。只查第一个点，长任务照样跑完。
- **存储层**：数据库的 `statement_timeout`、Redis 的查询超时也要跟着设。否则服务端停了，数据库还在替你扫一张大表。

F 那行的 3.6% 白干，就是这三层都做了的理想值；真实系统里因为 HTTP/1.1 和框架限制，通常落在 A 和 F 之间——**所以「我们没做 deadline 传播」不是一个中性的选择，它直接对应 30 个百分点的成功率**。

## 三、重试：只在一种条件下是收益

### 3.1 先算放大系数

三层服务，每层重试 3 次，最坏情况下最底层收到 `3 × 3 × 3 = 27` 倍的请求。两层就是 9 倍。这个数字不需要仿真，乘一下就知道——所以「内层重试 + 外层重试」是必须杜绝的组合，重试只能有一层，通常在最外层（或者干脆在统一的服务网格层）。

期望尝试次数（独立失败概率 p、最多 k 次）：

```
E[尝试] = 1 + p + p² + ... + p^(k-1) = (1 - p^k) / (1 - p)
p = 3%, k = 3 → 1.0303（成本只多 3%）
```

### 3.2 过载时重试是正反馈

3.1 的公式有个隐含假设：**失败是独立的**。真实过载场景里失败不是独立的，它和负载强相关——超时、队列满、限流，这些都是「因为你来了所以失败了」的类型。此时再套公式就错了，得仿真。回到第二节那张表，按负载排开：

| 负载 | A 不重试照做 | F 不重试查 deadline | B 3 次重试照做 | C 重试+丢弃 | D +抖动 | E +10% 预算 |
|---|---|---|---|---|---|---|
| 0.85 | 100.0% | 100.0% | 100.0% | 100.0% | 100.0% | 100.0% |
| 1.00 | 66.3% | 96.0% | 46.1% | 50.3% | 50.6% | 83.5% |
| 1.10 | 6.7% | 53.7% | 6.6% | 11.8% | 11.9% | 45.8% |
| 1.20 | 3.8% | 33.8% | 3.8% | 7.9% | 7.9% | 31.0% |
| 1.30 | 2.2% | 24.3% | 2.2% | 5.8% | 5.9% | 23.6% |

读法有三层：

1. **负载 0.85 时所有配置完全一样**。四个数字一模一样不是仿真出错，是重试根本没触发——尾延迟 56.5ms，离 300ms 超时很远。**正常负载下重试是白买的保险，出事的时候才收费。**
2. **负载 1.0 时重试让成功率从 66.3% 掉到 46.1%**。这不是反直觉，是结构性的：重试把尝试次数推到 2.08 倍，服务量也跟着翻倍，队列更长，超时更多，再触发更多重试。C 和 D 好一点（50%），因为它们不服务已过期的请求；但 p99 从 296ms 涨到 905ms 和 994ms——**超时 300ms 的系统，p99 到了 1 秒**，因为成功的请求要等前一次重试超时。
3. **重试预算（E）把成功率拉回 83.5%**，代价是 p99 517ms。它做的是止损：尝试次数被压在 1.08 倍，不允许重试把系统推进正反馈。

而 F（只查 deadline、完全不重试）在每一行都是最好的。这是这篇文章最想说的一个结论：**过载时，重试是最后才该动用的工具，先动的是「别做没人要的工作」**。

### 3.3 重试真正有用的场景，成本可以算清

独立随机失败（连接被重置、单机重启、DNS 抖动、502）确实是重试的主场。3% 的独立失败率：

| 次数 | 成功率 | 成本 |
|---|---|---|
| 1 | 97.000% | 1.00x |
| 2 | 99.910% | 1.03x |
| 3 | 99.997% | 1.06x |

两个数量级的错误率下降，成本 6%。**这就是为什么所有人都想加重试**——只是没人把它用在这个前提上。判断标准就一条：

> 这次失败，会不会因为「我又发了一次」而变得更可能失败？

会（超时、限流、队列满、连接池耗尽）→ 重试是有害的，应该快速失败 + 降级。
不会（对端进程挂了、包丢了、单机故障）→ 重试是廉价的，最多 2~3 次。

### 3.4 退避必须带抖动，否则重试会自己造出一个尖峰

仿真：400 个请求在同一瞬间失败（一次依赖抖动、一次批量任务的超时、一次配置推送引起的短暂不可用），下游 40 并发、单请求 10ms：

| 策略 | 10ms 窗口内最多的重试数 | 重试队列等待 p99 |
|---|---|---|
| 固定 100ms 退避 | 400 个 | 90.0 ms |
| 100ms 全抖动 | 48 个 | 3.5 ms |

同样的 400 个请求，固定退避让它们在同一个 10ms 里全部到达——下游从「能扛」瞬间变成「扛不住」，本来能恢复的抖动被重试放大成一次雪崩。全抖动把峰值压到 48，队伍等待 p99 从 90ms 降到 3.5ms，**25 倍**。

工业写法（AWS 的 full jitter）：

```
sleep = uniform(0, min(cap, base * 2^attempt))
base = 100ms, cap = 2s
```

不要用 `sleep = base * 2^attempt`（没抖动），也不要用 `base*2^n/2 + uniform(0, base*2^n/2)`（equal jitter，尖峰只削掉一半）。只要所有客户端的时钟和退避公式一致，没有抖动就等于同步。

### 3.5 重试预算：给放大系数封顶

gRPC 的 `retryThrottling`（tokenRatio 默认 0.1：每次成功回 0.1 个 token、每次失败扣 1 个）和 Envoy 的 `retry_budget`（按「活跃重试 / 活跃请求」比例设上限，`budget_percent` 常见配 20%）都是同一个思路：**重试的总量必须和成功的量挂钩，不能和失败的量挂钩**。

表格里 E 行就是这个机制的量化效果（10% 预算）：

| 负载 | 无预算（D） | 10% 预算（E） | 尝试/请求（D → E） |
|---|---|---|---|
| 1.00 | 50.6% | 83.5% | 2.03 → 1.08 |
| 1.10 | 11.9% | 45.8% | 2.82 → 1.05 |
| 1.30 | 5.9% | 23.6% | 2.92 → 1.02 |

注意 E 的尝试次数已经接近 1.0——预算在过载时**几乎禁止了重试**，只在小范围放开。这正是设计意图：宁可让一部分请求快速失败，也不能让重试占满容量。

### 3.6 重试的前置清单

- **幂等**：或者带请求去重键（客户端生成 request id，服务端去重窗口至少覆盖重试时长）。
- **错误分类**：连接拒绝、DNS 失败、5xx 可重试；4xx、业务错误、**超时不重试**。超时是最危险的一类——对端可能已经做完了，你只是没收到回执。
- **只重试一层**：内层重试会被外层再乘一遍。
- **重算 deadline**：重试的 deadline 是 `min(now + 单次超时, 原始 deadline)`，不是重新开一个。
- **带预算和断路器**：没有预算的重试，在故障时就是放大器。

## 四、连接池：超时的另一半死因

### 4.1 Little 定律：并发 = 到达率 × 延迟

连接池是排队系统，排队系统的最小并发需求由 Little 定律给出：

```
平均占用连接数 = λ × E[延迟]
```

20 条连接、下游 lognormal（中位 25ms、sigma 0.75，均值 33.1ms）：

```
理论容量 = 20 / 0.0331 = 604 req/s
```

仿真实测（客户端超时 300ms）：

| λ (req/s) | λ × 均值 | 池等待 p50 | 池等待 p99 | 端到端 p99 | 等池就超时 | 总超时 |
|---|---|---|---|---|---|---|
| 200 | 6.6 | 0.0 ms | 0.0 ms | 139 ms | 0.0% | 0.0% |
| 350 | 11.6 | 0.0 ms | 3.4 ms | 147 ms | 0.0% | 0.0% |
| 450 | 14.9 | 0.0 ms | 13.0 ms | 141 ms | 0.0% | 0.1% |
| 520 | 17.2 | 0.0 ms | 32.1 ms | 147 ms | 0.0% | 0.0% |
| 560 | 18.5 | 2.7 ms | 57.2 ms | 154 ms | 0.0% | 0.0% |
| 600 | 19.9 | 159.9 ms | 318.2 ms | 362 ms | 1.8% | 7.1% |

这张表最刺眼的是最后两行的对比：**从 560 到 600，流量只涨了 7%，池等待 p99 从 57ms 涨到 318ms，5.6 倍**。占用从 18.5 条涨到 19.9 条——看起来还差 0.1 条，实际上已经贴到天花板。

更值得记的是 600 那行的最后两列：**7.1% 的请求超时，其中 1.8% 连一个字节都没发出去**——它们在池队列里等到超时。这时候你把下游扩容、优化 SQL、加索引，全都没用：慢的不是下游，是你自己的排队。

### 4.2 三个数字必须一起算

```
超时 ≥ 池等待 p99 + 服务时间 p99 + 网络余量
```

如果超时 300ms、池等待 p99 已经 318ms，那么这 300ms 的超时对「慢请求」的约束是假的——它约束的其实是排队。表现出来就是：**超时率上去了，但下游监控一切正常**（下游每秒处理的请求数甚至下降了，因为你提前掐断了）。

### 4.3 池该多大

```
C ≈ λ × p99(延迟) × 安全系数(1.5)
```

按均值算是 20 条，按 p99 算是 `600 × 0.147 × 1.5 ≈ 132` 条。这两个数字差 6.6 倍，怎么选？

- 按均值算：省连接，但高峰期必然排队（表里 600 那行）。
- 按 p99 算：连接多，但你得确认下游吃得住——**池不是越大越好，超过下游容量只是把队列从你这搬到下游**，而且往往搬到了一个不会做限流的数据库上。

实践里的折中：池大小按 p99 算，但对下游做限流（保护下游），对本服务做快速失败（保护自己）。池耗尽的正确处理是**立刻失败 + 降级**，不是把 acquire 超时设成无限等。

## 五、预算怎么分：把 2000ms 分给三跳

### 5.1 逐跳 p99 相加，不是端到端的 p99

三跳串行，每跳独立同分布（中位 40ms、sigma 0.6）：

```
单跳 p99      = 161 ms
逐跳 p99 相加 = 484 ms
真实端到端 p50  = 134 ms
真实端到端 p99  = 317 ms   ← 只花掉相加预算的 65%
真实端到端 p99.9 = 428 ms
```

两件事同时成立，听起来矛盾但其实不：

- **相加是保守的**：它假设每一跳都同时处在自己的 p99 上，这种巧合的概率很低，所以真实 p99（317ms）低于相加值（484ms）。
- **但真实 p99 又是单跳 p99 的近 2 倍**：随机和的方差会累积，所以你也不能按单跳的 161ms 设端到端。

所以分配预算的正确姿势不是「相加」，也不是「取最大」，而是**按 SLO 反推 + 每层留余量**：

| 层 | 端到端 SLO | 该层预算 | 依据 |
|---|---|---|---|
| 网关 | 800 ms | 800 ms（入口 deadline） | 用户可接受 p99 |
| 服务 A | 800 ms | 700 ms | 留 100ms 给网关转发与序列化 |
| 服务 B | 700 ms | 400 ms | A 内部还要串行两跳 |
| 服务 C | 400 ms | 300 ms | 留 100ms 给 B 的处理与网络 |
| DB 查询 | 300 ms | 250 ms | statement_timeout 必须跟到这一层 |

### 5.2 预算不够时，先减跳数，再谈优化

端到端 800ms、三跳各 p99 161ms，看起来绰绰有余（相加 484）。但如果某跳 p99 是 500ms，相加立刻破 1000ms。这时候能做的事按性价比排：

1. **并行化**：串行两跳 161 + 161，并行后是 max(161, 161) ≈ 187（第一节的扇出表），省掉一半。
2. **降级**：非关键跳用缓存或默认值，直接把它从关键路径上摘掉。
3. **对冲**：见下一节，花 25% 的流量换 27% 的尾延迟。
4. **合并调用**：两次 RPC 合成一次批量调用，省一次 RTT 和一次排队。

## 六、对冲：花 25% 的钱买 27% 的尾延迟

对冲（hedging）是「超过 p95 还没回，就再发一份，取先返回的」。仿真（第二发在 60ms 后发出）：

| 指标 | 单发 | 对冲（60ms） |
|---|---|---|
| p50 | 40 ms | 40 ms |
| p99 | 161 ms | **117 ms** |
| p99.9 | 258 ms | 232 ms |
| 平均请求数 | 1.00 | 1.25 |

p99 降 27%，成本 25%。这在读多写少、下游有富余容量的场景里非常划算——但四个前提一个都不能少：

- **幂等**：只对读请求做，写请求对冲等于重复提交。
- **触发阈值**：按 p95（86ms）而不是按超时触发，否则对冲到的是已经病危的下游。
- **上限**：每个逻辑请求最多两发，且总对冲并发不超过活跃请求的一定比例（和对冲预算同理）。
- **p99 有下限**：对冲延迟 60ms，意味着 p99 不可能低于 60ms。想再低就要更早发，成本线性上升。

## 七、落地清单

1. **超时从分布算**：取该跳 p99.9，或者 p99 × 1.5；不要用「感觉 1 秒」。
2. **聚合接口单独算**：扇出 k 路的 p99 等于单路的 `F^-1(0.99^(1/k))`。
3. **deadline 往传下**：传绝对时间，每次重试重算剩余预算，留 15ms 余量。
4. **服务端查 deadline**：入队、开工前、循环中三个点；DB 的 statement_timeout 一起设。
5. **重试只在一层**，只对幂等 + 独立失败；超时不重试。
6. **退避必须全抖动**，`uniform(0, min(cap, base*2^n))`。
7. **重试预算 10~20%**，和成功量挂钩，不和失败量挂钩。
8. **连接池按 λ × p99 × 1.5 算**，并且算清楚池耗尽时的行为（快速失败，不是无限等）。
9. **超时 ≥ 池等待 p99 + 服务 p99 + 网络**。
10. **监控三件事**：超时率、池等待 p99、白干服务时间占比（服务完才发现调用方已经走了的比例）。第三个最少人做，也最能说明问题。

## 八、面试怎么答

**30 秒版**：超时从下游 p99.9 推出来，扇出接口要按 max 的分布重算；deadline 一路传下去，服务端开工前检查；重试只做一层、只对幂等和独立失败、带全抖动和 10% 预算；连接池按 Little 定律算，保证超时大于池等待加服务时间。

**3 分钟版**（加分项，按这个顺序）：

1. 先讲分布：p50 40、p99 161、p99.9 258，说明超时是尾部上的截断点。
2. 讲扇出放大：10 路并行 p99 从 161 到 258。
3. 讲白干的账：同样负载下，服务端查不查 deadline，成功率 66% 对 96%。
4. 讲重试的正反馈：过载 1.0 时加重试，成功率 66% 掉到 46%，尝试次数 2.08 倍。
5. 讲连接池：20 条连接在 600 req/s 时池等待 p99 318ms，7.1% 超时里有 1.8% 没发出请求。
6. 收尾讲清单：预算怎么分、什么时候对冲、监控哪三个指标。

能把这六个数字讲清楚，比背十种重试策略有用。

## 九、复现脚本

核心引擎（其余几张表用同一引擎换参数，对冲和扇出是解析计算）：

```python
import heapq, random

def run(lam, servers=8, svc=0.010, dur=40.0, seed=1, attempts=1,
        timeout=0.3, backoff=0.0, jitter=False, deadline_check=False,
        budget=None):
    rnd = random.Random(seed)
    free = [0.0] * servers
    heapq.heapify(free)
    arrivals, t = [], 0.0
    while True:                       # 泊松到达
        t += rnd.expovariate(lam)
        if t > dur:
            break
        arrivals.append(t)
    n = len(arrivals)
    ev = [(ta, 0, i, 0) for i, ta in enumerate(arrivals)]
    heapq.heapify(ev)
    made, first = {}, {}
    ok = failed = retry_cnt = 0
    lat, work, wasted = [], 0.0, 0.0
    tries = 0
    while ev:
        t0, kind, rid, k = heapq.heappop(ev)
        if rid not in first:
            first[rid] = t0
        dl = t0 + timeout
        tries += 1
        made[rid] = k + 1
        ft = heapq.heappop(free)          # 最早空闲的 worker，FCFS
        start = ft if ft > t0 else t0
        if deadline_check and start > dl:  # 开工前查 deadline
            heapq.heappush(free, ft)
            end, done = dl, False
        else:
            s = rnd.expovariate(1.0 / svc)
            end = start + s
            heapq.heappush(free, end)
            work += s
            done = end <= dl
            if not done:
                wasted += end - max(dl, start)   # 白干的服务时间
        if done:
            ok += 1
            lat.append(end - first[rid])
        else:
            can = made[rid] < attempts
            if can and budget is not None and retry_cnt >= budget * ok + 20:
                can = False
            if can:
                retry_cnt += 1
                d = backoff * (2 ** k)
                if jitter and d > 0:
                    d = rnd.uniform(0, d)
                heapq.heappush(ev, (end + d, 1, rid, k + 1))
            else:
                failed += 1
    return dict(success=ok / n, tries=tries / n,
                wasted=wasted / max(work, 1e-9),
                p50=..., p99=...)

# 那张 5 × 6 的表
cap = 8 / 0.010
for load in (0.85, 1.0, 1.10, 1.20, 1.30):
    run(load * cap, attempts=3, deadline_check=True,
        backoff=0.05, jitter=True, budget=0.10)
```
