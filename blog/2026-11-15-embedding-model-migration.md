## 一、事故形态：指标全绿，客服在喊

先说一个真实形态，细节做了脱敏。

某知识库检索服务决定把 embedding 模型从 A 换成 B（B 在同一份内部评测集上 NDCG 高 4 个点）。上线方案很"稳妥"：新写入的文档用 B 算向量，历史文档不动，查询侧逐步切到 B。理由是"两边语义空间差不多，混着用影响不大，慢慢回填"。

两周后：

- 客服反馈「搜不到三个月前的老工单」，抽样复现，能复现
- 检索服务的 recall@10 监控：**从 0.83 变成 0.84，还涨了一点**
- P99 延迟、GPU 利用率、索引内存：全部正常
- 人工标注了 50 条查询看 top-10：涉及新文档的都对，涉及老文档的一条都召不回

第三行是关键。**整体 recall 没掉，因为它统计的是"命中了多少个相关文档"，而这些命中全部来自新文档**。老文档被系统性地挤出了候选集，但没有任何一个指标以"版本"为维度去看这件事。

这种事故比 OOM 更贵，因为它不打断服务、不触发告警，只在业务侧以"搜不到东西"的形式缓慢渗透，通常要等用户投诉才被发现。

## 二、为什么两个模型的向量不能混

三层不可比，从根本到表面。

### 2.1 坐标系不可比

模型 A 是映射 `f_A: text -> R^d_A`，模型 B 是 `f_B: text -> R^d_B`。`cos(f_A(x), f_B(y))` 在数学上能算出一个数，但它**不表达任何语义关系**——它是两个独立训练出来的坐标系里各取一个点算夹角，结果近似随机。

维度相同也不救。1024 维的 bge 和 1024 维的 e5 是两个完全不相干的空间，第 37 维在 A 里可能编码"是否涉及金额"，在 B 里可能编码"语气正式程度"。维度不同更没得谈——补零、截断、PCA 对齐都是把一个空间硬塞进另一个，只保留维度数量的巧合。

### 2.2 各向异性不同，导致分数尺度不同

真实的 sentence embedding 有强烈的各向异性：所有向量分布在一个窄锥里，任意两句话的 cosine 均值远高于 0（典型在 0.1 到 0.4 之间，而不是各向同性假设下的 0）。

不同模型锥的开口角度不同。后果是：**同一个阈值在两个模型上完全不等价**，而且更致命的是，两版向量在同一候选集里比较时，分数分布不重叠的那一方会被系统性挤出。

### 2.3 别指望用线性映射把旧向量"转"过去

这是最常见的错误想法：「训一个小 MLP / 算一个 Procrustes 旋转矩阵，把旧向量映射到新空间，就不用重算了。」

Procrustes（正交对齐）只在**同架构、同训练数据、同维度**的两个 checkpoint 之间才勉强有意义（比如同一个模型微调前后的两版），跨模型时语义邻域结构会被非线性地扭曲，正交变换保不住。

实测经验：跨模型用线性映射对齐后再检索，recall 通常只能恢复到直接重嵌入的六到七成，且需要一份配对语料（几十万条同文本的双版本向量）去拟合。**省下的重嵌入算力，会在评估、调参、线上长尾上还回去**。直接重算，别绕。

## 三、量化：混用到底损失多少

合成实验，可复现（脚本在文末）。设计：6000 篇文档分布在 60 个语义簇里，1024 维，600 条查询（由真实文档加噪生成）。相关集定义为「与查询同簇的 top-50 文档」，基线 recall@10 在 v1 单一索引下是 **1.000**（这个合成集偏容易，只看相对变化）。

两个版本共享语义，但分数尺度不同——这是现实中两种真实存在的情形：

| 情形 | gamma | v2 自身 recall@10 | 旧文档平均分 | 新文档平均分 | top-10 旧/新 | 旧文档召回 | 新文档召回 | 整体 recall@10 |
|---|---|---|---|---|---|---|---|---|
| 基线（同版本） | 0.0 | 1.000 | 0.014 | 0.013 | 5.0 / 5.0 | 1.000 | 1.000 | 1.000 |
| 新模型抬分 | 0.8 | 1.000 | 0.011 | 0.400 | **0.0 / 10.0** | **0.000** | 1.000 | **1.000** |
| 新模型压分 | 0.8 | 0.684 | 0.012 | 0.008 | **10.0 / 0.0** | 0.801 | **0.000** | 0.808 |

（抬分 = 新模型各向异性更强，全体分数抬高；压分 = 新模型更分散，全体分数压低。两种都实测存在，取决于模型家族。）

两行加粗的数字就是事故的全部：

- **抬分情形**：top-10 里一个新文档都没给老文档留位置，旧文档召回 **0.000**，而整体 recall 依然是 **1.000**。因为相关集里一半是新文档，命中率被新文档撑满了。
- **压分情形**：反过来，新写入的文档永远排不上，新文档召回 **0.000**，整体掉到 0.808 但很少有人会把它归因到"版本混用"。

注意抬分那一行：整体指标**完全没有变化**。这就是"静默"的字面含义——不是"略微变差"，是"一半数据不可见，而度量指标无感"。

## 四、整体 recall 是错的指标

`recall@10` 回答的是「相关文档被召回了多少」，它默认所有文档在被检索这件事上是同质的。版本迁移期这个假设失效了。

迁移期必须加三个维度：

```python
import numpy as np

def slice_metrics(hits_by_doc, doc_version, k=10):
    """hits_by_doc: (n_query, n_doc) bool，是否被召回到 top-k
       doc_version: (n_doc,) 每条文档的向量版本
       返回按版本切片的召回率 + 覆盖率偏斜
    """
    out = {}
    for ver in np.unique(doc_version):
        mask = doc_version == ver
        # 1) 该版本作为"结果"被召回时的命中率
        out[f"recall_v{ver}"] = hits_by_doc[:, mask].mean()
        # 2) 该版本在 top-k 中的占比 vs 它在库中的占比
        share_in_results = hits_by_doc[:, mask].sum(1).mean() / k
        share_in_corpus = mask.mean()
        out[f"skew_v{ver}"] = share_in_results / max(share_in_corpus, 1e-9)

    # 3) 覆盖率偏斜的判据：skew 应该贴着 1.0
    #    skew ~ 0 或者 skew ~ 2 都是事故
    return out
```

三个指标里最关键的是 **skew**：某一版本在结果中的占比，除以它在库中的占比。基线应该接近 1.0；如果旧版本 skew 接近 0，不管整体 recall 多漂亮，迁移都是坏的。

这个指标应该常驻监控，而不是迁移时才临时加。

## 五、临时缓解：四种融合策略的真实收益

如果因为工期必须混用一段时间（比如双写一周），有没有办法把损失压住？我拿同一份数据跑了四种融合：

| 策略 | 抬分情形 整体 | 抬分 旧文档 | 压分情形 整体 | 压分 新文档 | top-10 旧/新 |
|---|---|---|---|---|---|
| 1) 原始分直接混排 | 1.000 | **0.000** | 0.802 | **0.000** | 0/10 或 10/0 |
| 2) per-version 全局 z-score | 0.905 | 0.803 | 0.736 | 0.644 | 4.8/5.2 |
| 3) per-query min-max 归一化 | 0.913 | 0.820 | 0.737 | 0.657 | 4.8/5.2 |
| 4) RRF 名次融合（k=100） | **0.931** | **0.863** | **0.773** | **0.687** | 5.0/5.0 |

三个结论，每个都反直觉：

**第一，原始分混排不是"变差一点"，是直接归零。** 分数尺度差异主导了排序，语义相关性完全不起作用。

**第二，校准能拉回偏斜，但整体指标会掉。** 抬分情形下 z-score 把旧文档从 0.000 救回到 0.803，整体从 1.000 掉到 0.905。掉的那部分是"把质量更差的新向量放回竞争后，挤掉了原本干净的旧文档"。**分数校准不能凭空创造语义质量**——它只对齐均值和方差，模型间的语义差异还在。

**第三，RRF 最好，但四种都救不回 1.000。** RRF 之所以赢，是因为它在每个版本内部先排序（版本内排序永远自洽），再融合名次，绕开了"跨空间比分数"这件事。代价是要对每个版本各取 100 个候选，延迟和计算翻倍。

所以：**融合只能是小时级到天级的灰度手段，不能是月级的常态**。如果方案文档里写"双写一个月慢慢回填、混着用"，那基本等于接受了几周的静默丢数据。

RRF 融合的最小实现：

```python
def rrf_merge(score_matrix, version_mask, k_rrf=60, topn=100, k=10):
    """按版本分组、各自排序后按名次融合。规避跨空间比分数。"""
    n_q = score_matrix.shape[0]
    fused = np.zeros_like(score_matrix)
    for mask in version_mask:
        sub = score_matrix[:, mask]                      # (n_q, n_ver)
        local = np.argsort(-sub, axis=1)[:, :topn]       # 版本内排序
        global_idx = np.where(mask)[0][local]
        ranks = np.arange(1, topn + 1)[None, :]
        np.add.at(fused,
                  (np.arange(n_q)[:, None].repeat(topn, 1), global_idx),
                  1.0 / (k_rrf + ranks))
    return np.argsort(-fused, axis=1)[:, :k]
```

## 六、迁移方案：三条路和它们的账

### 方案 A：停机全量重嵌入

最简单，成本最高。工期 = `总 token 数 / 单卡吞吐 / 卡数`。

一个中等规模知识库：1 亿条文档、平均 400 token = 400 亿 token。按单卡 2000 万 token/小时（bge-m3 级别，A10/A100 视 batch 而定，这个数字必须在自己的机器上实测，别用别人的）算，需要 2000 卡时。8 卡并行 = 250 小时 = 10 天。

10 天停机不可接受，所以 A 只适合小库（千万条以内）或者可以接受双活切换的场景。

### 方案 B：双写 + 双索引 + 查询侧版本路由（推荐）

核心约束只有一条：**任一时刻，一次查询只能对着一个版本的索引做检索**。不要让两版向量进同一个索引，无论你怎么融合。

```python
class EmbeddingMigration:
    """双写双索引状态机。关键：查询永不跨版本排序。"""

    def __init__(self, old_model, new_model, old_idx, new_idx):
        self.old_model, self.new_model = old_model, new_model
        self.old_idx, self.new_idx = old_idx, new_idx
        self.phase = "dual_write"      # dual_write -> shadow -> cutover -> cleanup

    def write(self, doc):
        # 双写期必须两边都写成，且不允许"新模型失败就写旧向量"的降级
        # 否则会出现第三种混合态，比不做还糟
        v_old = self.old_model.encode(doc.text)
        v_new = self.new_model.encode(doc.text)
        self.old_idx.upsert(doc.id, v_old, version=1)
        self.new_idx.upsert(doc.id, v_new, version=2)

    def query(self, text, traffic_pct):
        # 按流量比例切，不是按请求内容切；同一请求只走一个版本
        use_new = hash(text) % 100 < traffic_pct
        model, idx = ((self.new_model, self.new_idx) if use_new
                      else (self.old_model, self.old_idx))
        return idx.search(model.encode(text), k=10)

    def backfill(self, batch):
        # 回填 worker：只处理 version != 2 的文档，幂等
        for doc in batch:
            if doc.embed_version != 2:
                self.new_idx.upsert(doc.id, self.new_model.encode(doc.text), version=2)
                doc.embed_version = 2
```

三个必须写进设计文档的点：

1. **双写不允许降级**。新模型推理失败时，宁可直接失败重试，也不要"写个旧向量凑合"——那会在新索引里制造出一批向量版本未知的记录，而这些记录的召回表现和正常文档无法区分，排障成本极高。
2. **路由按流量比例，不按文档**。如果新文档走新索引、老文档走老索引，一条查询就只能命中一半库，效果上等价于混用。
3. **回填必须幂等且可断点续传**。用 `embed_version` 字段做游标，不要用时间戳（双写和回填会并发改同一批文档）。

### 方案 C：惰性回填（只写新数据，旧的不动）

死路。查询必须用某一个模型编码，用新模型就召不回旧文档，用旧模型就召不回新文档。除非你在查询侧路由（那其实是方案 B 的一半），否则数学上无解。

## 七、存储与工期的硬账

双索引期的存储是真的翻倍，这笔钱要提前报预算：

| 精度 | 字节/维 | 1 亿条 × 1024 维 | 双索引期 |
|---|---|---|---|
| float32 | 4 | 410 GB | 819 GB |
| float16 | 2 | 205 GB | 410 GB |
| int8 | 1 | 102 GB | 205 GB |
| binary | 0.125 | 13 GB | 26 GB |

注意 HNSW 还有图结构的开销：M=32 时每层每条边的邻接表约 `M × 4 字节 × 层数`，实际内存通常是原始向量的 1.3 到 1.6 倍。双索引期要按 **2.6 倍** 规划，不是 2 倍。

降精度的路可以走，但要在 golden set 上验证：float16 一般无损，int8 通常掉 1 到 3 个点 recall，binary 只在粗筛（配合 rerank）时可用。

## 八、索引层现实：HNSW 改不了向量

`hnswlib` / FAISS 的 HNSW 都**不支持原地更新向量**。改一条文档的向量 = 删一条 + 插一条。而删除只是打墓碑（tombstone），节点和边都留在图里，内存不释放。

墓碑的直接后果是 top-k 里混进已删节点，实际可用结果变少：

| 墓碑比例 p | top-10 存活率 | 凑够 10 个存活平均需取 | p95 倍数 |
|---|---|---|---|
| 0.00 | 1.000 | 10.0 | 1.00x |
| 0.05 | 0.958 | 10.4 | 1.20x |
| 0.10 | 0.919 | 10.9 | 1.30x |
| 0.20 | 0.834 | 12.0 | 1.50x |
| 0.30 | 0.762 | 13.2 | 1.70x |
| 0.50 | 0.595 | 17.3 | 2.40x |

经验公式：`over_fetch ≈ k / (1 - p)`，p95 需要再乘 1.2 左右。

迁移期这一点会放大：整个回填过程本质上是"把 1 亿条向量全部删一遍再插一遍"，墓碑比例会单调涨到接近 100%。所以：

- 回填**不要**对着线上索引做，要写进一个新建的索引，回填完再原子切换别名
- 如果必须原地回填，墓碑比例到 20%（top-10 存活率跌破 0.85）就该触发重建
- 重建成本按分片滚动算：单分片 1000 万条 HNSW 重建大约 30 到 60 分钟（取决于 M 和 efConstruction），期间该分片只能用旧索引兜底

## 九、验证与回滚

**评估集必须按版本打标。** golden set 里每条相关文档都记上它的 `embed_version`，报告时按版本切片。这是唯一能在灰度期发现"静默丢数据"的手段。

**放量节奏**：1% → 10% → 50% → 100%，每档至少跨一个业务周期（覆盖长尾查询）。每一档看三个数：整体 NDCG@10、旧版本文档的 skew、新版本文档的 skew。

**回滚成本是硬的**：回滚要求旧向量还在。所以双索引期的 2.6 倍内存不是"可以优化掉的浪费"，而是回滚能力的定价。想省钱提前删旧索引，等于放弃了回滚——这个决定要在方案评审时明确写出来，别让运维在预算压力下自己偷偷做了。

## 十、踩坑清单

1. **别用线性映射对齐旧向量**。跨模型只能恢复到重嵌入的六到七成，还要养一份配对语料。直接重算。
2. **别让两版向量进同一个索引**。哪怕维度相同、哪怕加了分数归一化，也只在灰度期用 RRF 过渡，不做常态。
3. **阈值必须重新标定**。旧模型 0.65 的阈值，在新模型上可能等价于 0.82 或 0.41。用 golden set 的分位数定，不要沿用绝对 cosine 值。
4. **整体 recall 会骗你**。迁移期必须按版本切片，看 skew，不看总量。
5. **双写不能降级**。新模型失败就失败，别写旧向量凑数，否则索引里出现版本未知的混合态。
6. **墓碑不还内存**。回填写新索引再切别名；原地回填要盯 top-k 存活率，跌破 0.85 就重建。
7. **双索引期按 2.6 倍内存报预算**，图结构开销别漏。

## 附：复现脚本

```python
import numpy as np

rng = np.random.default_rng(20261115)
D, N, NQ, K, C = 1024, 6000, 600, 10, 60

def unit(x):
    return x / np.linalg.norm(x, axis=-1, keepdims=True)

# 60 个语义簇
centers = unit(rng.normal(size=(C, D)))
cid = rng.integers(0, C, N)
docs_v1 = unit(centers[cid] + 0.42 * rng.normal(size=(N, D)) / np.sqrt(D))

QIDX = rng.choice(N, NQ, replace=False)
q_v1 = unit(docs_v1[QIDX] + 0.25 * rng.normal(size=(NQ, D)) / np.sqrt(D))
S1 = q_v1 @ docs_v1.T

# 相关集 = 同簇 top-50
rel = np.zeros((NQ, N), dtype=bool)
for i in range(NQ):
    same = np.where(cid == cid[QIDX[i]])[0]
    rel[i, same[np.argsort(-S1[i, same])[:50]]] = True

def recall(S, relset, k=K):
    idx = np.argsort(-S, axis=1)[:, :k]
    return np.take_along_axis(relset, idx, axis=1).sum(1).mean() / k

old = np.arange(N) < N // 2
new = ~old
g = 0.8
m = unit(rng.normal(size=D))
# 新模型更各向异性：全体分数抬高
d2 = unit(docs_v1 + g * m)
q2 = unit(q_v1 + g * m)

S_mix = q2 @ np.where(old[:, None], docs_v1, d2).T
top = np.argsort(-S_mix, axis=1)[:, :K]
hits = np.take_along_axis(rel, top, axis=1)

print("整体 recall@10 =", hits.sum(1).mean() / K)          # 1.000  <- 指标全绿
print("旧文档召回     =", hits[old[top]].mean() if old[top].any() else 0.0)  # 0.000
print("top-10 旧文档数 =", old[top].sum(1).mean())         # 0.0
```

跑出来就是「整体 1.000 / 旧文档 0.000 / top-10 里零个旧文档」。

一句话总结：**embedding 换代的正确姿势是把索引也换掉，而不是把向量混起来**。混用的代价不是"效果差一点"，而是一半数据在你的监控眼皮底下消失。
