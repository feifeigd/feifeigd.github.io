## 一、先把需求压成数字

系统设计的第一个动作永远不是画架构图，是把模糊需求压成 5 个数。

**规模。** 日搜索 12 亿次，平均 13,889 QPS，峰值系数取 5 → 峰值 70k QPS。

**放大系数。** 一次搜索在客户端会产生多次前缀请求：用户打「面试题」三个字，如果每个按键都发一次，就是 3 次；加了 250ms 防抖之后，一般在词与词的边界各发一次，实测经验系数是 1.5 到 2.5。取 2.5：

```
峰值前缀请求 = 70,000 × 2.5 = 175,000 QPS
```

**语料。** 索引里放 30 天窗口内去重后的 10 亿条查询，平均长度 13 个字符（下面第三节的实测语料就是这个量级的等比缩小版）。

**延迟。** typeahead 的用户感知极强：每按一个键都要刷新建议，p99 超过 100ms 用户就会觉得「卡」。所以目标定 p99 100ms。

**可用性。** 99.99%，每月 4.3 分钟不可用。

这五个数一摆出来，方案的空间就被框住了：175k QPS 的读、10 亿条的语料、100ms 的硬预算。接下来所有设计都只为这三个约束服务。

### 100ms 花在哪

面试时把这张表画出来，比画任何架构图都有效：

| 环节 | p99 预算 | 依据 |
| --- | --- | --- |
| 客户端 → 边缘（4G/5G RTT，TLS 已复用） | 35ms | 物理距离决定，架构改不了 |
| 边缘网关：鉴权、限流、路由 | 3ms | 本地内存判定 |
| 应用层：参数校验、归一化、个性化重排 | 5ms | 纯 CPU |
| 索引查询（含 1 次网络跳转） | 8ms | 同机房 RTT 0.3ms 加排队 |
| 序列化 + 下行传输（10 条 × 60B ≈ 1.2KB） | 10ms | 与上行同链路 |
| 余量（GC、慢节点、长尾） | 39ms | 留给不可预期 |

注意第四行：索引查询的预算是 8ms，而下文实测的单次索引查询是 **0.60 微秒**。差了四个数量级。这不是我写错了，这就是这道题的核心真相：

> **在这道题里，索引查询从来不是瓶颈。瓶颈是网络、是分发、是这个 100ms 预算里你要不要多跳一次网络。**

想通这一点，你才会把设计重心从「用什么树」挪到「怎么让请求少跳一次网络、怎么让索引在不停机的情况下换掉」。

## 二、数据结构不是瓶颈（实测）

先把这个误解彻底打死。用 15 万条查询建索引，两种查法各跑 6 万次取分位：

| 查法 | p50 | p99 | 说明 |
| --- | --- | --- | --- |
| 前缀 → top-10 表直接查（哈希表） | 0.60us | 1.40us | 长度不超过 4 的前缀，预计算 |
| 二分定位 + 堆取 top-10 | 5.70us | 36.10us | 长度 5 到 6 的前缀，扫描子树 |
| 纯二分定位区间（不含取 top-k） | 5.12us | — | 上一条的开销主体 |

（Python 3.11，单核，WSL。绝对值比 C++ 慢一个数量级左右，但量级结论完全一样。）

10 亿条语料是这里的 6667 倍，就算你把这些数字线性放大——一条不走索引的蠢实现——单次查询也就 40ms；而真正做过工程优化的索引，10 亿条下仍然是微秒到几十微秒。**所以面试官问「为什么用 trie 不用哈希表」时，他在考的不是性能，是空间和查询路径的匹配度。** 性能从来不是这题的难点。

那难点是什么？三件事：

1. **空间**：top-k 要预存多少条，才能既装得下又答得快。
2. **分片**：10 亿条切几片、切在哪、一次查询扇出多少。
3. **更新**：索引是只读的，怎么在不中断服务的前提下换掉它。

下面逐个算。

## 三、第一笔账：唯一前缀数有硬上界

先看实测。15 万条查询（平均 13.11 字符，p99 长度 24，总字符 1,966,702），把所有前缀展开去重：

| 前缀长度 | 唯一前缀数 | 累计 |
| --- | --- | --- |
| 1 | 26 | 26 |
| 2 | 675 | 701 |
| 3 | 6,309 | 7,010 |
| 4 | 19,772 | 26,782 |
| 全部（长度不超过 12） | 619,965 | — |

同时，语料总字符是 1,966,702——也就是说一棵完整 trie 的节点数约等于总字符数，200 万级。

### 如果给所有前缀都预存 top-10

每个条目 8 字节（4 字节 query id + 4 字节 score），10 条一批：

```
15 万条语料：619,965 × 10 × 8B = 47.3 MiB
10 亿条语料：× 6667 ≈ 315 GB
```

315 GB。这就是「画个 trie 每条边挂 top-10」的代价。装不下，方案作废。

### 但长度不超过 4 的前缀，数量有上界

这是整道题最漂亮的一步计算。26 个小写字母：

```
26 + 26^2 + 26^3 + 26^4 = 26 + 676 + 17,576 + 456,976 = 475,254
```

**475,254 这个数跟语料规模没有任何关系。** 你有 100 万条查询还是 100 亿条查询，长度不超过 4 的前缀最多就这么多，因为字符集和长度把它钉死了。于是：

```
475,254 × 10 × 8B = 38,020,320B ≈ 36.3 MiB
```

10 亿条查询的全部 4 字符前缀 top-10 表，**36 MiB**。单机内存随便放，甚至可以整份塞进 L3 之外的一级缓存里。

实测那一份更小：26,782 个前缀 × 10 × 8B = 2.0 MiB（Python 的 dict 版实测 4.4 MiB，合 172 B/前缀；紧凑的二维数组是 80 B/前缀）。

### 那长度 5 以上怎么办

先看流量分布。用户输入到第 4 个字符还没选中的比例有多低？按「60% 输入 1 个字符就停、25% 到 2 个、10% 到 3 个、5% 到 4 个」的输入停点模型，对语料加权统计请求落在哪个前缀长度：

| 需要的前缀长度 | 流量占比 | 累计 |
| --- | --- | --- |
| 1 字符 | 61.4% | 61.4% |
| 2 字符 | 23.2% | 84.6% |
| 3 字符 | 10.7% | 95.3% |
| 4 字符 | 4.7% | 100% |

**预计算到 4 字符，覆盖 100% 的请求**（这批语料最短 3 字符，所以第 4 个字符必然已经确定）。真实系统里用户会一直输入到 8 个字符，那也只需再补一条：

> 5 字符以上的前缀，节点数上界是 26^5 = 11,883,376，top-10 表要 946 MiB——不值得。这一层改走「二分定位子树 + 堆取 top-10」的扫描路径。

而扫描的代价是可以算的。实测各长度前缀下的子树规模（也就是要扫多少条候选）：

| 前缀长度 | 子树大小 p50 | p99 | 最大 | 均值 |
| --- | --- | --- | --- | --- |
| 2 | 77 | 2,013 | 8,578 | 222.2 |
| 3 | 13 | 134 | 806 | 20.9 |
| 4 | 3 | 72 | 584 | 7.2 |
| 5 | 2 | 63 | 1,178 | 6.6 |
| 6 | 1 | 43 | 1,177 | 4.6 |

注意 p99 和最大值的差距：长度 2 的前缀下有 8,578 条候选（那是「某个热前缀」），长度 5 的某个前缀下有 1,178 条（那是品牌词前缀，比如一家公司的全名）。这类长尾尖刺正是「扫描路径必须有上限」的原因——堆取 top-10 的复杂度是 O(n log k)，n 上千的时候实测 p99 就是 36 微秒，仍然远在预算内。

结论很清楚：

> **长度不超过 4 的前缀，全量预计算（36 MiB，可复制到每个节点）；长度 5 以上，二分 + 堆扫描（子树 p99 几十到上千条，几十微秒）。**

一句话把这题的「索引结构」答完了。数据结构的选型（双数组 trie、前缀哈希、有序数组 + 二分）在这里反而变成次要问题，因为三者都够快，差别只在构建复杂度和更新代价。

### 中文场景：上面这套上界全部失效

必须主动说出这个反例，否则会被追问打穿。汉字常用 3,500、Unicode 汉字区 20,992 个：

```
长度 1：20,992
长度 2：4.4 亿
长度 3：9.2 万亿
```

上界彻底没了。中文搜索的做法完全不同：

- 只对「热前缀白名单」预计算（前 100 万个高频前缀，实测能吃掉 80% 以上流量）；
- 其余走 n-gram 索引（1 到 2 字的 gram）+ 倒排，查询时求交集，再用 BM25 或点击率排序；
- 或者用有限状态转换器（FST）把词典压到原大小的 10% 以下，代价是构建慢、只能整份重建。

**「26 个字母」是这个解法成立的前提。** 换字符集，前提就没了，这是这道题最容易漏掉的一层。

## 四、top-k 怎么算出来：离线重建，蓝绿切换

索引是只读的快照，所以 top-k 一定是离线算好的。实测构建成本：

```
26,782 个前缀 × 每个 top-10，语料 150,000 条
耗时 0.99 秒，产出 140,596 个 (query id, score) 对
```

为什么这么快？因为复杂度不是直觉上的 O(N × L × k)。每个 query 只落进它自己的 L 个前缀桶（L 是它的长度截断到 4），桶内做一次 top-k 归并：

```
总工作量 = Σ(每个 query 贡献的前缀数) = N × L ≈ 4N
```

线性。放大到 10 亿条：

```
0.99s × 6667 ≈ 110 分钟（单线程）
32 个分片并行 → 约 4 分钟
```

**四分钟就能全量重建一次 10 亿条的索引。** 这个数字直接决定了架构选择：不要做增量更新，做蓝绿重建。

### 蓝绿的三个细节

1. **两套索引 + 一个版本指针。** 切换是一次原子赋值（`current = new`），读路径上的版本指针用 RCU 风格，老版本等在读请求排空后回收。
2. **回滚成本是 0。** 因为老索引还在，指针指回去就行；这在「新索引因为数据 bug 质量下降」的场景里救命。
3. **切换必须可分片独立进行。** 每个分片各自切，全局不需要协调；某个分片切失败，它继续用旧版本，也不会让整个集群不可用。

### 那实时的 5% 呢

真正需要「刚刚发生的查询立刻能补全」的场景极少（大多是运营或公关的幻想）。如果确实要，用 overlay：

- 近线作业每 60 秒聚合一次新查询的 top-k，写成一个小 overlay 索引；
- 读路径 = 主索引 top-10 + overlay top-10，合并取 10；
- overlay 大小超过主索引条目数的 10% 就触发重建。

合并成本是实测的微秒级（两个 10 条的有序表归并），完全可以放在读路径上。

### 一个高频错误答案

「把全站查询按分数排序，取前 100 万条作为建议池。」——这在前缀查询下完全不工作：按分数排序后，某个前缀的所有查询不再连续；而按字典序排序后，前缀的候选集连续了，但 top-10 不在区间头部。**两个排序键不可能同时满足，所以要么预计算，要么每次扫区间。** 这句话说出来，面试官就知道你真的想过。

## 五、第二笔账：分片切在前缀上，不是切在查询上

10 亿条、36 MiB 的短前缀表可以每节点一份，但 5 字符以上的长尾还是要分片。分片方案错了，前面所有优化都白费。

### 反例一：按 query 哈希分片

为了写入和容量均衡，很多人第一反应是 `shard = hash(query) % 26`。实测均衡性确实完美：

| 方案 | 条目 max/avg | 条目 min/avg |
| --- | --- | --- |
| hash(query) % 26 | 1.02 | 0.98 |

但代价是：**一个前缀的所有查询被打散到全部 26 个分片**，一次补全必须扇出 26 片、等最慢的那片。

扇出的代价是尾延迟放大，实测（每分片延迟取对数正态，p50 3ms、p99 8ms，模拟 20 万次）：

| 扇出 | p50 | p90 | p99 | p999 |
| --- | --- | --- | --- | --- |
| 1 | 2.75ms | 4.71ms | 7.35ms | 10.17ms |
| 4 | 4.18ms | 6.23ms | 9.00ms | 12.05ms |
| 16 | 5.68ms | 7.82ms | 10.75ms | 13.89ms |
| 64 | 7.24ms | 9.49ms | 12.57ms | 15.97ms |

**扇出 16，p99 从 7.35ms 涨到 10.75ms，涨了 46%。** 这是纯粹的「取最大值」统计效应，任何缓存、任何超时设置都消除不了——除非你减少扇出。而 100ms 预算里我们已经只留了 8ms 给索引。

### 反例二：按首字母范围分片

那就按前缀的字典序范围切，字母表天然是 26 片。实测：

| 指标 | 值 |
| --- | --- |
| 条目 max/avg | 8.08（46,597 对 1,014） |
| 流量最大分片占比 | 30.7% |
| 流量最小分片占比 | 0.4% |

**8 倍倾斜。** 只要首字母分布不均（现实中必然不均），26 片范围分片就有一片扛 30% 的流量，其余闲着。

### 正解：范围分片 + 等频切点，粒度要细

保留范围分片（因为前缀查询本质是范围查询，必须让子树落在同一片），但切点不能按字母数均分，要按**累计流量等频**切。而且粒度必须比热点粒度细：

| 分片数 | 切分粒度 | 流量 max/avg | min/avg |
| --- | --- | --- | --- |
| 26 | 1 字符 | 2.45 | 0.76 |
| 8 | 2 字符 | **1.000** | 1.000 |
| 16 | 2 字符 | 1.045 | 0.997 |
| 32 | 2 字符 | **2.090** | 0.953 |

三个数字各讲一件事：

- **26 片按 1 字符切，等频也救不了（2.45）。** 因为最大的那个字母自己就超过 1/26 的流量，切不开——粒度太粗，热点的最小单位还比片大。
- **8 片按 2 字符切，完美均衡（1.000）。** 675 个桶分给 8 片，每片 84 个桶，每个桶都远小于 1/8 的流量，贪心装填能装到几乎相等。
- **32 片按 2 字符切，反而退化成 2.090。** 675 / 32 ≈ 21 个桶每片，但最大的几个桶本身就有 1% 到 6.5% 的流量（实测最高单桶 6.5%），而 1/32 是 3.1%——**一个桶就超了一片该有的量**。分片数一旦逼近「桶的粒度」，均衡就崩了。

这条规律的通用形式：

> **分片的粒度必须比热点细一个数量级以上。** 经验值：每片至少装 50 到 100 个桶。

### 10 亿条时怎么落地

2 字符只有 675 个桶，不够切 64 片。往上取：

| 桶粒度 | 桶数上界 | 64 片时每片桶数 |
| --- | --- | --- |
| 2 字符 | 676 | 10.6（不够，会倾斜） |
| 3 字符 | 17,576 | **275（够）** |
| 4 字符 | 456,976 | 7,140（绰绰有余，但路由表变大） |

所以生产配置是：**3 字符桶、64 分片、按累计流量等频切点**，路由表 17,576 项 × 8B = 140KB，可以整份下发到每个边缘节点，路由是纯内存查表。

### 但短前缀怎么办：一级本地表

这里有个隐藏的陷阱。3 字符桶意味着「用户输入 1 个字符」时，`a` 这个前缀跨越所有以 `a` 开头的桶——按 30.7% 的流量分布，它可能横跨十几个分片。**短前缀的扇出问题，范围分片本身解决不了。**

解决办法正好和第三节的结论咬合：

> 长度不超过 4 的前缀 top-10 表只有 36 MiB 上界。**整份复制到每个边缘节点和每个分片。**

于是查询路径变成两级：

```
用户输入 L 个字符
  ├─ L ≤ 4：查本地全量表（0.60us），结束。不跳网络。
  └─ L ≥ 5：查路由表（内存）→ 1 次跳转到目标分片 → 二分 + 堆扫描（5.70us）
```

因为 L ≤ 4 覆盖了 95% 以上（本模型 100%）的请求，**绝大多数补全请求在边缘节点的本地内存里就结束了**。这解释了第一节那个「索引预算 8ms、实测 0.6us」的荒谬反差——不是你测得不准，是架构正确的时候，这次查询压根没发生。

### 容量核算

```
边缘命中的 95%：175,000 × 0.95 = 166,250 QPS，纯本地内存查表
中心长尾的 5%：175,000 × 0.05 = 8,750 QPS，分散到 64 分片 = 137 QPS/分片
单核扫描能力：1 / 5.7us ≈ 175,000 QPS
```

每分片 137 QPS，单核能力 175,000 QPS，**余量 1,277 倍**。所以索引层的容量根本不是问题，副本的作用是可用性而不是吞吐。真正的问题是：**怎么把 36 MiB 的表可靠地、可版本化地分发到 200 个边缘节点。**

这句话是这道题的分水岭。答到这里，你和「画 trie」的候选人已经不在一个层次上了。

### 每个分片返几条

如果某些场景确实要扇出（比如边缘没命中、回源聚合多副本，或者跨地域聚合），每片返几条直接影响正确性。实测 300 个 2 字符前缀，真实 top-10 与「每片只返 k' 条再合并」的召回率：

| 每片返回 k' | 召回率 | 解释 |
| --- | --- | --- |
| 1 | 84.12% | 平均每 10 条错 1.6 条 |
| 2 | 98.05% | 已经可用 |
| 3 | 99.87% | 几乎无损 |
| 5 | 100.00% | 严格正确 |
| 10 | 100.00% | 严格正确，也是教科书答案 |

严格的正确性要求每片返回 k 条、合并 k×S 条再取 k。想省带宽只返 3 条，理论上仍可能漏（一个分片包揽前 4 名时必漏），但实测召回 99.87%。**这是典型的「用 0.13% 的召回换 3 倍带宽」的取舍，可以谈，但必须说清代价。**

## 六、第三笔账：热词统计用什么

top-k 的分数从哪来？这是全链路唯一有写放大的地方，也是 CMS（Count-Min Sketch）最容易被误用的地方。

实测：15 万条查询，总事件数 838,550，用 w=2^16、d=4 的 CMS（1 MiB）：

| 频率排名区间 | 绝对误差 p50 | 相对误差 p50 | 相对误差 p99 |
| --- | --- | --- | --- |
| rank 1-100 | 1 | 0% | 1% |
| rank 1k | 1 | 1% | 7% |
| rank 10k | 1 | 5% | 50% |
| rank 50k | 1 | 25% | 250% |

三个结论：

1. **CMS 只高估、不低估。** 每个计数器的值等于「哈希到它的所有项之和」，所以误差恒为正。用它做排序，长尾会被系统性抬高。
2. **绝对误差的期望是「总量除以宽度」：** 838,550 / 65,536 = 12.80，实测 p50 的绝对误差是 1（因为大多数项的哈希碰撞少），但相对误差在小频次项上爆炸——rank 50k 的中位数是 25%，p99 是 250%。
3. **噪声与总量成正比。** 流量翻倍，绝对误差翻倍，相对误差不变；但如果你把宽度固定，语料增长就等于误差增长。

正确用法：

> CMS 只用来**粗筛候选**（谁有可能进 top-k），候选确定后用精确计数（分片内的精确 map 加 top-K 堆）算最终分数。头部 100 名 CMS 的相对误差只有 0% 到 1%，够粗筛；拿它当排序依据就是把 250% 的噪声写进用户看到的第一条。

如果连精确 map 都嫌大，用 Space-Saving：维护 k 个 (item, count) 槽，满了就替换最小者并继承它的计数。保证「出现频率超过总量 1/k 的项一定被留住」，而且计数误差有上界。

### 时间衰减：半衰期定了，排序就定了

分数不能是历史累计。实测公式 `score = count × 0.5^(age_days / halflife)`：

| 半衰期 | 90 天前累计 1 万次 | 今天 800 次 | 谁赢 |
| --- | --- | --- | --- |
| 3 天 | 0.0 | 800 | 今天的 |
| 7 天 | 1.3 | 800 | 今天的 |
| 30 天 | 1,250 | 800 | 常青词 |

反过来说，半衰期 7 天时，一个 90 天前的老词需要 **7,420 倍**的日搜索量才能和新词打平；半衰期 30 天时只需要 8 倍。

所以半衰期的选择是一次产品决策，不是技术参数：**7 天 = 追热点（新闻、突发事件）；30 天 = 保常青（工具、品牌）。** 一律 7 天会让「天气」这类词永远上不了榜，一律 30 天会让突发事件压不住。

### 55% 的查询只出现过一次

实测语料里 55.0% 的查询词频为 1。这带来两个后果：

- 它们永远进不了 top-k，但**必须存在索引里**——用户输入全名时你总得给个建议，只是分数并列时按字典序兜底。
- **隐私风险**：只被一个人搜过的 query 出现在补全里，等于泄露「谁在搜什么」。策略是只索引「出现次数不少于 3 且出现在多个独立会话」的查询，剩下的只做精确匹配兜底。

## 七、缓存、个性化与合规

### 缓存能吃多少

实测流量集中度：

| 对象 | 流量占比 |
| --- | --- |
| top-100 query | 23.10% |
| top-1000 query | 40.94% |
| top-10 的两个字符前缀 | 24.3%（最高单前缀 `aa` 6.5%） |

边缘缓存 `(prefix, 语言, 设备类型, 索引版本)` 到响应体的映射，TTL 30 到 60 秒，只缓存 top 1,000 个前缀就能覆盖 40.9% 的请求。索引版本必须进缓存键，否则蓝绿切换后用户会看到旧索引的建议，最长持续一个 TTL。

### 个性化会摧毁缓存

「根据用户历史调整建议顺序」听起来很合理，但缓存键从 4 维变成 4 维 + 用户，命中率立刻掉一个数量级。正确做法：

- **索引层只返回全局 top-20**，与用户无关；
- 应用层拿用户画像做**重排 + 注入 1 到 2 条个人化建议**，只对前 20 条动手；
- 这样全局缓存照旧生效，个性化只在应用层花几毫秒。

### 几个必须提的工程细节

- **黑名单在返回前过滤，不在建索引时过滤。** 涉黄涉政词的名单每天都在变，如果建索引时就剔除，每次更新都要重建 10 亿条的索引；返回前过滤只需把 top-10 扩到 top-30 再筛，滤掉一半也还剩 15 条。
- **归一化必须在索引入口和查询入口用同一份代码。** 大小写、前后空格、全半角、繁简、连字符。两边不一致的表现是「明明有这个查询，就是不命中」，实测这类 bug 会吃掉 5% 到 10% 的命中率，而且极难发现，因为日志里看不出异常。
- **拼写纠错不要放在索引路径上。** 编辑距离计算是毫秒级，会吃掉整个预算；放在「空结果兜底」分支里，只对没命中的请求付出代价。
- **空结果不要返回空。** 前端会闪一下空白；返回「最接近的前缀」（共享前缀最长的那个）加全局热词兜底，体验差距巨大。

## 八、追问清单

**追问一：索引怎么保证和线上数据一致？**
不需要一致。索引是「几分钟前的快照」，产品上完全可接受（没有用户会因为补全里没有 30 秒前的新词而投诉）。这条要主动说，否则面试官会以为你不知道索引是最终一致的。

**追问二：某个分片挂了怎么办？**
短前缀表每个节点都有副本，短前缀请求不受影响（95%）。长尾分片按 3 副本部署，读请求打主副本、失败重试到副本；因为索引只读且带版本号，副本之间没有一致性问题。

**追问三：怎么灰度新索引？**
按流量比例切版本指针：1% → 10% → 50% → 100%，每级观察「点击率」和「空结果率」。索引质量 bug 的典型表现是空结果率上升或 CTR 下降，而不是报错——所以这两个指标必须在新旧版本上分别打点。

**追问四：为什么不做成「一个请求查所有前缀」的批量接口？**
可以，而且值得。用户在输入「面试」的过程中会产生 4 次请求，如果客户端把每次按键都发出去，QPS 直接乘 4。实践做法是客户端防抖 250ms + 取消在途请求（AbortController），这一个改动就能砍掉 60% 的 QPS。

**追问五：前缀表 36 MiB 每节点一份，200 个节点就是 7.2GB，值得吗？**
值得，因为它是纯内存、只读、可压缩（id 用 4 字节、score 用 2 字节量化后从 36 MiB 压到 27 MiB），而且换来的是 95% 的请求不出边缘。相比之下，让这 166k QPS 全部打到中心，光网络和排队成本就远超 7.2GB 内存。

**追问六：为什么 ID 用 4 字节？**
10 亿条查询正好需要 30 位，4 字节能装（上限 42.9 亿），留了 4 倍余量。用 8 字节会让 top-k 表直接翻倍到 72 MiB，牺牲了「整份下发到边缘」这个最重要的性质。

**追问七：怎么衡量这套系统好不好？**
四个指标：① 空结果率（无建议的请求占比）；② 建议点击率（CTR）；③ 首字节延迟 p99；④ 索引新鲜度（新词进入索引的延迟）。前三者是架构指标，第四个是数据管道指标，混在一起看会误判。

**追问八：如果要求跨地域低延迟呢？**
每个大区各自一份完整索引（36 MiB 短前缀表 + 全量长尾分片），数据管道从中心 Kafka 复制。索引 10 亿条、四分钟重建，跨地域复制的是构建产物（快照文件），不是原始数据；单次全量约几百 GB，走专线或对象存储分发，每天一次足够。

## 九、收尾

这道题的三条线：

- **空间线**：短前缀的数量由字符集和长度决定，与语料规模无关。475,254 这个上界一旦算出来，36 MiB 的结论就锁死了，整套架构跟着它走。
- **分片线**：前缀查询是范围查询，分片必须切在前缀上；切点按流量等频，粒度要比热点细一个数量级以上；短前缀不要靠分片解决，靠复制。
- **更新线**：索引只读、四分钟全量重建、指针原子切换。任何「增量更新」的复杂度都花在了 5% 的收益上。

如果面试官继续往下压，还能往这几个方向走：**多语言与混合字符集**（中英混排的前缀边界在哪、拼音补全怎么建索引）、**语义补全**（向量召回替代前缀匹配时的延迟与召回权衡）、**对抗性输入**（恶意构造超长前缀或高频刷词，怎么做防刷与配额）、以及**索引压缩**（FST、succinct trie、前端编码，能把 36 MiB 再压一半）。

**文末附：本文所有数字的复现脚本（Python 3.11，单核，无第三方依赖）**

```python
import random, bisect, heapq, hashlib, math, time
from collections import Counter

rnd = random.Random(20261119)

# 1) 造语料：4000 词表，1-3 词组成一条查询，首字母带热点偏置
def make_vocab(n=4000):
    r = random.Random(7); w = set()
    while len(w) < n:
        L = r.randint(3, 8)
        w.add(''.join(r.choice('abcdefghijklmnopqrstuvwxyz') for _ in range(L)))
    return sorted(w)

V = make_vocab(); HOT = 'aceinst'
LW = [1.0 / (i + 1) ** 0.7 for i in range(len(V))]
qs = set()
while len(qs) < 150000:
    k = rnd.choice([1, 1, 2, 2, 2, 3])
    q = ' '.join(V[rnd.choices(range(len(V)), weights=LW, k=1)[0]] for _ in range(k))
    if q[0] not in HOT and rnd.random() < 0.5:
        q = rnd.choice(HOT) + q
    qs.add(q)
queries = sorted(qs); N = len(queries)
freq = [max(1, int(rnd.paretovariate(1.15))) for _ in range(N)]

def rng(p):
    return bisect.bisect_left(queries, p), bisect.bisect_left(queries, p + '\U0010ffff')

# 2) 唯一前缀数
for l in range(1, 5):
    print(l, len({q[:l] for q in queries if len(q) >= l}))

# 3) 构建 top-10 表并计时
t0 = time.perf_counter()
table = {}
for l in range(1, 5):
    for p in {q[:l] for q in queries if len(q) >= l}:
        lo, hi = rng(p)
        table[p] = heapq.nlargest(10, range(lo, hi), key=lambda j: (freq[j], -j))
print('build_s', round(time.perf_counter() - t0, 2), 'prefixes', len(table))

# 4) 查询延迟：查表 vs 二分加堆
pr = [p for p in table if len(p) == 4]
t0 = time.perf_counter()
for i in range(100000):
    table[pr[i % len(pr)]]
print('lookup_us', round((time.perf_counter() - t0) / 100000 * 1e6, 2))

# 5) 扇出尾延迟放大
def tail(fanout, sigma, mean=3.0, n=200000):
    lat = sorted(max(rnd.lognormvariate(math.log(mean) - sigma ** 2 / 2, sigma)
                     for _ in range(fanout)) for _ in range(n))
    return lat[n // 2], lat[int(n * 0.99)]

sigma = (math.log(8.0) - math.log(3.0)) / 2.326
for f in (1, 4, 16, 64):
    print(f, tail(f, sigma))
```

实测输出（关键几行）：

```

2 675
3 6309
4 19772
build_s 0.99 prefixes 26782
lookup_us 0.7
1 (2.75, 7.35)
4 (4.18, 9.00)
16 (5.68, 10.75)
64 (7.24, 12.57)
```
