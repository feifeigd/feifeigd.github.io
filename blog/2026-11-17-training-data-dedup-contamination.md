模型能力的上限由数据决定，这句话已经是共识；但落地时真正卡住后端工程师的不是"理念"，而是三个很硬的问题：**去重的参数怎么定**（拍脑袋的 b/r 会把 3% 改写的近重复全漏掉）、**污染检测为什么经常抓不到**（13-gram 只认逐字连续匹配）、**质量阈值凭什么定在 0.7 而不是 0.5**（拍出来的阈值会把长尾领域整片砍掉）。

这篇文章用一个可运行的 MinHash + LSH 实现和本地实测数据，把这三道关的账算清楚。

## 一、重复数据到底在偷什么

重复的来源比想象中脏：同一 URL 被 Crawl 多次、镜像站与转载、模板化页面的导航栏、GitHub fork 里的同一份 LICENSE 头、论坛签档。它们进入语料后偷走三样东西。

**第一是记忆化（memorization）。** 一条样本出现 n 次，梯度就朝它走了 n 次。Lee 等人 2021 年的工作用后缀数组做 50-token 粒度的子串去重，结论很直接：去重后的模型逐字复述训练样本的比例显著下降，同时在同等训练预算下评测表现不降反升——因为算力不再浪费在"背原文"上。

**第二是评测泄漏。** 训练集里混进 benchmark 原文，分数立刻虚高，而且是静默的虚高：你不会收到任何报错，只会在上线后发现模型在真实分布上差一大截。

**第三是纯算力浪费。** 这条最容易算：如果清洗后语料有 30% 是重复，等价于 30% 的 GPU 小时在重复同一批 token。以 1B 参数模型、100B token 训练为例，6·N·D ≈ 6×10⁹×10¹¹ = 6×10²⁰ FLOPs，砍掉 30% 重复 token 就是砍掉约 1.8×10²⁰ FLOPs 的等价开销。

## 二、MinHash + LSH：参数不是玄学，是 S 曲线

MinHash 的核心性质只有一个：随机置换下两个集合的最小哈希相同，其概率等于集合 Jaccard 相似度。取 k 个独立置换，**匹配分量比例就是 J 的无偏估计**，标准差 σ = √(s(1−s)/k)。k=128、s=0.75 时 σ≈0.038，也就是 128 个 permutation 只能把估计误差压到 4 个百分点以内——这个数字后面会和实测对上。

LSH 把 k 个分量切成 b 个 band、每 band r 行（k=b·r），任一 band 完全相同即判为候选对：

```
P(s) = 1 − (1 − s^r)^b          阈值 ≈ (1/b)^(1/r)
```

直接代数字：

```python
def threshold(b, r):
    return (1 / b) ** (1 / r)

for b, r in [(16, 8), (8, 16), (32, 4), (64, 2)]:
    print(f"b={b:>2} r={r:>2} k={b*r}  s*={threshold(b, r):.3f}")
# b=16 r= 8 k=128  s*=0.707
# b= 8 r=16 k=128  s*=0.878
# b=32 r= 4 k=128  s*=0.420
# b=64 r= 2 k=128  s*=0.177
```

注意这四个配置的 k 全是 128（同样的内存、同样的哈希开销），区别只在切法，阈值却从 0.18 一路到 0.88。**只有 b/r 决定召回边界，k 只决定估计精度。**

完整实现不到 60 行（生产建议直接用 datasketch 或自己写 numpy 版，逻辑一致）：

```python
import hashlib
M = (1 << 61) - 1

def h64(s):
    return int.from_bytes(hashlib.blake2b(s.encode(), digest_size=8).digest(), "big")

def shingles(tokens, k=5):
    return [" ".join(tokens[i:i+k]) for i in range(len(tokens)-k+1)]

def minhash(hashes, perms):
    # 单族 h_i(h) = (a*h + b) mod M，等价于 k 个置换，成本只有一次乘法
    return [min((a * h + b) % M for h in hashes) for a, b in perms]

def lsh_keys(sig, bands, rows):
    return [hash(tuple(sig[i*rows:(i+1)*rows])) for i in range(bands)]
```

### 实测：0.75 相似度的近重复，有一半配置会全漏

造 750 篇文档（240 token/篇，236 个 5-shingle），混入 60 对精确重复 + 90 对"3% token 改写"的近重复，跑四组参数（纯 Python 单核，7 分钟内全部跑完）：

| 配置 | 阈值 s* | 候选对 | 精确重复召回 | 近重复召回 | 误报 |
|---|---|---|---|---|---|
| b=16 r=8 | 0.707 | 136 | 60/60 | 76 | 0 |
| b=32 r=4 | 0.420 | 156 | 60/60 | 96 | 0 |
| b=8 r=16 | 0.878 | 75 | 60/60 | **15/90** | 0 |
| b=64 r=2 | 0.177 | 156 | 60/60 | 96 | 0 |

（近重复对数超过 90 是因为改写样本同时命中原文和原文的精确副本。）

同一批数据上测真实相似度与检出率（每档 30 对）：

| 编辑比例 | 真实 Jaccard | b=16 r=8 | b=8 r=16 | b=32 r=4 | 签名估计 MAE |
|---|---|---|---|---|---|
| 1% | 0.920 | 30/30 | 27/30 | 30/30 | 0.018 |
| 3% | 0.758 | 23/30 | **2/30** | 30/30 | 0.035 |
| 5% | 0.630 | 12/30 | 0/30 | 29/30 | 0.041 |

三件事值得记住：

1. **3% 的 token 改动就吃掉 24% 的 5-gram Jaccard**（0.92→0.76）。5-shingle 窗口里只要有一个 token 变了这片就不匹配，"看起来只改了一点"在 shingle 空间里是很重的伤。
2. **b=8 r=16 在 0.76 相似度上只召回 2/30**。这不是 bug，S 曲线阈值 0.878 就在那里。凡是"调了参数召回就崩"的事故，基本都是阈值压到了数据相似度之上。
3. **签名估计误差 1.8~4.1 个百分点，和理论 σ 完全吻合**。所以判重时不要拿 0.5 当硬边界去切——边界附近本来就有 ±4 点的噪声，正确做法是留缓冲带（比如 0.7 以上直接删、0.6~0.7 进人工/二次判）。

## 三、精确去重也得做，以及"去重雪崩"

MinHash 抓的是"集合级"相似，对**局部复制**（一篇文章里 300 token 抄自另一篇）不敏感：整体 Jaccard 只有 0.1，阈值再低也压不进去。这正是 suffix array 子串去重的价值——直接删掉长度 ≥ 50 token 的重复片段。代价是内存：10B token 的后缀数组在几十 GB 量级，且构建要 O(N log N)。

工程上的折中路线：

1. 先用**段落级精确哈希**（200-token 窗口 + sha1）找出高频桶；
2. 只对桶内文档跑后缀数组/滚动哈希；
3. 长度阈值设 50 token，短于此的重复多半是模板，交给启发式规则处理。

另一个坑是**语义去重雪崩**。用 embedding + kNN 建图、再取连通分量，看起来最"高级"，实际会把整个语料塌缩成一个巨型簇：A 和 B 相似、B 和 C 相似，但 A 和 C 早已不是同一篇文档，连通分量却把三者合并，最终一个"宇宙簇"吞掉半个数据集。修法只有两个，都反直觉：

- **贪心一遍过**：按质量分降序扫描，遇到与已保留样本超过阈值就丢，不做传递闭包；
- **限簇容量**：每簇最多保留 m 条（m 取 5~20），超出部分按质量分排序丢弃。

### 一个语义去重的正确判据

```python
def greedy_dedup(docs, emb, thr=0.92, max_cluster=10):
    """docs 已按质量分降序；docs: list[(id, text)]，emb: (n, d) 归一化向量"""
    kept, cluster_size = [], {}
    for i, (doc_id, _) in enumerate(docs):
        sims = emb[i] @ emb[[j for j, _ in kept]].T if kept else []
        if len(sims) and sims.max() > thr:
            j = int(sims.argmax())
            if cluster_size[j] >= max_cluster:   # 簇满，仍要丢
                continue
            cluster_size[j] += 1
            continue
        kept.append((i, doc_id))
        cluster_size[len(kept) - 1] = 1
    return [doc_id for _, doc_id in kept]
```

## 四、污染检测：13-gram 能抓什么、抓不到什么

GPT-3 的技术报告用的是 13-gram 重叠，这套方法至今仍是基线。**关键是把索引建在 benchmark 一侧、扫语料一侧**，而不是反过来——benchmark 通常只有几万到几百万 token，索引常驻内存毫无压力。

```python
def ngrams(tokens, n=13):
    return {" ".join(tokens[i:i+n]) for i in range(len(tokens)-n+1)}

bench_idx = set()
for ex in benchmark:                       # benchmark 侧建索引，规模小
    bench_idx |= ngrams(ex.tokens)

def contaminated(tokens, min_hit=1):
    hit = len(ngrams(tokens) & bench_idx)
    return hit >= min_hit, hit
```

本地实测：200 篇训练文档里埋 2 篇污染样本（分别从第 0 和第 40 个 token 开始复制 benchmark 的 150 token），13-gram 扫描把 2 篇全部标出，共享 13-gram 数 276 个（每篇 138 个）；200 篇扫描耗时 0.31s，折合 **561 Mtok/h/核**，纯 Python 的 set 交集，成本可以忽略。

但它的盲区很致命：

- **任何一处编辑就断链**。13 个连续 token 全等才算命中，中间插一个逗号、换个变量名、加一句引导语，就漏了。代码类 benchmark 尤其惨——变量重命名 + 格式化就能绕过。
- **改写/翻译完全无效**。中文 benchmark 被翻译成英文进入语料，13-gram 命中数为 0。
- **格式转换漏检**。LaTeX 公式转 markdown、HTML 转纯文本，token 序列变了但语义没变。

补强手段按成本递增：perplexity 法（对 benchmark 训 n-gram LM，语料片段 ppl 低于阈值即疑似）、embedding 粗筛（召回改写/翻译）、人工抽检。实务上建议**双报**：一份全量分数、一份"剔除可疑文档后重训"的 clean 分数。两者差距就是你的真实泛化能力的置信区间。

## 五、质量过滤：阈值是反解出来的，不是拍出来的

启发式规则负责砍掉明显的垃圾，Gopher/MassiveText 那一套至今好用，落地时用区间而不是单点：

- 词数 50~100k（文档级），平均词长 3~10 字符；
- 以 `#` 开头的行占比不超过 10%，以 `...` 结尾的行占比不超过 30%；
- 含 `javascript` 的行占比不超过 5%，黑名单词命中即丢；
- 重复行占比、重复 n-gram 占比超阈值即丢（这本身也是轻量去重）。

分类器打分（fastText / MiniLM 蒸馏一个"像不像高质量文本"的判别器）更有效，但**阈值必须反解**：先在小规模人工标注集上画 precision-recall 曲线，再按目标保留率反查阈值。拍 0.5 的典型后果是把法律、数学证明、非英语长尾整片砍掉——这些领域在通用质量分类器上分数天然偏低，模型随之在数学和代码上退化。

按领域分桶定阈值是必须的：同一个 0.85，在网页文本上保留 40%，在代码上可能只剩 8%。

## 六、流水线账本：内存、分片、幂等

**内存。** 128 个 permutation × 4 字节 = 512 B/文档。10⁸ 篇文档就是 51 GB 签名，装不进单机内存。做法是**按 band key 的前缀分片落盘**（RocksDB / 分片 parquet），流式两遍：pass 1 建桶写索引，pass 2 回查标记 `keep / dup_of`。桶的 key 必须是**稳定哈希**（sha1 取前 8 字节），绝不能用 Python 内建 `hash()`——进程重启带随机化种子，索引直接失效，重跑会对不上。

**吞吐（本地实测，单核）。**

| 阶段 | 实现 | 吞吐 |
|---|---|---|
| 5-shingle + 128 perms MinHash | 纯 Python | 35 docs/s ≈ 8.3 Ktok/s ≈ 30 Mtok/h |
| 同上 | numpy 广播 (128×236 uint64) | 81 docs/s ≈ 70 Mtok/h |
| 13-gram 交集扫描 | 纯 Python set | 561 Mtok/h |

numpy 只快了 2.3 倍，因为瓶颈不在算术而在**临时数组分配**（实测 sys 时间 21s > user 5.5s，典型的内存带宽受限）。真正有效的手段是减少重复 shingle 的哈希次数（先把 shingle 去重再哈希），以及按 10⁷ 篇为单位分片并行。按 70 Mtok/h/核算，10B token 的 MinHash 阶段在 64 核上约 2 小时量级，和后续的 IO、embedding 去重相比并不构成瓶颈。

**幂等与可重放。** 每个 shard 输出 `(doc_id, cluster_id, keep)`，同一输入必须产出同一结果；簇代表的选取规则要确定性（按 `(质量分, doc_id)` 排序取最小），否则两次跑出的"保留集"不同，训练不可复现——这类问题在排查 loss 曲线异常时极难定位。

## 七、踩坑清单

1. **shingle 哈希是热路径，先缓存再算。** 我第一版对每个 shingle 现算 blake2b、套 128 层 Python 循环，750 篇文档跑了 9 分钟还没完，直接超时被杀；改成 shingle→哈希缓存 + 单次遍历求 min 后降到 109 秒。规范化之后还要再降一次：shingle 集合先去重，重复 shingle 不重复哈希。
2. **默认参数会漏近重复。** datasketch 默认 128 perms/16 bands，对 3% 改写的近重复只召回 23/30；要抓改写就得把 r 压到 4（b=32），代价是候选对变多、后处理变重。
3. **别用不稳定的哈希做桶 key。** Python `hash()` 有随机种子，重启后索引不可复用；要用 blake2b/sha1 截断。
4. **去重后语料变小，训练步数要重算。** 按原始 token 预算跑，等价于多跑几个 epoch，反而过拟合；去重收益被这一步抵消掉是常见事故。
5. **污染索引要建在 benchmark 一侧。** 反过来把 10B token 的 13-gram 全塞进 set，内存直接爆掉，而且每次都白建一遍。
6. **语义去重不要用连通分量。** 传递闭包会把语料塌缩成一个巨型簇，用贪心一遍过或限簇容量。
7. **去重的产物要留样本。** 每批随机落 200 条"被判为重复"的样本到对象存储，事后能回答"为什么这篇文章被删了"——没有这个，数据事故只能靠猜。

## 八、收尾：三个可执行的默认值

- 近重复去重：5-shingle（词级）、128 perms、**b=32 r=4**（阈值 0.42），判重线 0.7 直接删、0.6~0.7 进二次判；
- 子串去重：段落级精确哈希粗筛 + 后缀数组，长度阈值 50 token；
- 污染检测：benchmark 侧 13-gram 索引 + embedding 粗筛，结果**双报**（全量 / clean）；
- 质量过滤：启发式区间规则打底，分类器按领域分桶反解阈值，不拍 0.5。

数据工程没有漂亮的 benchmark 可引用，只有一堆必须自己测的常数。上面这张表就是我能给出的、可复现的那部分——换语料、换 shingle 粒度，数字会变，但那三条 S 曲线的性质不会变：**阈值决定召回，k 决定精度，别把两者搞混。**
