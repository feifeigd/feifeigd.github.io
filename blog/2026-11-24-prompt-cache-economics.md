线上一个 Agent 服务的成本核算里出现过一组很难解释的数：缓存命中率稳定在 85% 上下，输入 token 的账单却只降了 73%。团队一开始以为是厂商计价不对，后来发现两件事都没错——命中率是 token 口径，账单是「读 0.1 倍、写 1.25 倍、普通 1 倍」三种价格混在一起，85% 的命中本来就只能换来这个折扣。

更贵的一次事故是反向的：某个版本把「今天日期 + 请求 ID」拼到 system prompt 第一行，为了「方便排查」。功能没问题，缓存命中率掉到 0.18%，输入账单涨到基线的 124.8%。缓存没坏，是前缀坏了。

这篇把这件事算成账：先把计费规则压成公式，再用一个 5 段式前缀模型算出两种真实流量形态下的分段命中率，最后列出把缓存打穿的写法。文中所有数字来自文末脚本的实际输出，价格用比率归一化（普通输入按 3 美元每百万 token），复算时换你自己的价格表即可，结论的形状不变。

## 一、把规则压成可以算的东西

三家的规则细节不同，但对后端的接口就三个数字：写一次缓存多少钱、读一次多少钱、没命中多少钱。加上两个约束：**前缀必须从头连续命中**，**有 TTL**。

| 形态 | 写入 | 读取 | 普通 | 关键约束 |
|---|---|---|---|---|
| 5 分钟显式缓存 | 1.25 倍 | 0.1 倍 | 1 倍 | 需在 content 里标断点，命中即续期 |
| 1 小时显式缓存 | 2.0 倍 | 0.1 倍 | 1 倍 | 同样的读写比率，写贵一倍 |
| 自动前缀缓存 | 1 倍 | 0.5 倍 | 1 倍 | 无写溢价，最小前缀长度约 1024 token |
| 隐式前缀缓存 | 1 倍 | 0.25 倍 | 1 倍 | 折扣最深，但不可控、不保证命中 |

前缀语义是这件事的根：缓存 key 是**从第一个 token 开始逐块哈希**得到的链，块粒度约 128 token，最小可缓存长度约 1024 token。这意味着第 1 个 token 变了，第 8000 个 token 的缓存也失效——不是「相似度匹配」，是纯字符串前缀。所有「我明明没改 prompt」的困惑，最后都落在这一条上。

## 二、盈亏平衡：写缓存什么时候是亏的

写缓存有溢价，所以「命中率」本身不是目标函数，正确的问题是：一个前缀在被写之后，要被**再读几次**才回本。

设写入溢价 w（1.25 或 2.0）、读取折扣 r（0.1），单位 token 的账是：不缓存时每次付 1；缓存时第 1 次付 w、之后每次付 r。回本条件 w + n·r 小于或等于 (1 + n)，即：

```
n >= (w - 1) / (1 - r)
```

代入四组比率：

| 形态 | 回本所需额外读取次数 |
|---|---|
| 写 1.25 / 读 0.10 | 0.278 |
| 写 2.00 / 读 0.10 | 1.111 |
| 写 1.00 / 读 0.50 | 0（自动缓存永远不亏） |
| 写 1.00 / 读 0.25 | 0（同上） |

两个结论直接可用。第一，5 分钟缓存几乎无脑赚：同一个前缀只要在第 2 次请求时还在 TTL 内，就回本了，多读一个字都是净赚。第二，**1 小时缓存必须先证明「1 小时内至少还有两次使用」**——0.278 变成 1.111 不是小差别，它是「会被第二次用到」和「会被第三次用到」的区别。给一个每天只跑一次的批处理任务开 1 小时缓存，是纯亏 100%。

## 三、按段算账：命中率必须分段看

把 Agent 的 prompt 拆成五段，每段的复用范围完全不同：

| 段 | 典型大小 | 复用范围 | 变化频率 |
|---|---|---|---|
| tools | 6144 | 全租户 | 部署时 |
| policy | 2048 | 单租户 | 版本发布 |
| userctx | 3072 | 单用户单会话 | 每次会话 |
| hist | 每轮 256 | 单会话 | 追加 |
| msg | 128 | 无 | 每轮 |

模拟器的核心就是这三行：把每段展开成块，逐块哈希成前缀链，然后从第 0 块开始走，遇到「链不存在」或「已过 TTL」就停。

```python
def chain_keys(blocks):
    keys, prev = [], 0
    for b in blocks:
        prev = hash((prev, b))     # 前缀链：位置 0 变了，后面全废
        keys.append(prev)
    return keys

def hit_blocks(keys, cache, now, ttl):
    hit = 0
    for k in keys:
        ts = cache.get(k)
        if ts is None or not (0.0 <= now - ts <= ttl):
            break                  # 前缀必须连续命中，断了就停
        hit += 1
    return hit
```

跑 150 个用户、每人 5 个会话、每会话 8 轮、轮间隔 15 秒、TTL 5 分钟，得到：

| 场景 | 总输入 | 命中率 | 相对无缓存成本 |
|---|---|---|---|
| A 不开缓存 | 73.73M | 0% | 100%（$221.18） |
| B 前缀顶部带时间戳 | 74.50M | 0.18% | **124.8%（$278.91）** |
| C 静态在前（正确写法） | 73.73M | 85.68% | 26.5%（$58.55） |
| E TTL 设成 10 秒（短于轮间隔） | 73.73M | 0% | **125.0%（$276.48）** |
| F TTL 1 小时，写 1.25 倍 | 73.73M | 85.72% | 26.4%（$58.44） |
| G TTL 1 小时，写 2.0 倍 | 73.73M | 85.72% | **37.1%（$82.12）** |

分段拆开看，才看得懂 85.68% 是怎么来的：

| 段 | 占输入 | 命中 | 写入 |
|---|---|---|---|
| tools | 36.86M（50%） | 87.50% | 12.50% |
| policy | 12.29M | 87.50% | 12.50% |
| userctx | 18.43M | 87.50% | 12.50% |
| hist | 5.38M | 75.00% | 25.00% |
| msg | 0.77M | 0% | 100% |

三个读数。**工具 schema 占了全部输入的一半**——这和「30 个工具就是 8k 固定税」是同一件事，它在缓存下几乎免费，在不开缓存时是最大单项成本。**msg 永远 0% 命中是对的**，动态尾巴本来就不该缓存，看到这一段的命中率低不用去修。**hist 只有 75%**，因为每轮新增的那一块必然 miss，8 轮里 2 块新增、6 块复用，和 75% 对得上——这是缓存的理论上限，不是 bug。

## 四、三类把缓存打穿的写法

**第一类：易变字段进了前缀。** 时间戳、请求 ID、trace ID、「您好，张先生」、locale、`user_id`，只要落在第一个 1024 token 里，命中率就是 0。上面的场景 B 就是这个：成本 124.8%，比不开缓存还贵四分之一。修法不是「记得别写」，而是让它结构上不可能——所有易变内容只允许出现在 messages 的最后一条。

```python
import json

def stable(obj):
    return json.dumps(obj, sort_keys=True, separators=(",", ":"), ensure_ascii=False)

def build_prompt(tenant, tool_specs, history, user_text):
    tools = sorted(tool_specs, key=lambda t: t["name"])   # 顺序必须确定
    static = stable({"policy": tenant["policy"], "tools": tools})
    body = {
        "system": [{"type": "text", "text": static,
                    "cache_control": {"type": "ephemeral"}}],
        "messages": [],
    }
    # 断点打在历史末尾，这样下一轮只需写新增的那一块
    for i, turn in enumerate(history):
        block = {"role": turn["role"], "content": turn["content"]}
        if i == len(history) - 1:
            body["messages"].append({"role": turn["role"], "content": [
                {"type": "text", "text": turn["content"],
                 "cache_control": {"type": "ephemeral"}}]})
        else:
            body["messages"].append(block)
    body["messages"].append({"role": "user", "content": user_text})
    return body
```

**第二类：动态内容放到了静态内容前面。** 检索结果、用户画像、租户配置如果排在 tools 前面，后面那 8k 工具就永远进不了缓存。单轮 API 流量下这个错误的代价是断崖式的：同样参数、只把顺序换成 userctx 在前，命中率从 71.80% 掉到 0%，成本从基线的 42.4% 变成 125.0%（$43.50 变成 $128.16）。

这里有个陷阱值得单独说：**在 Agent 流量下这个错误几乎看不见**。同一会话里 userctx 不变，8 轮里的 7 轮照样全命中，两种布局都在 85.7% 上下（85.68% 与 85.72%）——我第一版模拟器就是这么被骗过去的。要验证布局对不对，必须用单轮流量（或首轮命中率）压测，别拿多轮聚合命中率当验收标准。

**第三类：历史被重写。** 上下文压缩、滚动摘要、把前 5 轮改写成一段「之前讨论了……」、给早先的 assistant 消息补上新的 metadata——任何对已有前缀的修改都会让后续全量失效。历史必须只追加。要压缩就往**新的位置**压缩：保留原始前缀，在它后面追加一条摘要消息，把断点移到摘要之后。代价是一个额外的缓存断点，收益是前 8k 工具加历史仍然全命中。

顺带一个隐蔽的第四类：**工具列表顺序不稳定**。多 MCP server 并发注册、从 dict 或 set 遍历生成 schema、不同实例的插件加载顺序不同，会产出「内容相同、顺序不同」的两份前缀，等于两个隔离的缓存。上线前对生成的 payload 做一次哈希，跨实例比对，比任何 review 都有效。

## 五、TTL 悬崖：长工具调用会把 5 分钟打穿

TTL 不是「大概 5 分钟」，它是一个硬边界：超过边界，前缀回到 0。把轮间隔从 15 秒推到 480 秒（一次慢工具调用、一次人工审批、一次异步任务轮询），账立刻变形：

| 轮间隔 | TTL | 命中率 | 相对无缓存成本 |
|---|---|---|---|
| 15 秒 | 5 分钟 | 85.68% | 26.5% |
| 120 秒 | 5 分钟 | 85.68% | 26.5% |
| 480 秒 | 5 分钟 | **0%** | **125.0%（$276.48）** |
| 480 秒 | 1 小时 | 85.68% | 26.5% |
| 480 秒 | 1 小时（写 2 倍） | 85.68% | 37.2%（$82.31） |

40 秒到 120 秒之间是「安全区」，480 秒是「归零」——中间那段不是线性衰减，是断崖，因为整条前缀一起过期。所以判断标准不是「我的请求平均多快」，而是「**最长的那条链有多长**」：Agent 里一次工具调用跑 6 分钟，整个会话的缓存就从一个变成两个。

1 小时缓存看起来是解药，37.2% 仍然远好于 125%，但它要求你算清楚复用之下的账。上面 G 组是同一份流量、同样 85.72% 命中率，只把写入溢价从 1.25 换成 2.0，成本从 26.4% 变成 37.1%——多出来的 10 个百分点全是写给「等会儿才会用」的前缀。**什么时候值得**：会话跨度超过 5 分钟、且会话内还有多轮（人工审批、长任务、代码改完再跑一次检查）。**什么时候不值得**：一次性的长文档分析，写完就再也不读。

## 六、可观测与计费：两个指标，一个不能省

从 usage 里把三项拆出来，是这件事的最小基础设施：

```python
def cache_stats(usage):
    r = usage.get("cache_read_input_tokens", 0)          # 命中
    w = usage.get("cache_creation_input_tokens", 0)      # 写入
    p = usage.get("input_tokens", 0)                     # 未缓存
    tot = r + w + p
    return {"read": r, "write": w, "plain": p,
            "hit_rate": r / tot if tot else 0.0,
            "cost_units": p * 1.0 + w * 1.25 + r * 0.1}   # 以普通输入为 1
```

两个指标都要打点，缺一个就会得出错误结论：**只看 hit_rate**，会把「85% 命中、26.5% 成本」当成效率已经见顶；**只看 cost**，看不出成本下降是来自缓存还是来自流量结构变化。真正需要盯着的是分段的命中率——tools 段掉到 80% 以下说明有人往 schema 里塞了动态字段，hist 段掉到 60% 以下说明历史被重写了，userctx 段命中高但成本占比大说明检索内容不该走前缀。

计费侧有个容易错的点：三项必须分项入库。如果把 `cache_creation_input_tokens` 当普通输入算，毛利会少估；如果把 `cache_read_input_tokens` 当普通输入算，毛利会高估近 10 倍——读的价格是普通输入的十分之一，这个差额在百万级 token 的量上就是真金白银。上游账单和你的账单对不上时，先查这三项是不是被合并成了一项。

## 七、自托管是另一笔账

同样的前缀缓存，自托管时不算钱：GPU 已经租了，命中与否不影响账单，省的是 prefill 的算力和 TTFT。这时候「命中率」进的是 p99 曲线，不是成本表。这类账我在 [llama-server 的 prompt cache 台账](/blog/2026/11/16/llama-server-prompt-cache-ledger) 里算过，量纲完全不同——那边关心的是显存里能放多少条前缀、LRU 淘汰和 KV 碎片，这边关心的是断点打在哪、TTL 选多长、写入溢价回不回本。别把两套指标混在一个仪表盘里。

## 结论

三件事，按投入产出排序：

1. **静态在前、动态在后。** 这不是最佳实践，是缓存的物理约束。验收方式是用单轮流量（或首轮命中率）跑一遍，多轮聚合命中率会把这个错误完全掩盖。
2. **5 分钟是默认值，1 小时要证明。** 回本线是 0.278 次和 1.111 次额外读取——前者几乎必赚，后者要求「1 小时内至少再用两次」。挂在 5 分钟缓存上的长工具调用，只有两条路：改用 1 小时缓存，或者接受 125% 的成本。
3. **看每请求成本和分段命中率，不看总命中率。** 85.68% 的聚合命中率下面，藏着 87.5% 的工具段、75% 的历史段和 0% 的用户消息段，它们的优化手段完全不同。
