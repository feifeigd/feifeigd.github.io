## 一、题目与考点拆解

面试官的原话大概是：

> 我们有个业务：用户下单 30 分钟未支付要自动关单，会员到期前一天要发续费提醒，还有一批运营配置的定时推送。现在每天大概有一百万条这样的延迟任务。你设计一个调度系统——要求触发误差在秒级，机器挂掉任务不能丢，集群能水平扩容，同一个任务不能被执行两次。为什么不用数据库轮询扫表？如果量再涨十倍你怎么办？

这一题真正考六层，缺一层都答不透：

1. **容量建模**：先把「百万级」这个词拆成均值和峰值，算出真实的 TPS 与内存占用，而不是背架构图。
2. **存储与索引的物理成本**：为什么「按时间排序取前 N 条」这个动作在 MySQL 上有写放大，天花板在哪。
3. **定时器的数据结构**：时间轮为什么是 O(1)，O(1) 换来了什么代价（精度、内存、单圈覆盖范围）。
4. **分布式下的原子性与可见性**：怎么保证「取出」这个动作不被两个实例同时做，worker 崩了手上的任务怎么回收。
5. **投递与执行的解耦**：调度器为什么不该执行业务代码，重试应该发生在哪一层。
6. **语义边界**：exactly-once 做不到，「已触发但业务失败」到底由谁负责。

下面按这个顺序走，每一步都给可运行的代码和算得出来的数字。

## 二、先把量算清楚：百万级压在哪个维度

大部分人听到「每天一百万」就开始画 MQ 了。先别急，算一下：

```
100 万 / 86400 秒 ≈ 11.6 TPS（均值）
```

11.6 TPS 是一个**用 MySQL 扫表也毫无压力**的量。所以如果只按均值设计，第二天上线就会被打爆——因为延迟任务的时间分布几乎从来不是均匀的。

真实的分布长这样：

| 场景 | 分布特征 | 峰值放大倍数 |
| --- | --- | --- |
| 订单超时关单 | 跟着下单曲线走，晚高峰集中 | 5 到 10 倍 |
| 会员到期提醒 | 运营统一配置「每天 9:00 发」 | 80% 挤在同一分钟 |
| 大促开始提醒 | 全部定在同一个时刻 | 100 到 1000 倍 |
| 重试退避任务 | 失败后 1s/5s/30s 集中回灌 | 跟着上游故障走 |

按「80 万条挤在整点前后 5 分钟」算：

```
80 万 / 300 秒 ≈ 2667 TPS（触发侧峰值）
```

如果 1000 万条里有 500 万定在同一分钟：

```
500 万 / 60 秒 ≈ 83000 TPS（触发侧峰值）
```

结论：**延迟任务的容量瓶颈永远在触发侧的瞬时 QPS，不在存储总量**。这也直接决定了后面所有方案的取舍——你要优化的不是「怎么存一亿条任务」，而是「怎么在一分钟内把 500 万条任务吐出去，而且不把下游打挂」。

顺带算一下内存。假设每个任务对象 64 字节（id 8 字节 + 触发时间 8 字节 + 引用与轮次字段约 32 字节 + 对象头 16 字节），纯内存调度：

| 待触发任务数 | 内存占用 | 可行性 |
| --- | --- | --- |
| 100 万 | 约 64 MB | 单机轻松 |
| 1000 万 | 约 640 MB | 单机勉强，GC 压力大 |
| 1 亿 | 约 6.4 GB | 单机不可行，必须分片 |

记住这三行数，后面讲时间轮的天花板时直接引用。

## 三、扫表方案：为什么十万级就开始崩

最朴素的做法，一张表加一个轮询线程：

```sql
-- 索引：(status, trigger_at)
SELECT id, biz_type, payload
FROM delayed_task
WHERE status = 'PENDING' AND trigger_at <= NOW()
ORDER BY trigger_at
LIMIT 500;
```

看起来完全正确：索引覆盖了过滤和排序，LIMIT 限制了批量。十万条待触发任务、每秒轮询一次，很多团队就这么上线了，然后在大促当天出事。

崩的原因有四个，而且会叠加：

**1. 无谓轮询的成本是固定的，不随任务数下降。**

不管有没有到期任务，每秒都要做一次索引范围扫描。以 `status` 等值条件加上 `trigger_at` 的范围条件，在复合索引上做一次范围扫描，即使结果为空，也要定位到范围起点、读索引页。单次成本约 0.2 到 0.5 毫秒（Buffer Pool 命中），每秒一次只占千分之一核。但如果为了精度把轮询间隔降到 100 毫秒，或者分片数开到 64（每片一个轮询线程），就是 640 次/秒的常驻扫描——这部分 CPU 是纯浪费，而且会一直占着 InnoDB 的 trx 资源。

**2. 命中即写，写放大才是真正的天花板。**

扫出来不能只看，还要改状态：

```sql
UPDATE delayed_task SET status = 'RUNNING', updated_at = NOW()
WHERE id IN (...);
```

每触发一条任务，就是一次 UPDATE：写 undo、写 redo、写 binlog、维护 `(status, trigger_at)` 二级索引（status 从 PENDING 变成 RUNNING，索引条目要删除再插入）。任务跑完还要再 UPDATE 一次，数据量大了还要 DELETE 或归档。

单实例 InnoDB 在 NVMe 上，简单 UPDATE 的稳态吞吐大约 5000 到 15000 TPS（取决于 `innodb_flush_log_at_trx_commit` 与 binlog sync 策略）。一条任务至少两次 UPDATE，也就是单实例最多撑 **2500 到 7500 任务/秒**。这还没算业务自己的读写。

所以扫表方案的真实天花板是：**数据库的 UPDATE 吞吐，也就是一万每秒量级**。十万条待触发任务没事，一百万条集中在几分钟内触发就必然打满。

**3. 主从延迟会把下游读打脏。**

每触发一条任务就写一次 binlog。峰值一万 TPS 的 UPDATE 全压到从库回放，从库延迟从毫秒级涨到秒级。业务侧如果还在读从库做「任务是否已执行」的判断，就会读到旧状态，重复投递。

**4. 行锁与热点。**

多实例并发扫同一段索引，如果不加 `FOR UPDATE SKIP LOCKED`（MySQL 8.0.1 起支持），两个实例会扫到同一批行，然后一个等锁、一个改完提交，最终两条都投递一次——重复执行。加上 `SKIP LOCKED` 能解决正确性：

```sql
SELECT id FROM delayed_task
WHERE status = 'PENDING' AND trigger_at <= NOW()
ORDER BY trigger_at
LIMIT 500
FOR UPDATE SKIP LOCKED;
```

但 `SKIP LOCKED` 只是把「不重复」做对了，吞吐和写放大一点没变，而且长事务持有行锁会让 purge 线程追不上，undo 空间膨胀。

**结论**：扫表方案不是「错」，它适合**低频、可容忍秒级到分钟级延迟、总量十万以下**的场景（比如每天几十条对账任务）。它的能力上限就是数据库写入能力，扩不上去，也不该硬扩。要往上走，就得把「排序 + 定时」这件事从磁盘搬到内存。

## 四、时间轮：O(1) 的代价是精度和内存

定时任务最直接的思路是优先队列（小顶堆）：插入 O(log n)，取最近的一个 O(1)。Java 的 `ScheduledThreadPoolExecutor` 就是 `DelayQueue` 加堆，适合几万个任务，几十万个也能跑。

堆的问题是**插入和删除都是 O(log n)**，而且每次取任务要做一次 sift-down。百万级任务、每秒几万次插入时，log n 约为 20，CPU 就开始明显抖动了。

时间轮（timing wheel）把它降到了 O(1)。核心结构就是一个环形数组，每个槽对应一个时间区间：

```
槽位索引 = (deadline / tickDuration) & mask
```

Netty 的 `HashedWheelTimer` 是最好读的实现：

```java
// wheelSize 必须是 2 的幂，mask = wheelSize - 1
// 默认 tickDuration = 100ms，wheelSize = 512 → 一圈 51.2 秒
int idx = (int) ((deadline / tickDuration) & mask);
HashedWheelBucket bucket = wheel[idx];
// 剩余圈数：任务落地时间还差几个整圈
long calculated = timeout.deadline / tickDuration;
long remainingRounds = (calculated - tick) / wheel.length;
timeout.remainingRounds = remainingRounds;
bucket.addTimeout(timeout);
```

每个 tick 只处理一个槽，把槽里 `remainingRounds` 归零的任务取出来执行，其余减一。所以：

- 插入 O(1)（算索引 + 挂链表）
- 每 tick 摊销 O(1)（只处理一个槽）
- 不需要排序，不依赖堆

代价有三个，而且每个都很致命：

**代价一：精度等于 tickDuration，而且槽内是无序链表。**

同一个槽里的任务到期时间不同，但会被一起处理。Netty 的做法是「全部取出来，逐个检查 deadline 是否真的到期，没到期的重新入轮」。也就是说，实际精度是 tick 粒度（100ms），而这个精度是**用提前唤醒换来的**——槽内任务可能被提前最多一个 tick 唤醒，然后校验、回炉。这一进一出，在高负载下就是 2 倍的调度开销。

要想精度到 1 秒，tick 就是 1 秒，那么所有触发时间落在同一秒内的任务会挤在一个槽里，秒级峰值 8 万条时，这个槽就是一条 8 万元的链表，必须一次遍历完。**这就是时间轮的第一个天花板：单槽容量等于峰值 QPS 乘以 tick。**

**代价二：单圈覆盖范围 = wheelSize 乘以 tickDuration。**

512 个槽、tick 100 毫秒，一圈只覆盖 51.2 秒。更远的任务靠 `remainingRounds` 多圈计数——逻辑上能覆盖任意时长，但**任务必须一直待在内存里**。30 天后的任务，要在这里躺 30 天的圈数：

```
30 * 86400 / 51.2 ≈ 50625 圈
```

每个 tick 都要遍历它所在的槽给 rounds 减一。虽然摊销仍是 O(1)，但这份内存要占 30 天。按第二节的账，一亿条任务就是 6.4 GB——单机放不下。

**代价三：全内存，进程重启即丢。**

时间轮是纯内存结构，kill 一下全没了。所以要持久化：要么每个任务落库（那又回到 IO 瓶颈），要么写 WAL（比如 Redis 的 AOF、RocketMQ 的 timerlog），重启时重放重建。

于是得到一条清晰的判据：

> **单层时间轮适合「单进程内、任务量在百万以内、覆盖时间窗在分钟到小时级、允许重启后重建」的定时器。** 拿它当分布式调度系统的核心存储，一定不够。

## 五、分层时间轮：用 509 个槽覆盖一年

既然单层轮的问题是「槽数要么覆盖不够、要么内存爆炸」，那就分层——像时钟的秒针、分针、时针一样，粗粒度轮只存索引，细粒度轮存真实任务。

设四层，每层槽数等于上一层的进制：

| 层级 | 槽数 | 单槽跨度 | 覆盖范围 | 精度 |
| --- | --- | --- | --- | --- |
| 秒轮 | 60 | 1 秒 | 60 秒 | 1 秒 |
| 分轮 | 60 | 1 分钟 | 60 分钟 | 1 分钟 |
| 时轮 | 24 | 1 小时 | 24 小时 | 1 小时 |
| 天轮 | 365 | 1 天 | 365 天 | 1 天 |

槽位总数 = 60 + 60 + 24 + 365 = **509 个槽，覆盖一整年，精度 1 秒**。对比单层轮要达到同样效果需要 3153 万个槽——这就是分层的价值。

任务插入时，选「能覆盖它到期时间的最粗一层」：

```python
LEVELS = [
    # (name, slot_count, tick_ms)
    ("second", 60, 1_000),
    ("minute", 60, 60_000),
    ("hour",   24, 3_600_000),
    ("day",    365, 86_400_000),
]

def insert(levels, task, now_ms):
    for i in range(len(levels) - 1, -1, -1):
        name, slots, tick = levels[i]
        if task.trigger_at - now_ms < slots * tick:
            idx = (task.trigger_at // tick) % slots
            levels[i][idx].append(task)
            return i
    raise ValueError("超出一年覆盖范围，需要新增年轮或降级为 cron")
```

推进逻辑：秒针走一格就处理秒轮对应槽；秒轮转满一圈，就把分轮下一格的槽整体降级搬到秒轮（重新按秒取模分布）；分轮转满一圈搬时轮，依次类推。

```python
def tick(levels, now_ms):
    # 1) 处理秒轮当前槽
    sec_idx = (now_ms // 1000) % 60
    due, levels[0][sec_idx] = levels[0][sec_idx], []
    for task in due:
        if task.trigger_at <= now_ms:
            dispatch(task)
        else:
            insert(levels, task, now_ms)     # 提前唤醒的回炉
    # 2) 进位：秒轮满一圈，搬分轮
    if sec_idx == 59:
        mi = (now_ms // 60_000) % 60
        cascade(levels, 1, 0, now_ms)        # 分轮 mi 槽 → 秒轮
    # 3) 小时、天同理
```

**关键设计点**：降级搬迁是把「粗粒度槽」里的任务按细粒度重新散列，所以搬一次是 O(该槽任务数)，摊销到每个 tick 上依然很小——因为只有进位那一刻才搬，而且搬的是「未来一分钟内要到期的任务」，数量受峰值 QPS 约束。

这套结构与 Kafka 内部的 `TimingWheel` 是同一思路（它用 20 个槽、每层放大 20 倍，7 层覆盖约 6 天）。RocketMQ 5.x 的定时消息、很多公司的自研调度中间件，内核都是它。

但要清楚它仍然解决不了分布式问题：**内存、单机、重启丢失**这三件事一个都没变。分层只是把「内存占用」从 O(时间跨度) 压到 O(任务数)，把「覆盖范围」拉长。真正的分布式持久化，还得靠外部存储。

## 六、Redis ZSet 分桶：分布式场景下的默认答案

把「按时间排序」搬到 Redis，最自然的就是有序集合：member 是 task_id，score 是触发时间戳。

```bash
# 写入
ZADD delay:queue 1763368800000 task:88231

# 取到期任务
ZRANGEBYSCORE delay:queue -inf 1763368800000 LIMIT 0 500
```

ZSet 底层是跳表加哈希表，`ZADD` 和 `ZRANGEBYSCORE` 都是 O(log N)，一亿条也就 27 层指针。听起来完美，但直接上单一大 key 有四个坑：

**坑一：单个 key 承载全量任务，内存与复制成本都在一个分片上。**

100 万条任务的 ZSet，估算内存：跳表每层节点约 32 到 48 字节（含 level 数组），哈希表 entry 约 24 字节，member 字符串（如果是 16 字节 id）约 32 字节——单条 100 字节上下，加上 dict 扩容的装载因子，实际约 **120 到 150 MB**。

这带来三个具体问题：
- Redis Cluster 是按 key 分片的，单个 key 只能落在一个分片上，**水平扩容对这个 key 完全无效**。
- 主从复制是全量同步 + 增量传播，这个 key 每次 `ZADD`/`ZREM` 都要同步过去，主从带宽被它一个人吃掉。
- 做 RDB 快照或 AOF rewrite 时 fork + COW，这个大 key 被频繁修改会导致大量页复制，P99 抖动。

**坑二：`ZRANGEBYSCORE` 加 `ZREM` 不是原子的。**

两个调度实例同时执行，会取到同一批任务，然后各投递一次——重复执行。加锁能解决，但锁的粒度和性能都不划算。

**坑三：没有「不可见期」，取走就等于丢了。**

如果 `ZREM` 之后、投递之前进程崩了，任务就从系统里消失。这就是经典的「可见性超时」问题，Redis 的 List 队列（`BRPOPLPUSH`）之所以要先搬到 processing 列表，原因完全一样。

**坑四：时钟来源不统一。**

score 用哪台机器的时间算？20 台调度器各用自己的 `System.currentTimeMillis()`，NTP 偏差 ±300 毫秒很正常，结果就是有的任务早触发 300 毫秒、有的晚 300 毫秒，而且「早触发」的那批会让下游提前看到未生效的数据。

### 正确做法：按时间分桶

把一个大 key 拆成「一分钟一个桶」：

```
key = delay:bucket:<epoch_minute>      # 例如 delay:bucket:29389480
score = trigger_at 毫秒
member = task_id
```

好处立刻显现：

| 维度 | 单一大 key | 按分钟分桶 |
| --- | --- | --- |
| 单 key 成员数 | 全量 100 万 | 峰值每分钟约 1 万 |
| 单 key 内存 | 100 MB 以上 | 1 到 2 MB |
| 可水平分片 | 否 | 是（不同分钟天然落到不同 slot） |
| 过期清理 | 手动 ZREM 全量 | `EXPIRE` 自动回收 |
| 读取成本 | O(log N) 全量 | O(log 桶内) |

消费逻辑变成：每秒只查**当前分钟**和**下一分钟**的桶。

```python
def poll(redis_client, now_ms, limit=500):
    cur = now_ms // 60_000
    ids = []
    for b in (cur, cur + 1):                       # 下一分钟也扫，吸收时钟误差
        key = f"delay:bucket:{b}"
        ids += lua_pop_due(redis_client, key, now_ms, limit)
        redis_client.expire(key, 600)              # 10 分钟没取完就回收，防止泄漏
    return ids
```

注意两件事：
- **扫描下一分钟**是为了吸收多机时钟偏差与「提前一秒到达」的边界情况，属于用一点额外扫描换正确性。
- 桶的 TTL 不能太短。如果 worker 积压，桶被回收了任务就丢了；TTL 要大于「可接受的最大积压时长」，比如 10 分钟到 1 小时，同时配一个独立的对账任务去捞「过期桶里还剩的 member」。

### 原子取出：一段 Lua

`ZRANGEBYSCORE` 与 `ZREM` 必须在一次脚本里完成，Redis 单线程执行 Lua，天然原子：

```lua
-- KEYS[1] = delay:bucket:<minute>
-- ARGV[1] = now_ms, ARGV[2] = limit
local key   = KEYS[1]
local now   = tonumber(ARGV[1])
local limit = tonumber(ARGV[2])

local ids = redis.call('ZRANGEBYSCORE', key, '-inf', now, 'LIMIT', 0, limit)
if #ids == 0 then
  return {}
end
redis.call('ZREM', key, unpack(ids))
return ids
```

三个必须注意的细节：

1. **`unpack` 有参数上限**（Lua 5.1 约 8000 个栈槽，实际安全值 1000 以内），所以 `limit` 要控制在 500 到 1000，否则脚本直接报 `too many results to unpack`。
2. 这个脚本**只保证「只有一个实例能取到」**，不保证「取到就一定被执行」——取到之后进程崩了，任务还是丢了。所以必须配可见性超时。
3. Lua 里不能做耗时操作，`ZREM` 批量删除 1000 个成员会阻塞 Redis 主线程若干毫秒，需要压测确认单次执行时间远小于 1 毫秒，否则会影响同实例上的其他业务。

### 可见性超时：把崩掉的 worker 手上的任务捞回来

三段式结构：

```text
pending ZSet     score = trigger_at         任务待触发
processing ZSet  score = now + lease_ms     任务已被某个 worker 取走
hash task:payload                           任务内容
```

流程：

1. Lua 从 pending 取 N 条，同时 `ZADD processing now+lease_ms`（在同一个脚本里，保证不漏）。
2. worker 执行成功后从 processing `ZREM`，并把结果落库。
3. 一个独立的回收线程每 10 秒执行一次：

```lua
-- KEYS[1] = processing ZSet, ARGV[1] = now_ms, ARGV[2] = limit
local expired = redis.call('ZRANGEBYSCORE', KEYS[1], '-inf', ARGV[1], 'LIMIT', 0, ARGV[2])
if #expired == 0 then return {} end
redis.call('ZREM', KEYS[1], unpack(expired))
-- 归还给 pending，同时把重试次数加一由业务侧 hash 维护
redis.call('ZADD', KEYS[2], ARGV[1], unpack(expired))   -- 立即重新可触发
return expired
```

这就是「至少一次」语义的物理实现：宁可多跑一次，不能少跑一次。而「多跑一次」的安全性，必须由执行侧的幂等来兜——这一节最后会讲。

## 七、RocketMQ：18 级固定延迟与任意时间消息

如果不想自研这套「ZSet 加租约加了 Lua」，直接买 MQ 的延迟消息能力是最省事的。但要清楚它的边界。

### 4.x：18 个固定档位

RocketMQ 4.x 的延迟消息只支持 18 个级别：

```text
1s 5s 10s 30s 1m 2m 3m 4m 5m 6m 7m 8m 9m 10m 20m 30m 1h 2h
```

实现原理很巧：生产者发出的消息**不会直接进目标 topic**，而是被改写到内部 topic `SCHEDULE_TOPIC_XXXX`，`queueId = delayLevel - 1`，原 topic 与 queueId 存进消息属性，同时把 `storeTimestamp` 改写成「投递时间」（now 加延迟）。这样同一级别的消息天然按投递时间顺序排在同一个 ConsumeQueue 里。

`ScheduleMessageService` 为每个级别起一个定时任务，按 offset 顺序扫该级别的 ConsumeQueue，队首消息的投递时间到了，就把它**读出来、恢复原 topic、重新写入 CommitLog**——第二次写入才是正常消息，能被消费者看到。

这个设计的天花板很明确：

| 限制 | 原因 | 影响 |
| --- | --- | --- |
| 只有 18 个档位 | 每个档位一个队列，硬编码 | 业务要 45 分钟只能选 1 小时或自己拼 |
| 精度受扫描周期约束 | 每级一次定时扫描，默认 1 秒一次，单次最多处理一批 | 堆积时延迟放大 |
| 同档位串行 | 一级一个 ConsumeQueue | 峰值集中时同级别互相排队 |
| 二次写入放大 | 到期要重新写 CommitLog | 写入量翻倍，磁盘 IO 压力大 |

所以 4.x 的延迟消息适合「订单 30 分钟关单」「重试退避 1s/5s/30s」这类**固定档位够用**的场景，不适合「用户选的任意提醒时间」。

### 5.x：timerlog 加时间轮

5.0 起支持任意时间的定时消息，核心是 `timerlog`：

- 消息按「投递时间」追加写入 timerlog（顺序写，不做随机更新），同时消息本体仍在 CommitLog，timerlog 只存「投递时间 + 消息位置」的索引。
- 内存里维护按秒推进的时间轮，每个槽挂一个「投递时间落在这一秒」的链表，指向 timerlog 偏移。
- 定时器每秒推进，把到期槽位里的索引取出来，按偏移回 CommitLog 读消息、投递给消费者。
- 通过 checkpoint 文件记录各槽位推进到的位置，重启后从 checkpoint 重建内存时间轮。
- 投递后向 timerlog 写「已投递」标记（或延迟清理），定期滚动删除，避免 timerlog 无限增长。

能力与边界：

- 精度约 1 秒（受推进周期约束）。
- 最大延迟受 timerlog 保留期限制（官方默认量级是 3 天，可配置；具体以所用版本参数为准）。**超过保留期的任务必须换成别的手段**，比如拆成「定时任务在 D-3 再投一条延迟消息」。
- 任意时间意味着不能靠「一级一个队列」来排序，全靠内存时间轮加 timerlog 扫描，所以**单机 timerlog 的扫描吞吐就是天花板**，任务量极大时要靠多队列分片。

一句话总结这一段：

> **固定档位是「用队列做排序」，任意时间是「用时间轮做排序」。前者简单、吞吐高、精度受档位限制；后者灵活、精度约 1 秒、受 timerlog 保留期与扫描吞吐约束。**

## 八、分片与租约：多实例怎么不重复执行

单机调度器的正确性靠「一个线程」，多实例就必须解决「谁来处理哪一批任务」。

### 方案 A：静态分片

```
shard = hash(task_id) % N
```

每个实例只处理自己那 N 分之一。问题在于 N 变化：从 8 台扩到 12 台，所有任务的分片归属全部改变，rebalance 期间「旧实例已放弃、新实例还没接手」的任务会延迟，「两边都认为自己负责」的任务会重复。要靠一致性哈希把迁移量压到 1/N，但仍然需要一段「双读单写」的过渡期。

### 方案 B：时间桶抢占（推荐）

不按 task 分片，按**时间桶**抢占。每个调度实例抢「我接下来处理哪个分钟桶」的权利：

```bash
# 抢占：NX 保证只有一个赢家，PX 给租约而不是永久锁
SET lock:delay:bucket:29389480 <instance_id> NX PX 30000
```

```lua
-- 续约：只有持有者能延长，避免锁过期后被别人抢走导致的脑裂
if redis.call('GET', KEYS[1]) == ARGV[1] then
  return redis.call('PEXPIRE', KEYS[1], ARGV[2])
end
return 0
```

优点：

- **实例数变化自适应**：新实例上线后自然抢到没人处理的桶，不需要 rebalance。
- **崩溃自动接管**：实例挂了，租约 30 秒后过期，别的实例抢过来接着处理。桶内任务没被取走的还在 ZSet 里，被取走的在 processing ZSet 里由可见性超时回收——两道保险。
- **粒度可调**：一座城市整点推送 20 万条，就按「秒」分桶，抢的粒度更细，天然并行。

缺点与必须遵守的纪律：

- **必须 fail-stop，不能 fail-open**。拿不到锁就绝对不处理这个桶，哪怕队列已经积压。fail-open 的后果是两个实例同时处理同一批任务，重复执行。
- 续约必须校验持有者（上面的 Lua），否则租约过期后老实例「以为还持有」继续干活，就是脑裂。
- 租约时间要大于单个桶的处理耗时。处理一个桶要 5 秒、租约 3 秒，就一定会有两个实例在同一个桶上打架。
- Redis 不可用时，整个调度停摆。这是可接受的（延迟任务晚几秒不影响业务），但要有告警，且不能自动降级成「大家自己扫库」——那等于放弃去重。

### 方案 C：数据库 `SKIP LOCKED`

不想引入 Redis 的话，一张表加 `FOR UPDATE SKIP LOCKED` 就是天然的分布式队列，单机吞吐 3000 到 5000 任务/秒，百万级完全够用。它的成本我们在第三节算过了，问题不是正确性，是写放大和主从延迟。**百万级以下、能接受秒级精度、不想多加一个中间件，这就是最优解**——别为了架构好看硬上 Redis 集群。

## 九、触发与执行分离：调度器只做「到点投递」

一个常见的错误设计是：调度线程取到任务，直接 `ThreadPool.execute(businessTask)`。这样做的后果是调度精度被业务耗时污染——业务里有慢 SQL、有 HTTP 调用，线程池打满，调度线程阻塞，后面所有任务的触发时间全部延后，而且延迟会累积。

正确做法是把调度器和执行器彻底分开：

```text
            ┌──────────────┐         ┌──────────────┐         ┌──────────────┐
定时源  →    │  Scheduler   │  投递   │   MQ / RPC   │  消费   │   Worker     │
(cron/API)  │ 取任务+分片  │ ─────→  │  削峰缓冲    │ ─────→  │  执行业务    │
            └──────────────┘         └──────────────┘         └──────────────┘
                   │                                                   │
                   └──────────── 状态机回写 ────────────────────────────┘
```

好处：

1. **调度侧耗时可控**：只做「取 + 投递」，单条耗时微秒级，触发精度稳定。
2. **执行侧独立扩缩容**：整点 20 万条推送，加 worker 就行，调度器不受影响。
3. **天然削峰**：MQ 当缓冲，下游不会被瞬时流量打死。用 Redis 分桶方案时，桶本身就是缓冲，可以控制每次投递的速率（比如每秒最多 5000 条），让下游平滑消费。
4. **重试发生在执行侧**：业务失败重试不应该回到调度器，而是 MQ 的重试队列 / 延迟队列，避免调度器状态被污染。

代价是多了一次「投递」的失败窗口：取出来了、投递失败了，任务就处于中间态。所以状态机必须能表达这个中间态：

```text
PENDING ──取到──→ RESERVED(lease=now+30s) ──投递成功──→ PUBLISHED
   ↑                    │                                   │
   │                    └──投递失败/租约过期──┐              │
   └──────────────────────────────────────────┘             │
                                                             ↓
                                     RUNNING ──成功──→ SUCCESS
                                        │
                                        └──失败──→ FAILED(attempt+1) ──退避重排──→ PENDING
                                                          │
                                                          └──超过最大次数──→ DEAD(告警，人工介入)
```

关键点：**`RESERVED` 是必须存在的状态**。少了它，「取出来还没投出去就崩了」的任务没有任何人负责，只能靠全表对账去捞。

## 十、「已经触发但业务失败」：幂等、补偿与对账

这是面试官最爱追的一层，因为它考的是对语义边界的理解。

### 先认清边界：调度系统只能保证「至少执行一次」

exactly-once 在分布式下做不到，原因很朴素：投递成功与执行成功是两次不同的写，中间必然有崩溃窗口。如果投递成功后 worker 崩了，你不知道它到底执行了没有。

所以正确的表述是：

> 调度系统保证 **at-least-once**（每个到期任务至少被执行一次），**执行侧保证幂等**（重复执行不产生副作用），两者合起来才是业务意义上的 exactly-once。

### 幂等的四种落地方式

| 方式 | 实现 | 优点 | 局限 |
| --- | --- | --- | --- |
| 唯一索引 | `INSERT ... ON DUPLICATE KEY`，键为 task_id 加 attempt | 强一致，最简单 | 只适合「插入型」业务 |
| 去重表 | 单独一张 `exec_log(task_id, round)` 表，先写再执行 | 通用 | 多一次写，需清理 |
| Redis SETNX | `SET exec:task_id NX EX 86400` | 快，不占数据库 | Redis 挂了有窗口，TTL 内重放会被误挡 |
| 状态机守卫 | `UPDATE ... WHERE status='PENDING'`，受影响行数为 0 就跳过 | 无需额外存储 | 只适合有明确状态的业务 |

订单关单这类业务，最合适的是状态机守卫：

```sql
-- 只有从 PENDING 成功迁移到 CLOSED 的那一次才算真正关单
UPDATE orders
SET status = 'CLOSED', closed_at = NOW()
WHERE id = ? AND status = 'PENDING';
-- affected_rows = 0 → 已经被别的实例关过了，直接返回成功
```

「已经关过」被当成成功返回，而不是报错——**让重复执行变成无副作用的空操作**，这是幂等的本质。

### 重试与退避：不要用固定间隔

失败重试用指数退避，并且加抖动：

```text
第 1 次：1s ± 20%
第 2 次：5s ± 20%
第 3 次：30s ± 20%
第 4 次：5min ± 20%
第 5 次：30min ± 20%
第 6 次：2h ± 20%   → 之后进死信 DEAD
```

抖动（jitter）不是玄学：如果下游在某一刻挂了，一万个任务在 1 秒后同时重试，就是一次自制的 DDoS。加 ±20% 抖动能把重试窗口摊开。

### 每日对账：兜住所有漏网之鱼

不管设计得多严，一定有任务会卡在某个中间态。所以必须有一个独立的、丑陋但有效的对账任务：

```sql
-- 1) 该触发但还停在 PENDING（调度器漏了）
SELECT id FROM delayed_task
WHERE status = 'PENDING' AND trigger_at < NOW() - INTERVAL 1 HOUR
LIMIT 1000;

-- 2) 卡在 RUNNING 太久（worker 崩了没回写）
SELECT id FROM delayed_task
WHERE status = 'RUNNING' AND updated_at < NOW() - INTERVAL 30 MINUTE
LIMIT 1000;

-- 3) 卡在 RESERVED 超过租约（投递窗口内崩了）
SELECT id FROM delayed_task
WHERE status = 'RESERVED' AND updated_at < NOW() - INTERVAL 5 MINUTE
LIMIT 1000;
```

对账任务**就适合用扫表方案**——它每天跑一次、量小、延迟不敏感。同一套系统里用两种方案不是矛盾，是分工。

再往上一层：如果业务侧有更强的要求（比如「提醒必须发出去，发不出去要能被追责」），就需要「业务侧也记录应发清单」的双向对账，调度系统和业务系统互相比对。这属于业务架构范畴，面试时说出来是加分项——它说明你知道调度系统不是万能的。

## 十一、时钟：延迟任务最隐蔽的坑

### 坑一：系统时钟回拨

NTP 校时、虚拟机从挂起恢复、容器迁移，都可能让 `System.currentTimeMillis()` 往回跳。时间轮如果直接用它算 tick，回拨会导致：

- 槽位索引往回走，任务被反复触发（同一槽扫多遍）。
- 或者长时间不推进，整批任务卡住。

正确做法：**tick 的推进用单调时钟，触发判断用墙上时钟换算成单调差值**。

```java
long startWall  = System.currentTimeMillis();
long startNano  = System.nanoTime();

// 进程内的流逝时间用 nanoTime 算，不受校时影响
long elapsed = (System.nanoTime() - startNano) / 1_000_000L;
long nowWall = startWall + elapsed;
```

Linux 上对应 `CLOCK_MONOTONIC`。Go 的 `time.Time` 内部就带单调时钟读数，用 `t.Sub()` 而不是 `t.Unix()` 相减，能自动避开这个问题。

### 坑二：多机时钟偏差

20 台机器，NTP 收敛后偏差通常 1 到 50 毫秒，但负载高或网络差时能到几百毫秒。表现是「同一秒的任务被拆到两秒触发」或者「明明配置的是 9:00，实际 8:59:59.7 就发了」。

三种处理：

1. **统一时间源**：score 用数据库 `NOW()` 或 Redis `TIME` 生成，不用各机器的本地时间。代价是多一次网络往返。
2. **提前预取**：每次都多取 1 到 2 秒，本地按 `trigger_at` 精确排序，到点才投。这点额外扫描换来了精确的触发边界。
3. **容忍声明**：明确写进 SLA「触发时间误差 ±1 秒」，业务侧对「提前一秒」做兼容（比如判断「是否已生效」时用生效时间而不是触发时间）。

### 坑三：catch-up 风暴

进程被 GC 停顿或机器挂起 30 秒，恢复后瞬间发现「有 30 秒的任务全到期了」，时间轮要连续追赶 30 个 tick，一次性吐出所有积压任务——下游可能被瞬间打挂。

处理：**追赶要限速，而且要丢弃无意义的追赶**。

```python
def on_tick(now_ms):
    global last_tick
    gap = now_ms - last_tick
    if gap > 5000:
        log.warn("clock jump or long pause: %d ms, skipping catch-up", gap)
        last_tick = now_ms - TICK_MS      # 只补最近一格，不补 5 秒
        return
    ...
```

配合第九节的「投递限速」，即使真的积压，也是平滑地吐出去。

## 十二、选型对照表与容量算账

把前面的所有方案放在一张表里：

| 方案 | 触发精度 | 容量量级 | 持久化 | 多实例去重 | 适用场景 |
| --- | --- | --- | --- | --- | --- |
| DB 扫表 + SKIP LOCKED | 秒级（受轮询间隔） | 十万到百万 | 原生 | 原生 | 低频、可容忍延迟、不想加中间件 |
| 单机 `DelayQueue` / 堆 | 毫秒 | 万到十万 | 无 | 无 | 单进程内定时 |
| 单层时间轮（Netty） | tick 粒度 | 内存上限（百万） | 需外挂 | 需分片 | 连接超时、重试退避 |
| 分层时间轮 + WAL | tick 粒度 | 千万到亿 | timerlog | 分片 + 租约 | 自研调度中间件 |
| Redis ZSet 分桶 + Lua | 100ms 到 1s | 千万 | AOF/RDB | 租约 + 可见性超时 | 通用场景，默认推荐 |
| RocketMQ 4.x 延迟消息 | 档位级 | 亿（可堆积） | 原生 | 原生（消费组） | 固定档位够用 |
| RocketMQ 5.x 定时消息 | 约 1s | 亿 | timerlog | 原生 | 任意延迟，超长需拆段 |
| 云厂商托管调度 | 秒级 | 大 | 托管 | 托管 | 不想自运维 |

按量给一个决策线：

| 日任务量 | 峰值 TPS | 推荐方案 |
| --- | --- | --- |
| 小于 10 万 | 小于 50 | 数据库扫表，别过度设计 |
| 10 万到 100 万 | 50 到 3000 | 数据库加 `SKIP LOCKED`，或 MQ 固定档位 |
| 100 万到 1000 万 | 3000 到 3 万 | Redis 分桶加租约，或 RocketMQ 5.x |
| 大于 1000 万 | 大于 3 万 | 分层时间轮中间件 + 多级分片 + 投递限速 |

## 十三、故障与降级

面试最后一定会问「出故障怎么办」。延迟任务系统的降级原则只有一条：**宁可晚，不可乱**。

| 故障 | 表现 | 正确处理 | 错误处理 |
| --- | --- | --- | --- |
| Redis 主节点挂 | 抢占失败、取不到任务 | fail-stop 停止调度 + 告警，等主从切换 | 降级成各自扫库 → 重复执行 |
| MQ 不可写 | 投递失败率上升 | 任务退回 PENDING，限速重试 | 直接丢弃 → 任务永久丢失 |
| 下游超时 | worker 大量失败 | 退避重试 + 熔断，降低投递速率 | 无限重试 → 打挂下游 |
| 时钟跳变 | 任务提前或延后 | 检测跳变超阈值就暂停，人工确认 | 继续跑 → 任务重复或漏触发 |
| 单实例假死 | 租约不断续约但线程卡住 | 健康检查 + 强制摘除，租约不再续 | 不管 → 该分片全部积压 |
| 任务积压 | schedule lag 上涨 | 加 worker、提高单批 limit | 只看队列长度 → 误判 |

监控上有一个指标必须盯：

```
schedule_lag = now - min(pending 中最早 trigger_at)
```

它是「最老的那个已经该触发但还没被触发的任务，晚了多久」。这个指标比「队列长度」准得多——队列长度 100 万可能只是未来 24 小时的任务，而 lag 是 3 秒就说明真的出事了。

## 十四、面试追问三连

**追问一：为什么不直接用 cron / crontab？**

cron 只解决「周期性触发」，不解决四件事：无持久化（机器挂了配置就丢了）、无重试（跑失败没人管）、无分片（多实例会重复跑）、精度只到分钟。cron 适合「每天凌晨做统计」，不适合「每个用户各自的 30 分钟关单」。

**追问二：任务量涨十倍怎么办？**

先看瓶颈在哪。按第二节的账，十倍增长通常意味着峰值从 3 万 TPS 涨到 30 万 TPS，这时候不是换组件能解决的，要做三件事：① 把同一时刻的集中触发**打散**（加随机抖动，或者在业务侧就分散成多个批次）；② 分桶粒度从分钟降到秒，让并行度上去；③ 投递限速 + worker 独立扩容，把瞬时峰值拉平成可持续吞吐。真正的答案是「峰值管理」，不是「换个更快的队列」。

**追问三：怎么保证一个任务只执行一次？**

严格做不到。只能做到「至少一次投递 + 执行侧幂等」。落地三件套：状态机守卫（`UPDATE ... WHERE status = 旧值`，受影响行数为 0 就当成功）、唯一索引或去重表、每日对账兜底。回答时如果直接说「用分布式锁保证只执行一次」，面试官会追「锁过期了任务还没跑完怎么办」——你就会露馅。

## 十五、收尾

这道题的核心不是某个组件，而是三条线：

- **容量线**：瓶颈在峰值 TPS 和单槽容量，不在存储总量。所有方案的天花板都可以用一个除法算出来。
- **正确性线**：至少一次投递加执行侧幂等加对账兜底，三段缺一不可；`RESERVED` 中间态和可见性超时是防止任务凭空消失的关键。
- **时间线**：单调时钟管进程内推进，统一时间源管多机偏差，限速追赶管恢复后的风暴。

如果面试官继续往下压，还能往这几个方向走：任务之间的依赖（DAG 调度，一个任务等三个上游完成）、工作流引擎怎么表达「失败后回滚」（Saga 与补偿事务）、大规模调度的隔离（重要任务和普通任务要不要分池）、以及「调度系统本身怎么做灰度发布」（新旧两套调度器同时消费会不会重复）。这些留到后面的题。
